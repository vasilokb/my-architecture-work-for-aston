Принято. Ниже — **цельное, сдержанное и практичное описание Schema Service** без избыточных контрактов и «аналитических» подробностей. Только суть: откуда берём данные, что формируем, где и как храним, как обновляем. Учтены: **VPN/внутрикорпоративный доступ**, **PostgreSQL / MySQL / SQL Server**, **кеш-снимок в своей БД**, **шедулер обновляет кеш**.

# Schema Service — финальное описание

## 1) Назначение

Сервис формирует для UI **готовый снимок структуры учебной БД** (ER-представление): схемы, таблицы, колонки, PK/FK, индексы, вьюхи. Снимок **нормализован** (единые типы и формат) и **кешируется** в собственной БД, чтобы UI получал схему быстро и стабильно.

## 2) Границы и место в архитектуре

* Работает **только внутри корпоративной сети/VPN**.
* Общается **только** с:

    * учебными БД (**PostgreSQL / MySQL / SQL Server**) — **read-only** подключение;
    * собственной БД «Schema Snapshot DB» — хранение JSON-снимков.
* Не исполняет пользовательский SQL. Не ходит в чужие сервисные БД. **DB-per-service соблюдается.**

## 3) Откуда берём данные (метаданные)

Читаем системные каталоги/вьюхи каждой СУБД через JDBC:

* **PostgreSQL:** `pg_catalog`, `information_schema`
* **MySQL/MariaDB:** `information_schema` (+ при необходимости `SHOW CREATE TABLE`)
* **SQL Server:** `INFORMATION_SCHEMA.*`, `sys.foreign_keys`, `sys.indexes`, т. п.

Подключения — **R/O-учётками** с минимальными правами.
DSN/юзеры/пароли не хардкодятся: секреты приходят из **Jenkins Config File (DevOps-only)** → в контейнер как **env-переменные**.

## 4) Что формируем

Из «сырых» метаданных собирается **единый нормализованный снимок**:

* таблицы/колонки (типы приведены к общему набору: INT4/INT8, VARCHAR(n), NUMERIC(p,s), TIMESTAMP/DATETIME, BOOL и т. д.);
* ключи: PK/FK, индексы;
* связь таблиц (ER-граф) — для визуализации в UI;
* служебные поля: `capturedAt`, `hash` полезной нагрузки, указанные лимиты/фильтры (например, исключение системных схем).

## 5) Где и как храним (кеш)

Кеш — **обычная таблица** в собственной БД Schema Service (например, Postgres):

* Ключ кеша: `(sourceId, filterHash, formatVersion)`.
* Полезная нагрузка: **целый JSON-снимок**.
* Метаданные: `capturedAt`, `ttlExpiresAt`, `payloadHash`.
* Назначение: быстрый ответ UI без похода в учебную БД; **стабильное отображение** схемы для всех в течение TTL.

## 6) Как обновляем (политика жизненного цикла)

Три источника обновления:

1. **On-demand по запросу UI.**
   При обращении сервис смотрит кеш:

    * свежий — отдаёт его,
    * отсутствует/просрочен — собирает из БД, **сохраняет в кеш**, отдаёт.
2. **Фоновый шедулер (рекомендуется).**
   Раз в N часов проходит по зарегистрированным источникам, **пересобирает устаревшие** снимки и кладёт в кеш. UI получает всегда готовое.
3. **Ручной сброс/пересборка (админ).**
   Нужен, если учебная БД изменилась раньше TTL или для «форс-обновления».

**TTL** настраивается (типично 24 часа для стабильных стендов; 1–6 часов — для активных).
Если включены лимиты (макс. число таблиц/колонок), при срабатывании сервис возвращает **частичный снимок с пометкой**, а не «тишину».

## 7) Безопасность и доступ

* Доступ к UI/сервису — **только через VPN**.
* Аутентификация запросов — **JWT** (Identity Service).
* Подключение к учебным БД — **read-only**, таймауты и лимиты на сбор.
* Секреты — **не в коде**: Jenkins Config File → env vars (чтение на старте).
* Логи — **без секретов** и без полных DSN.

## 8) Нефункциональные цели (MVP ориентиры)

* **Время ответа из кеша:** миллисекунды.
* **Первичная сборка снимка:** до 2–5 секунд для схем ~до 100 таблиц (при адекватных лимитах).
* **Надёжность:** детерминированный снимок, `hash` для контроля изменений.
* **Простота сопровождения:** TTL + шедулер + ручной сброс; всё прозрачно SQL-запросом к кеш-таблице.

## 9) Типовые сценарии (коротко)

* **Первый заход в раздел схемы:** кеш пуст → сбор из учебной БД → сохранение → выдача.
* **Повторные заходы:** кеш свежий → мгновенная выдача без нагрузки на учебную БД.
* **Схема поменялась:** либо дождаться шедулера/TTL, либо админ жмёт «Обновить» → пересборка и новая версия в кеше.

## 10) Осознанные ограничения/риски

* Снимок — это **срез во времени**, а не «живой граф»; преднамеренно ради скорости/стабильности UI.
* Очень большие схемы требуют **жёстких лимитов** (чтобы не «взорвать» UI и сбор).
* Разные СУБД → **нормализация типов неизбежна** (мелкие несовпадения нативных типов — ожидаемы и допустимы).

## 11) Что сервис специально **не** делает

* Не выполняет пользовательские запросы (это Execution Service).
* Не ходит в чужие БД сервисов.
* Не изменяет учебные БД (только чтение метаданных).
* Не раздаёт «кусочки» по частям — **всегда один готовый снимок**.

---

### Короткое резюме для команды

Schema Service — это **«сервис-снимок»**: забирает метаданные **(R/O)** из PostgreSQL/MySQL/SQL Server, **нормализует**, складывает **целый JSON** в свою БД как кеш и **отдаёт UI мгновенно**.
Обновляется **по TTL/шедулеру/кнопкой**, секреты — через **Jenkins Config File**, доступ — **только через VPN**.
