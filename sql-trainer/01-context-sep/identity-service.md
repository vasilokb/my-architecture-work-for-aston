## Identity Service — описание

### 1. Назначение

**Identity Service** отвечает за:

* аутентификацию пользователей SQL Trainer через корпоративный **Active Directory**;
* управление сессиями (JWT);
* предоставление информации о ролях (Стажёр, Тимлид, Администратор);
* проверку прав доступа для всех остальных микросервисов (RBAC).

Это единая точка входа для всех запросов, требующих проверки личности.

---

### 2. Сценарии использования

1. **Логин**

    * Пользователь сначала подключается к корпоративной сети (VPN).
    * Открывает SQL Trainer (Web UI).
    * При попытке доступа UI перенаправляет запрос на `/login`.
    * Identity Service выполняет bind в AD, проверяет пароль и получает группу пользователя.
    * Возвращает JWT с `userId`, `displayName`, `roles`, `exp`.

2. **Верификация токена**

    * Каждый REST-запрос от UI к API Gateway несёт JWT в заголовке `Authorization: Bearer`.
    * Gateway валидирует подпись и срок жизни токена (публичный ключ Identity Service).
    * Сервис, обрабатывающий запрос, проверяет наличие нужной роли (например, `ROLE_ADMIN` для CRUD задач).

3. **Logout**

    * UI по запросу пользователя вызывает `/logout`, токен помечается как отозванный (в кэше или БД), UI стирает его из localStorage.

---

### 3. Интеграция

* **Внешние системы**:

    * Active Directory — проверка учётных данных по LDAP/LDAPS.
* **Внутренние сервисы**:

    * API Gateway — проверка JWT при каждом запросе (через public key или introspection).
    * Остальные микросервисы — проверка ролей и прав доступа (через lib или REST introspection).

---

### 4. Архитектура и компоненты

| Компонент           | Функция                                                                        |
| ------------------- | ------------------------------------------------------------------------------ |
| **Auth Controller** | REST API: `/login`, `/logout`, `/introspect`.                                  |
| **LDAP Adapter**    | Соединение с Active Directory, bind и получение атрибутов пользователя.        |
| **JWT Issuer**      | Генерация подписанного токена (HS256/RS256).                                   |
| **Session Store**   | (опционально) чёрный список отозванных токенов (Redis или внутренняя таблица). |
| **RBAC Engine**     | Проверка ролей на основе атрибутов AD.                                         |

---

### 5. Безопасность

* Доступ к приложению возможен **только из корпоративной сети** или через VPN.
* Аутентификация по **LDAPS** (TLS-шифрование).
* JWT с коротким TTL (например, 30 мин), плюс refresh-токен.
* Все REST-запросы — по HTTPS (TLS 1.2+).
* Секреты (ключи подписи JWT, LDAP bind user/pass) хранятся в Secrets Manager или в защищённых переменных окружения.

---

### 6. Типовые ошибки и обработка

| Ошибка                  | Ответ            | Сообщение пользователю           |
| ----------------------- | ---------------- | -------------------------------- |
| Неверный логин/пароль   | 401 UNAUTHORIZED | "Неверные учётные данные"        |
| У пользователя нет роли | 403 FORBIDDEN    | "Нет прав для доступа к ресурсу" |
| JWT истёк               | 401 UNAUTHORIZED | "Сессия истекла, войдите снова"  |

### 7. Пример REST-контрактов

**POST /login**
Request:

```json
{
  "username": "ivan.ivanov",
  "password": "******"
}
```

Response:

```json
{
  "token": "eyJhbGciOiJSUzI1NiIsInR...",
  "expiresIn": 1800,
  "refreshToken": "..."
}
```

**POST /introspect**

```json
{
  "token": "eyJhbGciOiJSUzI1Ni..."
}
```

Response:

```json
{
  "active": true,
  "username": "ivan.ivanov",
  "roles": ["ROLE_TRAINEE"]
}
```

## Identity Service — дополнение по безопасности

### Безопасность и хранение секретов

* **Сетевой доступ:**

    * SQL Trainer доступен только из корпоративной сети или через VPN.
    * Все запросы идут по HTTPS (TLS 1.2+).

* **Аутентификация:**

    * LDAPS к Active Directory (шифрованный канал).
    * JWT с коротким TTL (например, 30 минут) + Refresh токен.
    * Подпись JWT выполняется приватным ключом, проверка — публичным ключом на Gateway и в сервисах.

* **Хранение секретов:**

    * Секреты (ключи подписи JWT, LDAP bind user/password) **не хранятся в коде**.
    * Используется **Jenkins Config File**, доступный только DevOps.
    * При деплое ключи и пароли загружаются в окружение контейнера как **защищённые переменные** (env vars).
    * Сервис читает их из переменных окружения при старте.

* **Отзыв токенов:**

    * Храним blacklist токенов в Redis/в памяти (опционально) для сценариев logout или принудительной блокировки пользователя.
