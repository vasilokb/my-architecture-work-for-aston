### 6.3. Mitigation strategies

Ниже — стратегии снижения рисков из раздела 6.1.

---

**R1. Нагрузка на Training DB и лимит соединений**

*Риск:* одновременные тяжёлые учебные запросы, исчерпание пула коннектов, деградация скорости проверки задач.

**Mitigation:**

1. **Технические лимиты (реализация KD1):**

    * таймаут выполнения запроса 2 секунды;
    * пул соединений к Training DB фиксированного размера (50);
    * очередь запросов с предсказуемым поведением при переполнении.

2. **Мониторинг и алерты:**

    * метрики: доля запросов, завершённых по таймауту; среднее/95-й перцентиль времени проверки; использование пула коннектов;
    * оповещения при достижении порогов.

3. **Контроль сложности учебных задач:**

    * методистам даётся гайд по ограничениям: запрет “монстр-запросов” с огромным объёмом данных, неконтролируемыми join-ами и т.п.;
    * сложные задачи тестируются на нагрузочном стенде перед публикацией.

4. **Возможность ручной корректировки настроек:**

    * таймаут, размер пула и параметры очереди вынесены в конфигурацию;
    * при появлении проблем значения можно оперативно изменить без релиза кода.

---

**R2. Риск не уложиться в дедлайн 3 месяца с приемлемым качеством**

*Риск:* команда из стажёров и джунов + Kubernetes + микросервисы → не успеем или сильно просядем в качестве.

**Mitigation:**

1. **Чёткое ограничение объёма MVP:**

    * фиксируем минимальный набор сценариев: решение задач, базовый прогресс, простая отчётность;
    * любые “хотелки” (интеграции, сложная аналитика, красивый дашборд) сразу выносятся в “next release”.

2. **Приоритизация архитектурных решений:**

    * сначала реализуются ключевые решения по безопасности и данным (две БД, SSO, ограничения Training DB);
    * второстепенные оптимизации и “красота” могут быть выполнены позже.

3. **Наставничество и code review:**

    * регулярные ревью архитектором/ведущим;
    * согласованные “шаблоны” сервисов (скелет проекта, общие библиотеки, пример конфигурации).

4. **Возможность упрощений внутри микросервисного подхода:**

    * на MVP допускается общий репозиторий и упрощённый DevOps-процесс;
    * при нехватке времени можно временно уменьшить число сервисов, сохранив доменную сегрегацию в коде.

---

**R3. Зависимость от SSO (Keycloak/AD)**

*Риск:* при недоступности Keycloak/AD пользователи не могут войти в систему; ошибки конфигурации ролей рушат доступ.

**Mitigation:**

1. **Явная фиксация зависимости в AVD и OP:**

    * SQL Trainer рассматривает SSO как критичный внешний сервис;
    * это отражено в Deployment View и Security View.

2. **Совместная настройка и тестирование с командой SSO:**

    * раннее пилотное подключение к Keycloak;
    * отдельная проверка моделей ролей и групп.

3. **Диагностика и отображение ошибок:**

    * в UI выводятся понятные сообщения в случае проблем с SSO (аутентификация не доступна, попробуйте позже/обратитесь в поддержку);
    * логирование ошибок интеграции с Keycloak.

4. **Оговорка SLA и план действий при инцидентах:**

    * ответственность за доступность SSO лежит на соответствующей команде;
    * SQL Trainer использует их стандартные каналы инцидент-менеджмента.

---

**R4. Отсутствие формального ревью безопасности со стороны ИБ на момент MVP**

*Риск:* модель безопасности построена “по best practices”, но формально не утверждена ИБ; могут всплыть новые требования.

**Mitigation:**

1. **Явная фиксация текущей модели в Security View:**

    * все допущения и решения по безопасности описаны в отдельном разделе AVD;
    * упрощения (например, проверка JWT только на входе) помечены как “MVP only”.

2. **Ранний запрос ревью ИБ:**

    * перед выпуском MVP инициируется консультация с ИБ;
    * документ AVD и Security View передаётся как исходная точка.

3. **Готовность к эволюционным изменениями:**

    * архитектура изначально предполагает возможность усиления:

        * проверка JWT в сервисах;
        * дополнительные зоны и сегментация;
        * расширенное логирование и аудит;
    * изменения можно внести без полной ломки стека и структуры.

4. **Минимизация рисков за счёт контура:**

    * стенд доступен только из корпоративной сети/VPN;
    * используются учебные данные, изолированные от боевых;
    * базы данных не доступны напрямую из пользовательской зоны.
