### Executive Summary

**Цель системы**
SQL Trainer — внутренняя веб-система для обучения сотрудников базовым и продвинутым навыкам работы с SQL (операторы SELECT). Цели MVP:

* обеспечить стажёрам и аналитикам регулярную практику (не менее 20 решённых задач в день на человека);
* выровнять базовый уровень владения SQL по компании;
* дать руководителям и методистам прозрачную статистику по прогрессу и типичным ошибкам.

Целевая метрика по производительности: среднее время проверки одного решения (выполнение запроса + сравнение результата) не более 1 секунды для типовых задач.

**Краткое описание решения**
SQL Trainer — SPA-приложение на React, работающее через корпоративный VPN и SSO (Keycloak/AD). Пользователь входит по SSO, выбирает курс и задачи, вводит SQL-запрос (SELECT) в веб-редакторе и отправляет его на проверку. Backend на Java + Spring выполняет запрос над учебной `Training DB`, сравнивает результат с эталонным и сохраняет попытку в `App DB`. Методисты создают задачи и учебные наборы данных, просматривают статистику по сотрудникам и типичным ошибкам. Система развёрнута во внутренней инфраструктуре (Hetzner), доступ извне не предусмотрен.

**Ключевые архитектурные решения**

* **Стек и архитектурный стиль**

    * Frontend: React SPA.
    * Backend: Java + Spring, единая платформа (монолит с внутренним разделением на домены tasks/users/progress/execution) в рамках MVP, с возможностью дальнейшего выделения микросервисов.
    * Базы данных: PostgreSQL.
    * Веб-слой: Nginx (reverse proxy + базовая логика API-шлюза).

* **Разделение данных: App DB и Training DB**

    * `App DB` — сервисные данные (курсы, задачи, пользователи, история попыток, отчёты, настройки).
    * `Training DB` — учебные схемы и наборы данных, над которыми выполняются запросы обучающихся.
    * Базы размещены на отдельных серверах, доступ к ним возможен только со стороны backend-приложения по JDBC; прямой доступ из пользовательской сети отсутствует.

* **Безопасность и доступ**

    * Доступ к системе — только из корпоративной сети/через VPN, по HTTPS.
    * Аутентификация и базовая авторизация — через Keycloak/SSO и Active Directory; SQL Trainer не хранит пароли и локальные учётные записи.
    * Учебные данные физически и логически изолированы от боевых систем и не содержат реальных клиентских данных.
    * Для учебного стенда применяется упрощённая модель: проверка JWT-токена на входе (на уровне API-шлюза/Nginx), внутренние сервисы доверяют результату и используют только роли/атрибуты из токена. Это решение зафиксировано как **MVP only**; для “продового” сценария предусмотрен переход к схеме Authorization Code + PKCE/BFF и валидации JWT в сервисах.

* **Управление нагрузкой на Training DB**

    * Максимальное время выполнения учебного SQL-запроса — 2 секунды; по истечении таймаута запрос прерывается, соединение возвращается в пул.
    * Размер пула соединений к `Training DB` — 50 соединений; дополнительные запросы ставятся в очередь.
    * Параметры таймаута и размера пула конфигурируемы и подлежат корректировке по результатам нагрузочного тестирования и эксплуатации.

* **Эксплуатация и наблюдаемость**

    * Выделены среды Dev, Test, Prod (внутренний учебный стенд).
    * На Prod мониторятся занятость пула соединений к `Training DB`, время проверки задач (среднее и p95), количество запросов, прерванных по таймауту, а также ошибки SSO.
    * Все попытки решения задач сохраняются в истории (`App DB`) с полным текстом SQL, временем, результатом и длительностью выполнения.

**Основные риски и допущения**

* **Риск R1 — нагрузка на Training DB.**
  При всплеске одновременных тяжёлых запросов возможно исчерпание пула соединений и деградация производительности. Смягчается введением таймаута, ограничением пула, очередью запросов и мониторингом ключевых метрик.

* **Риск R2 — срок MVP 3 месяца и уровень команды (стажёры/джуниоры).**
  Существует риск недостижения требуемого качества при попытке реализовать “взрослые” решения. Смягчается жёстким ограничением объёма MVP и явными архитектурными упрощениями, зафиксированными как временные (MVP only).

* **Риск R3 — зависимость от SSO (Keycloak/AD).**
  Недоступность SSO делает SQL Trainer недоступным для входа пользователей. Предполагается, что SSO поддерживается отдельной командой по корпоративным SLA; на стороне SQL Trainer добавлен мониторинг ошибок аутентификации.

* **Риск R4 — отсутствие формального ревью ИБ на момент MVP.**
  Архитектура учебного стенда построена по стандартным практикам (зоны, VPN, SSO, отсутствие боевых данных, разделение App/Training DB), но формально не утверждена службой ИБ. В документации зафиксирован текущий дизайн безопасности и целевой “взрослый” вариант; после ревью ИБ планируется внести необходимые корректировки.

Архитектурные решения и ограничения, описанные в настоящем документе, направлены на то, чтобы в рамках ограниченного срока MVP и возможностей команды обеспечить баланс между безопасностью, производительностью и простотой реализации для учебного стенда SQL Trainer.
