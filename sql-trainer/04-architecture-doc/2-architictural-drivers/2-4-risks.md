### 2.4. Риски и допущения

Данный подраздел фиксирует ключевые риски, связанные с реализацией и эксплуатацией Системы, а также допущения, на которых основаны архитектурные решения и оценки.

---

#### 2.4.1. Ключевые риски

**R1. Нагрузка на Training DB при одновременном выполнении тяжёлых запросов**

**Описание**
Существует риск, что при одновременном выполнении большого числа сложных учебных SQL-запросов (многотабличные `SELECT` с агрегациями и фильтрацией) учебная база данных `Training DB` не выдержит нагрузку. Возможные последствия:

* исчерпание пула соединений к `Training DB`;
* существенный рост времени проверки задач (выход за целевое значение по производительности);
* деградация производительности Системы для всех пользователей.

**Связанные допущения**

* A1: типовые учебные задачи спроектированы так, чтобы не требовать чрезмерно тяжёлых запросов по очень большим наборам данных;
* A2: количество одновременных пользователей и частота запросов находятся в пределах ожидаемых значений.

**Стратегия смягчения**

* ограничение максимального времени выполнения одного запроса к `Training DB` (архитектурно задаётся таймаут выполнения);
* ограничение размера пула соединений к `Training DB` и использование очереди запросов;
* настройка мониторинга занятости пула, времени проверки задач и количества запросов, прерванных по таймауту;
* при росте нагрузки — возможность масштабирования `Training DB` и добавления read-only реплик для аналитических сценариев без влияния на учебный контур.

---

**R2. Риск не уложиться в сроки MVP и/или снижение качества реализации**

**Описание**
MVP Системы реализуется в ограниченный срок (3 месяца) командой, в которую входят стажёры и специалисты уровня junior, при этом архитектура строится на основе микросервисного подхода и Kubernetes. Существует риск:

* не успеть реализовать согласованный объём функционала;
* сократить качество реализации (нестабильность, технический долг, упрощённая безопасность и наблюдаемость) для укладывания в срок.

**Связанные допущения**

* A3: объём MVP ограничивается базовыми сценариями обучения, без сложной аналитики и интеграций;
* A4: команда разработки получает регулярную поддержку и ревью со стороны опытных специалистов (архитектор, ведущий разработчик, DevOps).

**Стратегия смягчения**

* приоритизация ключевых учебных сценариев (решение задач, хранение прогресса, базовая отчётность);
* фиксация в архитектурной документации упрощений, допустимых для учебного стенда (и пометка “MVP only” для решений, не подходящих для промышленного контура);
* использование проверенного стека (React, Java + Spring, PostgreSQL, Kubernetes) и минимизация дополнительных технологий;
* проведение регулярных архитектурных и код-ревью для критичных частей (работа с `Training DB`, безопасность, интеграция с SSO).

---

**R3. Зависимость от корпоративного SSO (Keycloak/AD)**

**Описание**
Система полностью полагается на корпоративный SSO/Keycloak и Active Directory для аутентификации и получения ролей пользователей. При недоступности SSO или ошибках конфигурации:

* пользователи не могут войти в Систему, даже если сами сервисы SQL Trainer и базы данных доступны;
* часть сценариев (назначение ролей, доступ к административному функционалу) может работать некорректно.

**Связанные допущения**

* A5: работоспособность и доступность Keycloak/AD обеспечиваются отдельной командой в соответствии с корпоративными соглашениями по уровню сервиса;
* A6: интеграция SQL Trainer с SSO корректно согласована и поддерживается совместно с соответствующими подразделениями.

**Стратегия смягчения**

* чёткое разделение зон ответственности (учётные записи и пароли управляются на стороне AD/SSO, SQL Trainer не внедряет собственную модель аутентификации);
* использование стандартных протоколов и рекомендованных настроек для интеграции с Keycloak;
* мониторинг ошибок аутентификации и технических ошибок взаимодействия с SSO;
* согласование с ответственными за SSO регламентов плановых работ и ожиданий по доступности.

---

**R4. Отсутствие формального ревью безопасности со стороны ИБ на момент MVP**

**Описание**
Архитектура учебного стенда SQL Trainer проектируется с учётом стандартных практик безопасности (зоны, VPN, SSO, изоляция учебных данных), однако на момент подготовки настоящего документа формальное ревью информационной безопасности и официальное утверждение модели могут отсутствовать. Возможны дополнительные требования со стороны ИБ, влияющие на архитектурные решения.

**Связанные допущения**

* A7: текущая модель безопасности (VPN, SSO, отсутствие боевых данных, разделение `App DB` и `Training DB`, запрет прямого доступа к БД из пользовательской сети) соответствует базовым требованиям ИБ к внутренним учебным системам;
* A8: потенциальные доработки по результатам формального ревью ИБ смогут быть реализованы без радикального изменения архитектурного ядра и разрушения учебных целей проекта.

**Стратегия смягчения**

* явная фиксация в архитектурной документации текущей модели безопасности и допущений, сделанных для учебного стенда;
* указание целевых “взрослых” решений (например, более строгие схемы работы с токенами, дополнительные меры контроля доступа) в разделе развития архитектуры;
* подготовка материалов для ревью ИБ (диаграммы зон, описание потоков данных, перечень логируемых событий);
* планирование времени и ресурсов на внедрение корректировок по результатам ревью.

---

#### 2.4.2. Сводный перечень допущений

Для удобства анализа ниже приведён сводный список ключевых допущений, на которых базируется архитектура MVP:

* **A1.** Типовые учебные задачи не требуют выполнения чрезмерно тяжёлых SQL-запросов по очень большим наборам данных.
* **A2.** Количество одновременных пользователей и частота выполнения запросов находятся в пределах рассчитанных нагрузок для учебного стенда.
* **A3.** Объём MVP ограничен базовыми сценариями обучения без сложной аналитики и внешних интеграций.
* **A4.** Команда разработки (стажёры, специалисты уровня junior) получает достаточную поддержку и ревью со стороны опытных специалистов.
* **A5.** Работу и доступность SSO/Keycloak и AD обеспечивает отдельная команда по корпоративным договорённостям об уровне сервиса.
* **A6.** Интеграция SQL Trainer с SSO настроена и сопровождается совместно с ответственными подразделениями.
* **A7.** Модель безопасности учебного стенда (VPN, SSO, отсутствие боевых данных, разделение `App DB` и `Training DB`, запрет прямого доступа к БД) соответствует базовым требованиям корпоративной информационной безопасности.
* **A8.** Требования ИБ, которые могут быть сформулированы по итогам формального ревью, позволят адаптировать архитектуру эволюционным путём, без полной переработки ключевых решений.

Указанные риски и допущения используются при анализе архитектурных альтернатив, планировании объёма работ и оценке последствий изменений требований.
