### 4.2. Container View

#### 4.2.1. Назначение представления

Container View показывает основные программные контейнеры Системы «SQL Trainer» и их взаимодействия: веб-интерфейс, серверные сервисы, базы данных, компоненты периметра и внешние системы. Цель представления — дать единое понимание того, из каких крупных частей состоит решение и какие протоколы используются между ними, без детализации внутреннего устройства каждого сервиса.

---

#### 4.2.2. Перечень контейнеров

В рамках Container View выделяются следующие контейнеры:

1. **Nginx (Reverse Proxy / API Gateway-логика)**

    * Назначение: точка входа HTTP(S) в Систему, терминация TLS, маршрутизация запросов.
    * Функции:

        * отдача статических ресурсов фронтенда (React SPA);
        * проксирование запросов от браузера к backend-сервисам в кластере Kubernetes;
        * возможная базовая проверка токенов и маршрутизация по API (ограниченная логика API-шлюза в рамках согласованной модели безопасности).
    * Основные протоколы:

        * HTTPS от браузера пользователей;
        * HTTP(S) к фронтенду и микросервисам backend.

2. **Frontend (React SPA)**

    * Назначение: пользовательский интерфейс, работающий в браузере сотрудников.
    * Функции:

        * отображение курсов, модулей, задач, учебных данных, отчётности;
        * интерфейс ввода SQL-запросов (операторы `SELECT`) и отправки решений на проверку;
        * отображение результатов проверки и прогресса обучения;
        * взаимодействие с backend по REST API.
    * Основные протоколы:

        * HTTPS запросы к API backend (через Nginx).

3. **Backend-сервисы (Java/Spring, микросервисы)**
   На уровне контейнеров backend представлен набором микросервисов, развёрнутых в Kubernetes. Логически выделяются следующие сервисы:

    * **Users/Auth Service**

        * работа с данными пользователей в контексте тренажёра;
        * получение и проверка ролей на основе токенов SSO;
        * доступ к данным пользователей в `App DB`.

    * **Courses/Tasks Service**

        * управление курсами, модулями и задачами;
        * выдача содержимого задач и связанных настроек на фронтенд;
        * работа с сущностями курсов и задач в `App DB`.

    * **Execution Service**

        * приём SQL-запросов обучающихся;
        * проверка на допустимость (только `SELECT`, ограничения по синтаксису при необходимости);
        * выполнение запросов над `Training DB` с учётом настроек таймаута и пула соединений;
        * сравнение результатов с эталонными и формирование вердикта.

    * **Progress/Reporting Service**

        * запись и агрегирование информации о попытках из `App DB`;
        * расчёт прогресса по курсам и задачам;
        * предоставление данных для отчётов методистам и руководителям.

   Все backend-сервисы реализованы на Java с использованием Spring и взаимодействуют между собой через внутренние HTTP(S) API либо иные согласованные механизмы (например, асинхронные очереди при расширении архитектуры).

    * Основные протоколы:

        * HTTP(S) от фронтенда (через Nginx) к микросервисам;
        * JDBC соединения к `App DB` и `Training DB`;
        * HTTPS к Keycloak при необходимости обращения к SSO на прикладном уровне.

4. **App DB (PostgreSQL)**

    * Назначение: хранение сервисных данных Системы.
    * Содержимое:

        * пользователи и их роли в контексте тренажёра (в части, относящейся к приложению);
        * курсы, модули, задачи, настройки задач и курсов;
        * история попыток решения (включая текст SQL-запросов, результаты, длительность);
        * агрегированные данные для базовой отчётности.
    * Доступ:

        * только со стороны backend-сервисов по JDBC;
        * прямой доступ из пользовательской сети не предоставляется.
    * Основной протокол:

        * соединения PostgreSQL (JDBC поверх TCP).

5. **Training DB (PostgreSQL)**

    * Назначение: хранение учебных схем и наборов данных, над которыми выполняются учебные SQL-запросы.
    * Содержимое:

        * учебные таблицы и схемы, используемые в задачах;
        * тестовые данные, не содержащие боевых клиентских сведений.
    * Доступ:

        * только со стороны Execution Service и, при необходимости, других backend-сервисов по JDBC;
        * прямой доступ из пользовательской сети и из других приложений компании не планируется в рамках архитектурной модели безопасности.
    * Основной протокол:

        * соединения PostgreSQL (JDBC поверх TCP).

6. **SSO / Keycloak (внешний контейнер)**

    * Назначение: центральная система аутентификации и авторизации пользователей.
    * Функции:

        * аутентификация пользователей по корпоративным учетным данным;
        * выдача токенов доступа и обновления, передача атрибутов пользователя и ролей.
    * Для SQL Trainer Keycloak рассматривается как внешняя по отношению к Системе часть корпоративной инфраструктуры.
    * Основные протоколы:

        * HTTPS (OIDC/OAuth2) при перенаправлении браузера пользователей и обмене токенами;
        * взаимодействие с Active Directory по протоколам LDAP/LDAPS (не является прямым взаимодействием SQL Trainer, но влияет на контекст).

---

#### 4.2.3. Связи и протоколы между контейнерами

На уровне Container View фиксируются следующие основные связи:

* Браузер пользователей взаимодействует с **Nginx** и **Frontend (React SPA)** по HTTPS.
* **Frontend** обращается к backend-сервисам через **Nginx** по HTTPS/HTTP (REST API).
* Backend-сервисы взаимодействуют:

    * с **App DB** и **Training DB** по JDBC (PostgreSQL поверх TCP);
    * с **Keycloak** по HTTPS (OIDC/OAuth2) при необходимости валидации токенов или получения метаданных.
* Взаимодействия между backend-сервисами реализуются через внутренние HTTP(S) API и могут быть расширены асинхронными механизмами при развитии архитектуры.

Container View служит основой для построения Deployment View, где те же контейнеры будут размещены на конкретных элементах инфраструктуры (кластер Kubernetes, базы данных, периметровый Nginx и связанные узлы).
