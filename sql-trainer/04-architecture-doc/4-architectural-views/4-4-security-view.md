### 4.4. Security View

#### 4.4.1. Назначение представления

Цель данного представления – описать модель безопасности системы SQL Trainer: зоны доверия, сетевые взаимодействия и ключевые решения, обеспечивающие изоляцию учебных данных от боевых систем, а также доступ к приложению только через корпоративную инфраструктуру (VPN, внутренняя сеть, SSO).

Security View используется для согласования модели безопасности с ИБ, архитекторами и эксплуатацией и служит основой для дальнейшего развития решений по аутентификации и авторизации.

---

#### 4.4.2. Зоны безопасности

В рамках Security View выделяются следующие зоны:

1. **Пользовательская зона (Employee Network / VPN)**

    * Рабочие станции сотрудников (стажёры, аналитики, методисты, администраторы), подключённые к корпоративной сети или через VPN.
    * Из этой зоны пользователи получают доступ к SQL Trainer через веб-браузер по HTTPS.
    * Прямое подключение к учебным базам данных с рабочих станций обучающихся и методистов не допускается.

2. **Зона приложения (Application Zone)**

    * Серверы, на которых размещены Nginx, серверное приложение SQL Trainer (Java + Spring) и статические файлы SPA.
    * Это основной узел обработки запросов пользователей, выполнения учебных SQL-запросов и работы с базами данных.
    * Логическая роль API-шлюза (проверка токенов и маршрутизация запросов) реализуется здесь, на базе Nginx/ingress или отдельного gateway-компонента.

3. **Зона сервисных данных (App DB Zone)**

    * Сервер базы данных App DB (PostgreSQL), хранящий сервисные данные приложения: курсы, задачи, попытки, отчётность, настройки и другие служебные сущности.
    * Доступ к зоне предоставляется только серверному приложению SQL Trainer по внутреннему соединению (JDBC, порт 5432/tcp).

4. **Зона учебных данных (Training DB Zone)**

    * Сервер базы данных Training DB (PostgreSQL), содержащий учебные схемы и данные для выполнения SQL-запросов обучающихся.
    * Учебные данные физически и логически изолированы от боевых систем и не содержат боевых данных или персональных данных клиентов.
    * Доступ к зоне имеет только серверное приложение SQL Trainer по JDBC (порт 5432/tcp).
    * Прямой доступ из пользовательской сети и других приложений компании в рамках MVP не предусмотрен.

5. **Зона аутентификации (SSO Zone)**

    * Кластер Keycloak/SSO и Active Directory, управляемый отдельной командой и рассматриваемый как корпоративный сервис.
    * SQL Trainer использует Keycloak для аутентификации пользователей и получения их ролей и атрибутов; учётные записи и пароли внутри самого приложения не хранятся.

---

#### 4.4.3. Основные потоки доступа и протоколы

1. **Доступ пользователя к приложению**

    * Пользователи из пользовательской зоны обращаются к SQL Trainer через веб-браузер по HTTPS (порт 443/tcp), подключаясь к Nginx в зоне приложения.

2. **Доступ приложения к базам данных**

    * Серверное приложение SQL Trainer устанавливает соединения по JDBC (PostgreSQL, порт 5432/tcp) к:

        * App DB – для работы с сервисными данными приложения;
        * Training DB – для выполнения учебных SQL-запросов обучающихся.
    * Прямой сетевой доступ к этим базам данных из пользовательской зоны отсутствует.

3. **Взаимодействие приложения и SSO**

    * Для аутентификации и авторизации используется взаимодействие с Keycloak/SSO по протоколу HTTPS с использованием OpenID Connect / OAuth2.
    * Конкретные сценарии аутентификации (целевой вариант Authorization Code с PKCE и HttpOnly-cookie и упрощённый сценарий для MVP) описаны отдельно и согласуются с требованиями информационной безопасности.

---

#### 4.4.4. Ключевые решения по безопасности

1. **Изоляция учебных данных**

    * Учебные данные размещены в отдельной базе Training DB и физически и логически изолированы от сервисных данных и боевых систем.
    * Выполнение учебных SQL-запросов не может повлиять на реальные боевые данные.

2. **Доступ только через корпоративную инфраструктуру**

    * Доступ к SQL Trainer возможен только из корпоративной сети или через VPN и только через веб-интерфейс по HTTPS.
    * Публикация приложения во внешний периметр не предусмотрена.

3. **Централизованная аутентификация и базовая авторизация**

    * Аутентификация и базовая авторизация централизованы в корпоративном SSO (Keycloak/AD).
    * SQL Trainer не управляет паролями и не хранит локальные учётные записи пользователей.

4. **Запрет прямого доступа к учебной БД**

    * Прямое подключение к учебной базе данных с рабочих станций сотрудников в ролях обучающихся и методистов не допускается.
    * Все операции с учебными данными выполняются через серверное приложение SQL Trainer.

5. **Доступ других систем к агрегированным данным**

    * Возможный доступ других внутренних систем к агрегированной информации об учебной активности рассматривается отдельно.
    * Может быть реализован через реплику базы данных в режиме только чтение или через выгрузки, без изменения модели безопасности основного контура SQL Trainer.

---

#### 4.4.5. Аутентификация, токены и роль API-шлюза

##### 4.4.5.1. Учебный стенд (MVP под VPN)

Для учебного MVP используется упрощённая модель безопасности, достаточная для внутреннего стенда с учебными данными:

1. Вся внешняя нагрузка проходит через единую логическую точку входа – API-шлюз (Nginx/ingress в зоне приложения).

2. После успешной аутентификации пользователя в Keycloak access token сохраняется в cookie `sql_access_token` со следующими атрибутами:

    * `Secure`;
    * `SameSite=Strict`;
    * ограниченный срок жизни (Max-Age), согласованный с политикой безопасности.

3. Браузер отправляет эту cookie автоматически при обращении к SQL Trainer. Фронтенд-приложение формирует заголовок `Authorization: Bearer …` от имени пользователя.

4. API-шлюз на каждом запросе:

    * извлекает токен из cookie `sql_access_token`;
    * валидирует JWT с помощью интроспекции в Keycloak: проверяет активность токена, срок действия, issuer, audience и другие обязательные параметры;
    * при успешной проверке проксирует запрос во внутренние сервисы (Execution, Tasks и другие), добавляя служебные заголовки с идентификатором пользователя, ролями и другими атрибутами, полученными из токена.

5. Внутренние сервисы в рамках MVP не выполняют криптографическую проверку JWT. Они доверяют проверке на входе API-шлюза и используют только переданные идентификаторы и роли для принятия решений об авторизации.

6. Такой подход выбран осознанно как компромисс между простотой реализации и достаточной безопасностью: система развёрнута во внутренней сети под VPN, работает только с учебными данными и не содержит боевых клиентских данных.

##### 4.4.5.2. Рекомендации для развития (целевой “продовый” вариант)

Для более зрелого, критичного для бизнеса решения рекомендуется более строгая модель:

1. API-шлюз по-прежнему выполняет первичную проверку токена, отсеивает явно невалидные запросы и защищает внешний периметр.

2. Каждый внутренний сервис, который обрабатывает защищённые запросы, самостоятельно валидирует JWT:

    * проверяет подпись по JWKS;
    * проверяет срок действия, issuer, audience и другие требования безопасности;
    * реализует собственные правила авторизации на основе содержимого токена.

3. При возникновении проблем с производительностью, связанных с проверкой токена по интроспекции в API-шлюзе, допускается переход на модель проверки токена по JWKS.

4. В целевой модели после успешной аутентификации пользователя в Keycloak сервер аутентификации перенаправляет пользователя на API-шлюз, который добавляет в ответ cookie с access token и атрибутом `HttpOnly`. В этом случае браузер отправляет cookie автоматически при обращении к SQL Trainer, без явного формирования заголовка `Authorization: Bearer …` на стороне фронтенда.

5. Переход от модели MVP к целевой модели фиксируется как архитектурное направление развития SQL Trainer и должен быть учтён при масштабировании системы и включении её в более широкий ландшафт корпоративных сервисов.
