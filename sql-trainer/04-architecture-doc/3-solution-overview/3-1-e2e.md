## 3. Обзор решения (Solution Overview)

### 3.1. Сценарий end-to-end (основной пользовательский поток)

Данный раздел описывает базовый сквозной сценарий работы обучающегося с Системой «SQL Trainer» — от входа до получения результата проверки решения задачи. Этот сценарий является ключевым для проектирования архитектуры, так как проходит через все основные компоненты и интеграции.

1. **Доступ к Системе и аутентификация**

* Пользователь устанавливает подключение к корпоративной сети (напрямую либо через VPN) и открывает в браузере адрес SQL Trainer.
* Запрос поступает на Nginx во внутренней инфраструктуре, после чего перенаправляется на фронтенд-приложение (React SPA), размещённое в кластере Kubernetes.
* При отсутствии действующей сессии пользователю отображается страница входа через корпоративный SSO.
* Браузер пользователя направляется на Keycloak; пользователь проходит аутентификацию с использованием корпоративных учётных данных (AD).
* После успешной аутентификации Keycloak возвращает в Систему данные о пользователе и его ролях, формируется авторизованная сессия.

2. **Навигация по курсам и выбор задачи**

* После входа пользователю отображается главная страница Системы с перечнем доступных курсов и модулей, соответствующих его роли и назначениям.
* Обучающийся выбирает курс, открывает список задач и выбирает конкретную задачу для решения.
* Фронтенд запрашивает через соответствующие backend-сервисы (например, `courses`/`tasks`) данные о задаче из `App DB` и отображает:

    * текст условия;
    * при необходимости примеры структуры учебных таблиц и примеры данных;
    * вспомогательную информацию (уровень сложности, подсказки, ограничения).

3. **Ввод и отправка SQL-запроса**

* Пользователь вводит решение задачи в виде SQL-запроса (оператор `SELECT`) в встроенном редакторе.
* По команде «Выполнить» фронтенд отправляет запрос на backend (например, сервис `execution`) через Nginx по защищённому HTTP-интерфейсу с учётом действующей сессии и токенов авторизации.

4. **Проверка решения на стороне backend**

* Backend-сервис, отвечающий за выполнение учебных запросов, получает:

    * идентификатор пользователя;
    * идентификатор задачи;
    * текст SQL-запроса.
* Сервис валидирует запрос на предмет соблюдения допустимых ограничений (разрешённые конструкции, только операции чтения) и выбирает соответствующую учебную схему и набор данных в `Training DB`.
* Запрос выполняется над `Training DB` с учётом заданных ограничений по времени выполнения и параметров пула соединений.
* Результат запроса сравнивается с эталонным результатом или эталонным SQL-решением, хранящимся в `App DB`.
* Формируется вердикт проверки (успешно, частично верно, неверно), при необходимости — краткий комментарий.

5. **Сохранение истории и возврат результата пользователю**

* Backend сохраняет информацию о попытке в `App DB`:

    * идентификатор пользователя и задачи;
    * текст SQL-запроса;
    * статус проверки и, при необходимости, детализацию результата;
    * длительность выполнения запроса и проверки.
* Сформированный вердикт передаётся во фронтенд.
* Пользовательский интерфейс отображает:

    * статус проверки;
    * табличный результат выполнения запроса (в пределах установленного лимита строк);
    * дополнительные комментарии (например, указание на типичную ошибку или подсказку, если она разрешена настройками курса).

6. **Анализ прогресса и повторные попытки**

* Обучающийся при необходимости может скорректировать SQL-запрос и выполнить новую попытку решения задачи.
* На основе накопленных попыток формируется прогресс по задаче, модулю и курсу.
* Методисты и руководители получают доступ к агрегированной отчётности по попыткам и прогрессу сотрудников через соответствующие интерфейсы Системы, использующие данные из `App DB`.

Описанный сквозной сценарий используется в качестве основы для проектирования архитектурных представлений (Context, Container, Deployment, Security View) и выбора ключевых архитектурных решений, связанных с производительностью, нагрузкой на `Training DB`, безопасностью и эксплуатацией.
