### 8.2.2. Цели и область покрытия

**Цель Deployability View:**

Обеспечить для SQL-тренажёра:

1. Быстрое и предсказуемое развёртывание новых версий сервисов.
2. Безопасный и быстрый откат проблемных релизов.
3. Возможность частичных выкатываний по сервисам и по функциональности.
4. Минимальное негативное влияние релизов на ключевые пользовательские сценарии (чтение задач, проверка решений, работа уже залогиненных пользователей).

**В область представления входят:**

* Сервисы:

    * UI (frontend),
    * Backend API,
    * Execution Service,
    * AuthFacade (интеграция с корпоративным SSO/IdP).
* Хранилища:

    * Tasks DB,
    * Progress/Results DB,
    * Sandbox DB.
* Инфраструктура:

    * Kubernetes/контейнерная платформа,
    * CI/CD-пайплайн.

### 8.2.3. Целевые сценарии развёртываемости

#### D1. Деплой новой версии Execution Service без простоя

* Источник (Source): разработчик / владелец продукта.
* Стимул (Stimulus): подготовлена новая версия `Execution Service` с исправлением ошибки или улучшением логики проверки SQL; она одобрена к включению в релиз.
* Артефакт (Artifact): сервис `Execution Service` (контейнерный образ, Deployment).
* Окружение (Environment): production, рабочее время; пользователи активно решают задачи и запускают проверки.
* Реакция (Response):

    * новая версия Execution собирается, проходит pipeline и разворачивается как rolling update или через canary;
    * во время выката часть pod’ов обслуживает трафик на старой версии, часть — на новой;
    * при ухудшении метрик или росте ошибок выполняется быстрый rollback на предыдущую стабильную версию.
* Метрика (Response measure):

    * максимальное снижение доступности функции “Проверить решение” из-за релиза Execution — не более заданного порога (например, не более 30 секунд деградации);
    * время отката на предыдущую версию — не более заранее оговоренного значения (например, до 15 минут);
    * доля релизов Execution, вызвавших инциденты, стремится к нулю.

#### D2. Миграция схемы Tasks DB и Backend API

* Источник (Source): разработчик / DBA.
* Стимул (Stimulus): необходимо изменить схему `Tasks DB` (новые поля задач, статусы, связи) и соответствующую часть `Backend API`.
* Артефакты (Artifacts): миграции `Tasks DB` + новая версия `Backend API`.
* Окружение (Environment): dev → stage → production.
* Реакция (Response):

    * миграции и новая версия Backend проходят полный pipeline (dev, stage с тестированием);
    * в production миграции выполняются в плановом окне, при ошибках возможен откат или альтернативный план восстановления;
    * UI → Backend → Tasks DB сохраняют работоспособность, данные не повреждаются.
* Метрика (Response measure):

    * миграции выполняются за отведённое окно и не выходят за него;
    * нет потери данных из-за миграции;
    * для заранее помеченных обратимых изменений доступен откат схемы.

#### D3. Частичный запуск новой функциональности под фича-флагом

* Источник (Source): владелец продукта.
* Стимул (Stimulus): требуется добавить новую функциональность (например, новый тип задач, подсказки при решении, расширенный отчёт), но с контролируемым риском для производственного контура.
* Артефакты (Artifacts): изменения в Backend, UI и конфигурации фичефлагов.
* Окружение (Environment): production, ограниченная аудитория (internal/beta).
* Реакция (Response):

    * код новой фичи выкатывается в составе обычного релиза, но по умолчанию выключен флагом;
    * фича включается только для ограниченной аудитории;
    * при проблемах фича отключается изменением флага (kill switch), без отката всего релиза.
* Метрика (Response measure):

    * включение/выключение фичи занимает минуты, не требует релиза;
    * проблемы с новой функциональностью не влекут за собой откат релиза целиком.

### 8.2.4. Архитектурные решения и тактики

#### 8.2.4.1. Управление pipeline и окружениями

* Ввести простой, но формальный **deployment pipeline**:

    * окружения: `dev`, `stage`, `prod`;
    * шаги: сборка → автоматические тесты → deploy на dev → тесты/проверка → deploy на stage → ручное подтверждение → deploy на prod.
* Все операции деплоя оформить как код:

    * манифесты Kubernetes / Helm charts для `backend`, `execution`, UI, AuthFacade;
    * миграции БД через Flyway/Liquibase или аналог, запускаемые из pipeline или при старте приложения.
* Обеспечить **environment parity**:

    * одинаковые версии платформы и образов на dev/stage/prod;
    * отличия только в конфигурации (URL, credentials, фичефлаги).

#### 8.2.4.2. Масштабируемые выкаты и откат

* Для `backend-api` и `execution-service`:

    * использовать `Deployment` в Kubernetes со стратегией `RollingUpdate`;
    * при необходимости использовать отдельные Deployment/Service для canary-деплоя.
* Настроить **rollback**:

    * хранить версии Docker-образов;
    * использовать стандартные механизмы отката (`helm rollback`, `kubectl rollout undo`);
    * для миграций БД там, где возможно, предусмотреть `down`-миграции.
* Определить и зафиксировать:

    * условия остановки rollout (рост ошибок, деградация latency);
    * условия немедленного отката.

#### 8.2.4.3. Управление взаимодействием сервисов

* Документировать контракты:

    * UI ↔ Backend (REST/JSON),
    * Backend ↔ Execution (HTTP/gRPC),
    * Backend ↔ Tasks DB (схема БД).
* Развивать контракты **обратно совместимо**:

    * добавление полей и опций без ломания старых клиентов;
    * для ломающих изменений использовать версионирование API (`/api/v2/...`).
* Ввести интеграционные тесты:

    * “старый UI → новый Backend”,
    * “старый Backend → новый Execution”,
      чтобы контролировать совместимость при rolling update.

#### 8.2.4.4. Фича-флаги и управление функциональностью

* Реализовать механизм **feature toggle**:

    * хранение флагов в конфигурации или БД;
    * чтение флагов в Backend и, при необходимости, в UI.
* Для рискованных фич:

    * добавить отдельные **kill switch** флаги, полностью отключающие фичу;
    * описать условия, при которых эти флаги должны быть выключены (симптомы, метрики).
* Для постепенного запуска:

    * поддержка понятия “аудитория” (internal/beta/all);
    * включение фич сначала для ограниченной группы, затем расширение на всех.

### 8.2.5. План внедрения (Roadmap по развёртываемости)

**Ближайший этап (сразу после MVP):**

1. Оформить `backend-api` и `execution-service` как Kubernetes Deployment’ы со стратегией RollingUpdate.
2. Вынести деплой сервисов и миграции БД в CI/CD-пайплайн (скриптуемый деплой).
3. Настроить базовый rollback для сервисов (Helm/kubectl rollback).
4. Зафиксировать и документировать контракты UI ↔ Backend ↔ Execution, ввести правило обратной совместимости.
5. Реализовать базовый механизм фичефлагов и kill switch для наиболее рискованных фич.

**Дальнейшее развитие:**

1. Внедрить canary-деплой для Execution и других критичных сервисов.
2. Сформировать полную стратегию миграций БД с возможностью отката там, где это допустимо.
3. Расширить набор автоматизированных проверок (интеграционные и smoke-тесты после релиза).
4. Использовать фичефлаги как стандартный инструмент запуска крупных изменений (новые типы задач, сложные отчёты, интеграции).
