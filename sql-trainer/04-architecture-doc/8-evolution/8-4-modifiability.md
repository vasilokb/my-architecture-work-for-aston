## 8.4. Modifiability View (план развития)

### 8.4.1. Опросник по модифицируемости (состояние MVP и необходимость улучшений)

Оценка того, насколько текущая архитектура (UI + Nginx + Users/Auth + Courses/Tasks + Execution + Progress/Reporting + App DB + Training DB + Keycloak/AD) поддерживает дешёвые и безопасные изменения. Вопросы сгруппированы по тактическим группам из главы про модифицируемость.

#### 8.4.1.1. Повышение связности модулей (Increase Cohesion)

| Аспект                                                               | Состояние MVP                                                                                                                                                                                                                                                                                                                             | Необходимые улучшения (с учётом планов Integrability)                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Разделены ли сервисы по предметным областям, без “комбайнов”?        | На уровне контейнеров предметные области уже разделены: `Users/Auth Service` – пользователи и роли; `Courses/Tasks Service` – курсы и задачи; `Execution Service` – выполнение SQL над `Training DB`; `Progress/Reporting Service` – история попыток и прогресс. Единого “толстого” backend-а нет, это хороший базовый уровень связности. | Зафиксировать это разделение как архитектурный принцип и не пытаться “пристроить всё подряд” в существующие сервисы. Новые возможности (например, интеграция с ИИ, LMS) размещать либо внутри соответствующего доменного сервиса (через фасад/клиент), либо в отдельном интеграционном сервисе, как заложено в 8.3 (Integrability View).           |

Логику интеграций (SSO, ИИ, LMS, BI), как описано в 8.3, выносить в отдельные фасады и клиенты в “интеграционном” слое, а не мешать с доменной логикой. |

| Аспект                                                                 | Состояние MVP                                                                                                                                                                                                                                                                                                                                                                                              | Необходимые улучшения (с учётом планов Integrability)                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Спрятаны ли изменчивые детали за явными интерфейсами сервисов?         | Уже сейчас `Execution Service` скрывает работу с `Training DB` – другие сервисы видят только API проверки. `Users/Auth Service` скрывает структуру данных пользователей/ролей в `App DB`. `Progress/Reporting` скрывает детали расчёта прогресса и отчётности. Интеграция с Keycloak реализована на уровне `SPA ↔ Keycloak`, backend в целом опирается на проверенный токен, но явного фасада для IdP нет. | Реализовать и использовать фасады, описанные в 8.3: `AuthFacade / AuthService` (работа с IdP/Keycloak), `IAIGenerationService`/`ExternalAIGenerationClient` (интеграция с ИИ), `LmsClient`/`LmsIntegration` (интеграция с LMS), фасад для выгрузки в BI/DWH. Остальные компоненты (Courses/Tasks, Progress, UI) должны зависеть только от этих фасадов, не зная URL, ключей и протоколов внешних систем.              |

Взаимодействия с потенциальными внешними системами (ИИ, LMS, BI) пока не реализованы.                                                            | Соблюдать подход, описанный в 8.3: все внешние интеграции только через интеграционный слой (фасады/клиенты) внутри backend-сервисов или отдельные интеграционные микросервисы. Для связи `Execution → Progress` на уровне MVP оставить HTTP, но предусмотреть возможность вынести взаимодействие на событийную шину, если отчётность и интеграции (LMS/BI) начнут требовать подписки на события “результат проверки”. |

Отдельного интеграционного слоя и общих корпоративных интеграционных сервисов (corp-auth, corp-ai-platform, corp-lms-integration) пока нет.                                                                                                                     | Продолжить линию 8.3: внедрить общий интеграционный слой (пакет/модуль `integration` внутри backend-сервисов или отдельный сервис), оформляющий взаимодействие с SSO, ИИ, LMS, HR, BI. При дальнейшем росте – рассматривать вынос таких интеграций в корпоративные сервисы (например, `corp-ai-platform`), чтобы SQL-тренажёр был клиентом этих общих сервисов, а не главным владельцем интеграций.                   |

### 8.4.2. Цели и область покрытия

**Цели Modifiability View:**

1. Обеспечить, чтобы типичные изменения (новые типы задач, изменение правил прогресса, подключение/замена внешних систем – ИИ, LMS, BI) были прогнозируемыми по объёму и затрагивали ограниченный набор сервисов.
2. Связать развитие модульной структуры (Users/Auth, Courses/Tasks, Execution, Progress/Reporting) с планами по интеграциям (8.3), чтобы интегрируемость не “ломала” модифицируемость.
3. Перевести большую часть параметров обучения и интеграций в конфигурацию и данные: часть изменений должна решаться настройкой фасадов/таблиц/фичефлагов, а не постоянными правками кода.
4. Сохранить понятные границы между сервисами и слоями, чтобы каждый новый интеграционный сценарий (из 8.3) не превращался в неуправляемый рост связей.

**В область представления входят:**

* `SQL Trainer UI` (SPA) и его взаимодействие с Nginx и Keycloak.
* `Nginx / API Gateway` как точка входа и маршрутизации.
* `Users/Auth Service`, `Courses/Tasks Service`, `Execution Service`, `Progress/Reporting Service`.
* `App DB` и `Training DB` как отдельные хранилища.
* Фасады и интеграционный слой, описанные в 8.3: `AuthFacade`, `IAIGenerationService`, `LmsIntegration`, клиенты для BI/HR и др.

---

### 8.4.3. Ключевые сценарии изменений

#### M1. Добавление нового типа учебной задачи

* **Ситуация.**
  Методист/владелец продукта хочет новый тип задачи (например, задача на объяснение ошибки, задача с генерацией условия/объяснения через ИИ, комбинированная задача с несколькими шагами).

* **Ожидаемое поведение архитектуры.**

    * В `App DB` (зона `Courses/Tasks Service`) создаётся запись в справочнике типов задач с метаданными: как отображать, какие поля нужны, какие ограничения, какой обработчик проверки использовать.
    * В `Execution Service` (либо в доменном слое `Courses/Tasks`, если часть проверки остаётся там) появляется новая реализация логики проверки под этот тип, по общему контракту.
    * UI считывает метаданные типов задач и адаптирует форму/отображение без переписывания всего фронтенда.
    * Если тип задачи использует ИИ, это делается через `IAIGenerationService` (из 8.3), а не прямыми вызовами AI API.

* **Целевая характеристика.**
  Изменения ограничиваются `Courses/Tasks`, `Execution`, UI и, при необходимости, интеграционным слоем ИИ. `Users/Auth`, `Progress/Reporting`, Nginx и схемы интеграции SSO/LMS/BI в общем случае не затрагиваются.

---

#### M2. Изменение правил подсчёта прогресса и отчётности

* **Ситуация.**
  Бизнес/HR меняет политику прогресса (веса задач по сложности, учёт подсказок, критерии “курс пройден / не пройден”, дополнительные показатели для выгрузки в BI/LMS).

* **Ожидаемое поведение архитектуры.**

    * Все алгоритмы прогресса сосредоточены в `Progress/Reporting Service`; другие сервисы не считают прогресс самостоятельно.
    * В `App DB` существуют таблицы/конфиги с параметрами прогресса (веса, пороги, параметры для отчётности). Изменение правил чаще всего сводится к обновлению этих данных.
    * Экспорт в LMS и BI (описанный в 8.3) использует стабильный контракт `Progress/Reporting`, так что внутренние изменения в расчётах минимально затрагивают интеграции.

* **Целевая характеристика.**
  Большинство изменений реализуется настройкой параметров и локальной логикой в `Progress/Reporting`, без изменений в `Execution`, `Courses/Tasks`, `Users/Auth` и без перелопачивания схем интеграций (SSO, ИИ, LMS, BI).

---

#### M3. Подключение и замена AI-провайдера для генерации задач/решений

* **Ситуация.**
  Планируется подключение внешнего AI-сервиса для генерации условий задач, эталонных решений и объяснений на основе учебных БД (см. 8.3, сценарий I2). В будущем возможно переключение на другого провайдера или добавление ещё одного.

* **Ожидаемое поведение архитектуры.**

    * В `Courses/Tasks Service` реализуется `IAIGenerationService` с первой реализацией `ExternalAIGenerationClient`. Методисты вызывают генерацию только через этот интерфейс.
    * Информация о провайдере ИИ (URL, ключи, модель, режим работы – выключен/пилот/боевой) задаётся конфигурацией, а не зашивается в код.
    * При смене провайдера меняется реализация фасада и конфиги; доменная логика создания задач и UI меняются минимально (либо вообще не меняются).

* **Целевая характеристика.**
  Подключение/замена AI-провайдера не трогает `Execution` (проверка SQL), `Progress/Reporting` (прогресс и отчётность), `Users/Auth`, Nginx и схему SSO. Влияние на тесты и сценарии работы обучающихся минимально: ИИ – вспомогательный инструмент для методистов.

---

### 8.4.4. Архитектурные решения и тактики (с учётом Integrability View)

#### 8.4.4.1. Повышение связности

* Закрепить доменные границы существующих сервисов:

    * `Users/Auth` – всё, что касается пользователей и ролей (включая фасад `AuthFacade` к Keycloak/IdP).
    * `Courses/Tasks` – авторинг и хранение курсов/модулей/задач, плюс логика работы с ИИ (через `IAIGenerationService`) и, при необходимости, LMS (через `LmsIntegration`).
    * `Execution` – выполнение SQL над `Training DB` и логика проверки решений.
    * `Progress/Reporting` – прогресс, история попыток, отчётность и интеграции с BI/DWH.
* Внутри каждого сервиса:

    * использовать стандартный набор слоёв: контроллеры → доменные сервисы → репозитории/фасады;
    * не смешивать в одном классе бизнес-правила, JDBC, HTTP-клиентов и подготовку DTO/ответов.

#### 8.4.4.2. Уменьшение зацепления

* Следовать принципам из 8.3 по фасадам и интеграциям:

    * `AuthFacade` – единая точка доступа к IdP/Keycloak/AD для всех backend-сервисов;
    * `IAIGenerationService` – фасад для ИИ в `Courses/Tasks`;
    * `LmsIntegration`/`LmsClient` – фасад для LMS;
    * отдельные клиенты/адаптеры для BI/DWH.
* Не допускать прямых зависимостей от SDK/HTTP-клиентов внешних систем в доменной логике: всё – только через фасады/интеграционный слой.
* Сохранить роль `Nginx` как единственной точки входа для UI и контролировать, чтобы новые фронтенды (например, админский UI) также работали через него.
* Для `Execution → Progress` определить стабильный контракт (структура данных “результат проверки”) и иметь возможность в будущем заменить синхронный HTTP на шину событий без массового переписывания логики.

#### 8.4.4.3. Отложенное связывание

* В `Courses/Tasks`:

    * хранить в `App DB` метаданные типов задач и их атрибуты – UI и `Execution` будут опираться на них;
    * реализовать привязку “тип задачи → обработчик проверки” через конфиг/таблицу, чтобы добавление нового типа чаще означало добавление новой реализации, а не переписывание старого кода.
* В `Progress/Reporting`:

    * вынести веса, пороги и другие параметры прогресса в конфиг/таблицы;
    * предусмотреть разные наборы параметров для разных курсов/программ обучения.
* В интеграционном слое:

    * параметры интеграций (IdP, ИИ, LMS, BI) держать в конфиге (endpoints, ключи, строки подключения, режимы), как описано в 8.3;
    * обеспечить возможность оперативно отключить/изменить режим работы интеграции (например, выключить ИИ или остановить синхронизацию с LMS) без перекомпиляции.

### 8.4.5. План внедрения (Roadmap по модифицируемости)

**Ближайшие шаги (совместно с Integrability View 8.3):**

1. Зафиксировать и донести до команды границы ответственности сервисов (`Users/Auth`, `Courses/Tasks`, `Execution`, `Progress/Reporting`) и общую архитектурную схему взаимодействий (UI → Nginx → backend-сервисы → DB/внешние системы).
2. Реализовать базовые фасады из 8.3:

    * `AuthFacade` в зоне `Users/Auth`,
    * `IAIGenerationService` (скелет) в зоне `Courses/Tasks`,
    * начать выделение интеграционного слоя/пакета (`integration`) для внешних вызовов.
3. Начать выносить в `App DB`/конфиги:

    * метаданные типов задач (в `Courses/Tasks`),
    * базовые параметры прогресса (в `Progress/Reporting`),
    * ключевые параметры интеграций (в конфиг-файлы/секреты Kubernetes).

**Среднесрочные шаги:**

1. Довести до рабочего состояния сценарий I2 (ИИ) из 8.3:

    * использовать `IAIGenerationService` только через фасад,
    * чётко разделить “ИИ для методистов” и основной поток решения задач студентами.
2. Начать подготовку к сценарию I3 (LMS) из 8.3:

    * ввести `LmsIntegration`/`LmsClient`,
    * согласовать формат данных и стратегию синхронизации.
3. Расширить конфигурируемость:

    * поддержка разных схем прогресса для разных программ/курсов,
    * фичефлаги на уровне сервисов (поддержка ИИ, интеграция с LMS, расширенная отчётность).
4. По мере роста — оформить архитектурные проверки (архитектурные тесты/линтер), чтобы контролировать зависимости между сервисами и слоями.

Так Modifiability View (8.4) опирается на уже намеченное развитие Integrability View (8.3) и контейнерную архитектуру, и вместе с ним задаёт понятный путь, как развивать тренажёр так, чтобы изменения в функционале и интеграциях оставались управляемыми.
