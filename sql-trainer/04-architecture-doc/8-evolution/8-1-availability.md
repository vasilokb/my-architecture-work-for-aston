## 8.1. Availability View (план развития, не реализовано в MVP)

### 8.1.1. Опросник по доступности (состояние MVP и необходимость улучшений)

Оценка текущего состояния **MVP** по ключевым тактикам доступности.
Во всех комментариях указано, **что требуется улучшить** для достижения целевого решения.

#### 8.1.1.1. Detect Faults — обнаружение сбоев

| Тактика / вопрос                                         | Состояние в MVP        | Комментарий и необходимость улучшения                                                                                                                                                                                          |
| -------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Health-check (Ping/echo) для `backend-api` и `execution` | **Нет**                | Сбои сервисов выявляются фактически по логам или ручной проверкой. **Нужно**: ввести HTTP health-check (`/health`, `/ready`) и подключить их к k8s/балансировщику, чтобы нездоровые инстансы автоматически выводились из пула. |
| Централизованный мониторинг (system monitor)             | **Частично / вручную** | Есть базовый логинг, но нет системного мониторинга по ключевым цепочкам (проверка решения, чтение задач). **Нужно**: настроить Prometheus/аналог, дашборды и алерты по ошибкам и таймаутам Backend/Execution/Tasks DB/SSO.     |
| Exception detection (таймауты, обработка исключений)     | **Частично**           | Исключения ловятся не всегда, таймауты внешних вызовов не унифицированы. **Нужно**: задать единую политику timeout + обработка ошибок для вызовов Execution/Tasks DB/SSO.                                                      |
| Self-test / sanity-check Execution                       | **Нет**                | Execution не проверяет сам себя (нет тестовой задачи, нет самодиагностики). **Нужно**: добавить простой self-test (выполнение тестовой задачи) и отражать результат в `/health`.                                               |

#### 8.1.1.2. Recover from Faults — восстановление после сбоев

| Тактика / вопрос                                               | Состояние в MVP               | Комментарий и необходимость улучшения                                                                                                                                                                                         |
| -------------------------------------------------------------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Redundant spares (несколько инстансов `backend` / `execution`) | **Нет (1 инстанс)**           | Падение единственного инстанса полностью останавливает функцию. **Нужно**: развернуть по нескольку pod’ов `backend` и `execution` за k8s Service/балансировщиком.                                                             |
| Retry при временных сбоях Execution/БД                         | **Нет**                       | При ошибке/таймауте запрос сразу падает, пользователь вынужден “нажимать ещё раз”. **Нужно**: внедрить ограниченный `retry` с backoff на уровне Backend.                                                                      |
| Graceful degradation (грациозная деградация UI)                | **Нет**                       | При падении Execution или Tasks DB пользователь видит общую ошибку/500. **Нужно**: реализовать честные сообщения и временную блокировку “проблемных” действий (например, “Проверить”), при сохранении остального функционала. |
| Reconfiguration (авто-вывод нездоровых инстансов)              | **Нет (в логике приложения)** | Переключение/отключение инстансов делается вручную. **Нужно**: использовать k8s liveness/readiness probes, чтобы нездоровые pod’ы автоматически выводились из пула и перезапускались.                                         |
| Rollback (откат релиза/состояния)                              | **Частично**                  | Транзакции БД есть, но откат релизов и миграций в основном ручной. **Нужно**: настроить процедуры rollback deployment’ов и миграций (helm/k8s + миграции “вперёд/назад”).                                                     |

#### 8.1.1.3. Prevent Faults — предотвращение сбоев

| Тактика / вопрос                                            | Состояние в MVP   | Комментарий и необходимость улучшения                                                                                                                                                                  |
| ----------------------------------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Транзакции при изменении решений/прогресса                  | **Да (частично)** | Используются транзакции, но не гарантировано, что все критичные изменения всегда атомарны. **Нужно**: убедиться, что операции “сохранить решение + обновить прогресс” оформлены как единая транзакция. |
| Removal from service (контролируемый вывод из эксплуатации) | **Вручную**       | Обслуживание/обновление сервисов оформлено как ручная операция. **Нужно**: формализовать процедуры вывода pod’ов/нод из-под трафика (cordon/drain, масштабирование до 0) при обновлениях.              |
| Exception prevention (валидация, ограничения на SQL)        | **Частично**      | Базовая валидация входа есть, но тяжёлые/опасные SQL могут доходить до Execution. **Нужно**: добавить фильтрацию опасных запросов, лимиты на время выполнения и размеры результатов.                   |

### 8.1.2. Цели и область покрытия

**Цель:**
Обеспечить приемлемую доступность ключевых пользовательских сценариев SQL-тренажёра за счёт архитектурных решений в Runtime / Deployment слоях.

**Ключевые сценарии, попадающие в область:**

1. **Проверка решения:**
   UI → Backend API → Execution Service → Sandbox DB.
2. **Чтение курсов и задач:**
   UI → Backend API → Tasks DB.
3. **Работа уже залогиненных пользователей при проблемах с SSO:**
   UI → Backend API (локальная сессия / токен) при временной недоступности SSO.

**Статус:**

* В **MVP** поддерживаются только базовые механизмы (1–2 инстанса сервисов без формализованных SLO и чётких тактик по доступности).
* Данный раздел фиксирует **план доработок по доступности** как часть следующего релиза и целевое архитектурное состояние.

---

### 8.1.3. Целевые показатели доступности (черновые SLO)

Для планирования:

* **SLO-1. “Проверка решения”**
  Доступность функции “Проверить решение” (UI показывает результат или контролируемое сообщение об ошибке) — **≥ 99.5%** в месяц.

* **SLO-2. “Чтение задач и курсов”**
  Доступность чтения списка курсов/задач — **≥ 99.7%** в месяц.

* **SLO-3. “Работа уже залогиненных пользователей при падении SSO”**
  При недоступности SSO уже залогиненные пользователи сохраняют возможность работать с задачами и проверкой не менее **X часов** (конкретизировать с бизнесом).

Эти SLO опираются на сценарии и тактики, описанные ниже.

### 8.1.4. Цепочка 1: Проверка решения (UI → Backend → Execution → Sandbox DB)

**Сценарий:**
Студент нажимает “Проверить решение” в вечерний пик, один из инстансов Execution падает / зависает.

**Требуемое поведение (кратко):**

1. Система **детектит fault** (падение инстанса Execution).
2. Система **переключает нагрузку** на живые инстансы Execution.
3. Пользователь либо получает результат проверки, либо контролируемое сообщение (“проверка временно недоступна”), а не 500/белый экран.

#### Архитектурные решения и задачи по сервисам

**UI (Frontend):**

* Обработать “контролируемую ошибку проверки” от Backend:

    * показать пользовательское сообщение:

      > “Проверка временно недоступна. Попробуйте ещё раз через несколько минут.”
    * временно заблокировать кнопку “Проверить” (debounce/таймер).
* Не падать при ошибках API, а работать в режиме graceful degradation.

**Backend API:**

* Добавить HTTP-клиент к Execution с:

    * явными таймаутами (например, 3 сек);
    * политикой retry (1–2 повтора, с backoff) до объявления ошибки.
* Реализовать обработку исключений при обращении к Execution:

    * логировать fault с контекстом (userId, taskId, инстанс);
    * возвращать в UI контролируемый ответ, а не необработанную 500.
* Разделить уровни:

    * доменная логика проверки;
    * инфраструктурная логика (retry/timeout/circuit-breaker).

**Execution Service:**

* Настроить несколько инстансов Execution (min 2–3 pod’а) в k8s.
* Добавить health endpoint (`/health`, `/ready`), отражающий:

    * готовность принимать запросы;
    * статус подключения к Sandbox DB.
* Локальная обработка “тяжёлых” запросов:

    * ограничение времени выполнения;
    * прерывание слишком долгих операций (защита от самоуничтожения сервиса).

**Sandbox DB (DB для выполнения SQL):**

* Обеспечить отдельный контур (sandbox), не влияющий на боевые системы.
* При необходимости — реплика/standby для уменьшения времени простоя.

**Инфраструктура / k8s / Мониторинг:**

* Настроить liveness/readiness probes для Execution:

    * k8s должен автоматически **выводить из пула** нездоровые pod’ы и перезапускать их.
* Балансировка запросов Backend → Execution через k8s Service / Ingress.
* Настроить мониторинг:

    * метрики ошибок и latency вызовов Execution;
    * алерты при росте ошибок/таймаутов.

### 8.1.5. Цепочка 2: Чтение задач (UI → Backend → Tasks DB)

**Сценарий:**
Во время рабочего дня падает primary-инстанс базы задач (Tasks DB).

**Требуемое поведение (кратко):**

1. Система обнаруживает недоступность primary Tasks DB.
2. Переключает чтение/запись на standby/реплику (если предусмотрено).
3. Пользователь либо продолжает видеть список задач, либо получает понятное сообщение о временной недоступности, а не “падает всё”.

#### Архитектурные решения и задачи

**UI (Frontend):**

* Обработать контролируемую ошибку “невозможно загрузить список задач”:

    * показать понятное сообщение;
    * оставить возможность работать с уже открытыми задачами (если данные есть в state/кэше).

**Backend API:**

* Использовать **единый слой доступа к Tasks DB** (репозиторий/DAO), чтобы переключение primary/replica было прозрачно для бизнес-логики.
* Настроить **таймауты** и **обработку исключений** при запросах к Tasks DB:

    * логировать ошибки подключения;
    * возвращать в UI контролируемые ответы.

**Tasks DB:**

* Рассмотреть конфигурацию с **primary + standby / репликой** (Postgres cluster, managed DB и т.п.).
* Настроить процесс **failover** (автоматический или полуавтоматический) с целевым временем переключения (например, ≤ 30 сек).

**Инфраструктура / Мониторинг:**

* Настроить мониторинг доступности БД:

    * health-check’и на уровне DB;
    * алерты по ошибкам подключения.
* Если используется кластер:

    * проверка роли (primary/replica);
    * мониторинг lag’а репликации.

### 8.1.6. Цепочка 3: Работа уже залогиненных пользователей при проблемах с SSO

**Сценарий:**
Корпоративный SSO (IdP) временно недоступен. Пользователь уже залогинен в тренажёр и решает задачи.

**Требуемое поведение:**

1. Уже залогиненные пользователи **продолжают работать** с задачами и проверкой решений.
2. Новые логины могут быть временно недоступны, но UI даёт понятное сообщение.

#### Архитектурные решения и задачи

**UI (Frontend):**

* Корректно работать с локальной сессией/токеном, не дёргать SSO напрямую.
* При ошибке логина показывать понятное сообщение:

  > “Аутентификация временно недоступна. Попробуйте позже или обратитесь в поддержку.”

**Backend / AuthFacade:**

* Ввести **слой AuthFacade**:

    * Backend не зависит напрямую от конкретного IdP, все обращения – через фасад.
* Использовать **локальные серверные сессии или access/refresh tokens**:

    * при недоступности SSO не инвалидировать уже существующие сессии;
    * минимизировать количество обращений к IdP в нормальном режиме.
* Настроить **таймауты и обработку ошибок** при вызове SSO:

    * переводить их в контролируемые ответы для UI, а не падать.

**Инфраструктура / Мониторинг:**

* Мониторинг доступности SSO:

    * периодический health-check endpoint’ов IdP;
    * мониторинг доли ошибок логина.
* Алерты: “логины в тренажёр недоступны из-за SSO”.

### 8.1.7. План внедрения (Roadmap)

**Пост-MVP, следующий релиз:**

* Внедрение таймаутов, retry и обработок исключений в цепочке Backend → Execution → Sandbox DB.
* Добавление health endpoints и probes для Execution и Backend.
* Настройка мониторинга и алертов по Execution и Tasks DB.
* Реализация контролируемых ошибок и graceful degradation в UI (проверка, чтение задач).
* Введение слоя AuthFacade и базовых стратегий работы при недоступности SSO.

**Дальнейшее развитие:**

* Кластеризация / standby для Tasks DB.
* Уточнение SLO по доступности вместе с бизнесом.
* Доработка сценариев availability для отчётности, фоновых задач и интеграций (если появятся).
