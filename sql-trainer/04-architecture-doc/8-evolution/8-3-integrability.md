### 8.3.2. Цели и область покрытия

**Цель Integrability View:**

Обеспечить, чтобы SQL-тренажёр:

1. Легко подключался к внешним корпоративным сервисам (SSO/IdP, LMS, HR, BI, ИИ).
2. Позволял менять или добавлять интеграции с минимальными изменениями основной логики.
3. Не становился “жёстко привязанным” к конкретным платформам/поставщикам.
4. Контролировал риски: безопасность данных, отказоустойчивость и влияние интеграций на UX.

**В область представления входят:**

* Сервисы тренажёра:

    * UI (frontend),
    * Backend API,
    * Execution Service,
    * модули авторинга задач и курсов.
* Интеграционный слой:

    * AuthFacade / AuthService (SSO),
    * AI Generation Facade (`IAIGenerationService`),
    * LmsIntegration / другие внешние клиенты.
* Внешние системы:

    * корпоративный IdP (SSO/Keycloak/AD),
    * AI-провайдер(ы),
    * LMS/портал обучения,
    * HR-система и BI/DWH (в перспективе).

### 8.3.3. Целевые сценарии интеграции

#### I1. Интеграция с корпоративным SSO/IdP

* Источник (Source): архитектор/безопасники/администраторы доступа.
* Стимул (Stimulus): требуется интегрировать тренажёр с корпоративным IdP (SSO), чтобы все пользователи входили под корпоративной учёткой, с учётом ролей.
* Окружение (Environment): dev → test/stage → production; работающая система, пользователи активно заходят в тренажёр.
* Артефакты (Artifacts): Backend API, UI, `AuthFacade`, конфигурация IdP.
* Ответ (Response):

    * реализуется `AuthFacade`, скрывающий детали IdP;
    * UI использует стандартный redirect/flow SSO, Backend — проверку токенов через фасад;
    * при смене IdP достаточно поменять конфигурацию и реализацию фасада.
* Метрики (Response measure):

    * время внедрения интеграции с новым IdP измеряется неделями, а не месяцами;
    * смена IdP затрагивает ограниченный набор модулей (в основном AuthFacade);
    * не более допустимого числа инцидентов по аутентификации при переходе.

#### I2. Интеграция с AI-сервисом генерации задач и решений

* Источник (Source): владелец продукта, методисты.
* Стимул (Stimulus): требуется подключить внешний AI-сервис, генерирующий задачи и эталонные решения по SQL на основе учебных БД.
* Окружение (Environment): сначала dev/stage (для методистов и внутреннего тестирования), затем prod; основная функциональность тренажёра уже используется.
* Артефакты (Artifacts): модуль авторинга задач, `IAIGenerationService`, фасад `ExternalAIGenerationClient`, UI для методистов, внешний API AI-провайдера.
* Ответ (Response):

    * в Backend вводится интерфейс `IAIGenerationService` и его реализация, инкапсулирующая взаимодействие с AI-провайдером;
    * UI методистов получает кнопки “Сгенерировать задачу/решение/объяснение”;
    * при недоступности ИИ методист получает контролируемое сообщение и может создать задачу вручную.
* Метрики (Response measure):

    * время первой интеграции ИИ (до рабочей версии для методистов) — в пределах согласованного срока (например, не более 2–3 спринтов);
    * при смене AI-провайдера изменения локализованы в модуле интеграции, основной Backend/UI почти не трогаются;
    * сбои ИИ не приводят к падению тренажёра и не влияют на студентов.

#### I3. Интеграция с LMS/порталом обучения (перспективный сценарий)

* Источник (Source): бизнес/корпоративный отдел обучения.
* Стимул (Stimulus): требуется интегрировать тренажёр с LMS, чтобы:

    * загружать пользователей/группы;
    * синхронизировать прогресс по курсам;
    * передавать результаты в LMS.
* Окружение (Environment): dev/stage для отладки, затем prod; ограничения по окнам интеграции и SLA LMS.
* Артефакты (Artifacts): Backend API, модуль `LmsIntegration`, внешнее API LMS.
* Ответ (Response):

    * проектируется контракт обмена данными с LMS (курсы, пользователи, результаты);
    * реализуется `LmsIntegration`/`LmsClient`, выполняющий обмен через API/очередь/файлы;
    * основная модель прогресса тренажёра не зависит от конкретного LMS.
* Метрики (Response measure):

    * время добавления первой интеграции с LMS в рамках планового релиза;
    * добавление ещё одного LMS (или смена существующего) требует ограниченных изменений в интеграционном слое, а не переписывания домена;
    * стабильность обмена: допустимый процент ошибок синхронизации и задержка обновления данных.

### 8.3.4. Архитектурные решения и тактики

#### 8.3.4.1. Инкапсуляция внешних сервисов (Encapsulation)

* Для SSO/IdP:

    * реализовать `AuthFacade`, предоставляющий доменный интерфейс: получение текущего пользователя, ролей, проверка прав;
    * вся логика протокола (OpenID Connect/SAML и т.п.) и формат токенов скрыта внутри фасада.
* Для ИИ:

    * реализовать `IAIGenerationService` и его реализацию `ExternalAIGenerationClient`;
    * фасад отвечает за формирование промптов, вызовы API, парсинг ответов, обработку ошибок, логирование.
* Для LMS/HR/BI:

    * для каждой системы – свой фасад/клиент, скрывающий детали протокола и форматов данных.

#### 8.3.4.2. Ограничение зависимостей (Restricting dependencies)

* UI и доменные сервисы зависят только от интерфейсов фасадов, а не от конкретных SDK/HTTP-клиентов.
* Execution Service и хранилища не имеют прямых зависимостей от внешних интеграций.
* Вводятся простые правила:

    * “любой внешний вызов — только через фасад/интеграционный слой”;
    * “никаких прямых зависимостей от IdP/AI/LMS в доменном коде”.

#### 8.3.4.3. Использование посредника (Using an intermediary)

* В Backend выделяется интеграционный слой (пакет `integration`):

    * единая точка для конфигурации URL, ключей, таймаутов;
    * добавление ретраев, логирования и метрик.
* При росте числа продуктов возможно выделение общих интеграций в отдельные микросервисы (например, общий AI-gateway или общий LMS-интегратор).

#### 8.3.4.4. Абстракция общих сервисов (Abstracting common services)

* Прописать интерфейсы для:

    * `corp-auth` (единая аутентификация),
    * `corp-ai-platform` (общий сервис ИИ),
    * `corp-lms-integration` (единый слой интеграции с LMS).
* SQL-тренажёр рассматривается как один из клиентов этих сервисов, а не как владелец интеграций.

#### 8.3.4.5. Контракты, версии и тестирование интеграций

* Документировать контракты:

    * API фасадов,
    * структуры данных,
    * сценарии обмена (SSO, ИИ, LMS).
* Ввести версионирование интеграций там, где изменения ломают обратную совместимость.
* Добавить набор автотестов:

    * контракты интеграций,
    * моковый режим для ИИ,
    * тесты для основных бизнес-сценариев с включёнными/отключёнными интеграциями.

### 8.3.5. План внедрения (Roadmap по интегрируемости)

**Ближайший этап (после MVP):**

1. Ввести `AuthFacade` для интеграции с SSO, убрать прямые обращения к IdP из бизнес-логики.
2. Спроектировать и реализовать `IAIGenerationService` и его первую реализацию под выбранного AI-провайдера, использовать только в модуле авторинга задач.
3. Выделить интеграционный слой (пакет/модуль `integration`) в Backend и перенести туда текущие и новые интеграции.
4. Описать и зафиксировать базовые контракты интеграций (SSO, ИИ) и правила зависимостей.

**Дальнейшее развитие:**

1. Подготовить интерфейсы и прототип `LmsIntegration` для будущей интеграции с корпоративным LMS.
2. Рассмотреть возможность выделения общих интеграций (например, AI-интеграции) в отдельные корпоративные сервисы с собственными SLA.
3. Расширить набор автотестов и мониторинга для интеграций (контракты, метрики, алерты по ошибкам внешних сервисов).
4. Формализовать политику защиты данных при обмене с внешними системами, особенно с ИИ-сервисами.
