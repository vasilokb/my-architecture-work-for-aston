### 5.2. KD2: Авторизация через SSO и проверка JWT только на входе (MVP only)

**Context**

* Система SQL Trainer работает **только во внутреннем контуре под VPN**, с учебными данными в Training DB и без боевых клиентских данных.
* Аутентификация пользователей централизована через **Keycloak/SSO**, который интегрирован с **Active Directory**.
* API-шлюзом для приложения выступает **Nginx/ingress** в зоне приложения: через него проходят все внешние запросы к backend-сервисам.
* Команда разработки – стажёры и junior-специалисты, срок реализации MVP ограничен тремя месяцами.
* Полноценная “продовая” схема (когда **каждый** внутренний сервис сам валидирует JWT по JWKS и реализует собственные правила авторизации) увеличивает сложность реализации и риск ошибок.

В этих условиях для **учебного стенда** принято упрощённое решение по авторизации.

---

**Decision (MVP only)**

В рамках MVP принимается решение:

1. **Единая точка проверки токена – API-шлюз (Nginx/ingress)**

    * Все внешние HTTP(S)-запросы к backend-сервисам проходят через Nginx.
    * Nginx извлекает `access_token` (из cookie или заголовка, согласно выбранному сценарию) и **проверяет валидность JWT** через интроспекцию/конфигурацию Keycloak:

        * токен активен;
        * не истёк срок действия;
        * issuer, audience и другие параметры соответствуют ожиданиям.
    * При неуспешной проверке запрос отклоняется на уровне периметра, во внутренний контур (Execution, Tasks, Progress) он не попадает.

2. **Внутренние сервисы доверяют claims, не проверяя подпись JWT**

    * Backend-сервисы SQL Trainer **не выполняют криптографическую валидацию JWT** и не ходят напрямую в Keycloak для проверки токенов.
    * Сервисы получают от API-шлюза уже проверенную информацию об идентификаторе пользователя и его ролях (через заголовки или проксирование claims).
    * Авторизация на уровне бизнес-логики выполняется на основе переданных идентификаторов и ролей (например, “обучающийся”, “методист”, “администратор”).

3. **Явная пометка “MVP only” в документации**

    * Данная модель авторизации фиксируется как **упрощённое решение для учебного стенда** и не рассматривается как целевая для боевых критичных систем.
    * В разделе Security View и в настоящем разделе явно указано, что для “продового” варианта требуется переход к схеме, где **каждый сервис валидирует JWT самостоятельно**.

---

**Consequences**

Положительные последствия:

* Существенное **упрощение реализации** backend-сервисов: им не нужно интегрироваться с Keycloak, поднимать клиентские библиотеки OAuth2/OIDC и реализовывать собственную проверку подписи и параметров токена.
* **Снижение рисков ошибок** при работе с JWT на уровне нескольких микросервисов (особенно для команды из стажёров и junior-разработчиков).
* Централизация основной логики проверки токена на уровне API-шлюза:

    * удобнее логировать невалидные запросы;
    * проще конфигурировать политику доступа на периметре.
* Решение достаточно безопасно для учебного стенда:

    * стенд доступен только через VPN/корпоративную сеть;
    * используется SSO Keycloak/AD;
    * в Training DB нет боевых клиентских данных.

Негативные и ограничивающие последствия:

* Внутренние сервисы **доверяют** тому, что им передал API-шлюз, и не могут самостоятельно отфильтровать запросы с поддельным или повторно использованным токеном, если кто-то получит возможность обойти периметр.
* Модель **не подходит** для боевых, критичных для бизнеса систем, где:

    * возможны вызовы сервисов в обход API-шлюза (изнутри кластера, через port-forward, от других сервисов);
    * требуется строгая самостоятельная проверка JWT каждым сервисом.
* При развитии системы до “продового” статуса потребуется **миграция** на модель, где:

    * API-шлюз по-прежнему выполняет базовую проверку;
    * каждый сервис дополнительно валидирует JWT (подпись, срок, issuer, audience) и реализует более детализированные правила авторизации.

Это архитектурное решение действует только в рамках текущего учебного MVP и осознанно балансирует между безопасностью и простотой. Переход к более строгой модели описан в Security View и должен быть реализован при масштабировании SQL Trainer и интеграции его в более широкий ландшафт корпоративных сервисов.
