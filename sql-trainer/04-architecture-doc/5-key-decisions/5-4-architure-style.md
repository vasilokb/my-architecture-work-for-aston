### 5.4. KD4: Выбор стека и архитектурного стиля (React SPA + Java/Spring микросервисы на Kubernetes)

**Context**

* Проект реализуется как **учебный стенд** для стажёров и junior-разработчиков.
* В компании уже используются:

    * Java + Spring для backend;
    * React для frontend;
    * PostgreSQL как основная СУБД;
    * Kubernetes как платформа развертывания.
* По требованиям курса по архитектуре важно, чтобы студенты работали именно с **микросервисным приложением на Kubernetes**, а не с “чистым” монолитом.
* При этом:

    * сроки MVP ограничены тремя месяцами;
    * команда слабая по опыту;
    * система не несёт боевой нагрузки и работает только с учебными данными.

Нужно найти баланс между учебными целями (микросервисы, Kubernetes) и реализуемостью в рамках MVP.

---

**Decision**

1. **Технологический стек**

    * Frontend: **React SPA** (одностраничное приложение).
    * Backend: **Java + Spring** (Spring Boot) как базовый фреймворк для всех сервисов.
    * Базы данных: **PostgreSQL** для `App DB` и `Training DB`.
    * Периметр и веб-сервер: **Nginx** (раздача статики SPA, reverse proxy для backend).
    * Платформа развертывания: **Kubernetes** во внутренней инфраструктуре.

2. **Архитектурный стиль backend**

    * Backend проектируется в **микросервисном стиле** с выделением небольшого набора доменных сервисов:

        * Users/Auth;
        * Courses/Tasks;
        * Execution;
        * Progress/Reporting.
    * Для MVP допускаются упрощения:

        * общий репозиторий кода для всех сервисов;
        * единый pipeline сборки с разными артефактами;
        * общие технические библиотеки и инфраструктурный код.
    * Сервисы разворачиваются в Kubernetes как отдельные deployment/под, но используют общий стек и подходы, чтобы снизить порог входа.

3. **Развитие архитектуры**

    * Выбранный стек и стиль считаются **целевым направлением**: при развитии системы можно:

        * добавлять новые сервисы без смены технологий;
        * постепенно усиливать границы между сервисами (отдельные репозитории, более строгая изоляция БД, отдельные очереди и так далее).

---

**Consequences**

Положительные последствия:

* Стек и архитектурный стиль **совпадают с корпоративной практикой** и инфраструктурой (Java/Spring, React, PostgreSQL, Kubernetes, Nginx).
* Студенты и стажёры получают **реальный опыт работы с микросервисами на Kubernetes**, а не только с теоретическим монолитом.
* Ограниченный набор сервисов и единый технологический стек упрощают:

    * обучение;
    * ревью кода;
    * эксплуатацию стенда.
* Масштабирование и развитие системы возможны без смены стека и архитектурного подхода.

Негативные и ограничивающие последствия:

* Микросервисный стиль даже в упрощённом виде сложнее для команды из стажёров, чем монолит; возрастает риск:

    * ошибок в интеграции между сервисами;
    * накладных расходов на деплой и отладку.
* Для полноценного использования Kubernetes и микросервисов нужны базовые DevOps-практики:

    * настройка CI/CD;
    * мониторинг;
    * управление конфигурацией и секретами.
* Для маленькой по объёму функциональности микросервисная архитектура может быть избыточной с точки зрения строго утилитарного MVP, но оправдана **учебной целью проекта**.

Данное решение фиксирует, что SQL Trainer в рамках курса и учебного стенда строится на стеке React + Java/Spring + PostgreSQL и использует микросервисный стиль на Kubernetes как целевую модель, с осознанными упрощениями в первой версии.
