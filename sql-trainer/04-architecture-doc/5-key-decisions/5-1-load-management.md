## 5. Ключевые архитектурные решения (Key Decisions)

### 5.1. KD1: Управление нагрузкой на Training DB (таймаут 2 сек, пул 50, очередь)

**Context**

* Training DB используется для выполнения учебных SQL-запросов обучающихся.
* По нефункциональным требованиям время проверки типовой задачи должно быть не более 1 секунды, при этом одновременно могут работать десятки и сотни пользователей.
* Учебные запросы по определению могут быть тяжёлыми (многотабличные `SELECT`, агрегации), а команда разработчиков состоит в основном из стажёров и junior-специалистов.
* Прямая перегрузка Training DB (очень долгие запросы, неконтролируемое число соединений) может привести к деградации работы всего стенда и сделать тренажёр практически непригодным для использования.

**Decision**

Для управления нагрузкой на Training DB в Execution Service принимается следующее решение:

1. **Ограничение времени выполнения запроса**

    * Для каждого учебного SQL-запроса задаётся максимальное время выполнения в Training DB.
    * На этапе MVP устанавливается значение таймаута **2 секунды**.
    * По истечении таймаута запрос к Training DB принудительно прерывается, пользователю возвращается ошибка о превышении лимита времени.

2. **Ограниченный пул соединений к Training DB**

    * Execution Service использует пул соединений к Training DB фиксированного размера.
    * Стартовое значение размера пула для учебного стенда – **50 соединений**.
    * Пул соединений является общим для всех одновременных запросов; новые запросы не создают дополнительные соединения вне пула.

3. **Очередь запросов на выполнение**

    * Если все соединения пула заняты, новые запросы на выполнение SQL ставятся в очередь ожидания свободного соединения.
    * Максимальная длина очереди и поведение при её переполнении (отказ, сообщение пользователю, возврат ошибки) настраиваются конфигурационно.

4. **Конфигурируемость параметров**

    * Значения таймаута, размера пула соединений и параметров очереди задаются в конфигурации Execution Service.
    * Эти параметры могут корректироваться по итогам нагрузочного тестирования и эксплуатации без изменения кода приложения.

**Consequences**

Положительные последствия:

* Защита Training DB от перегрузки за счёт жёсткого ограничения числа активных соединений и времени выполнения одного запроса.
* Снижение риска ситуации, когда один или несколько тяжёлых запросов блокируют ресурсы и ухудшают работу тренажёра для всех пользователей.
* Возможность управляемой деградации: при высокой нагрузке часть запросов будет завершаться по таймауту или попадать в очередь, но система в целом останется работоспособной.
* Гибкость настройки – параметры можно адаптировать под реальные нагрузки без переработки архитектуры.

Негативные и ограничивающие последствия:

* При повышенной нагрузке и сложных учебных задачах часть запросов может завершаться по таймауту, что потребует корректной обработки ошибок в интерфейсе и объяснений для обучающихся.
* Неправильно подобранные значения (слишком маленький таймаут, слишком маленький пул или очередь) могут привести к ухудшению пользовательского опыта и росту числа неуспешных попыток.
* Требуется мониторинг метрик Training DB и Execution Service (доля запросов, завершённых по таймауту, загрузка пула соединений), а также периодическая ревизия настроек по мере роста числа пользователей и усложнения задач.

Данное решение фиксирует базовую стратегию защиты Training DB и служит опорой для дальнейших решений по масштабированию и оптимизации учебных баз данных.
