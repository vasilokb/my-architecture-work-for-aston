## 6. Риски и допущения (Risks & Assumptions)

### 6.1. Общие положения

Данный раздел фиксирует ключевые риски реализации и эксплуатации системы SQL Trainer, а также допущения, на которых основаны архитектурные решения и оценки. Для каждого риска при необходимости указывается стратегия смягчения (mitigation), реализуемая на уровне архитектуры, процессов разработки или эксплуатации.

---

### 6.2. Ключевые риски

#### R1. Нагрузка на Training DB при одновременном выполнении тяжёлых запросов

**Описание**

Существует риск, что при одновременном выполнении большого числа тяжёлых учебных SQL-запросов (сложные `SELECT` с джойнами и агрегациями) учебная база данных `Training DB` не выдержит нагрузку. Возможные последствия:

* исчерпание пула соединений к `Training DB`;
* существенный рост времени проверки задач (выход за целевое значение ≤ 1 сек);
* деградация производительности всей системы для всех пользователей.

**Связанные допущения**

* A1: типовые учебные задачи будут спроектированы так, чтобы не требовать чрезмерно тяжёлых запросов по очень большим наборам данных;
* A2: одновременное количество активных пользователей и частота запросов находятся в пределах ожидаемых значений (до 500 одновременных пользователей).

**Стратегия смягчения**

* ограничение максимального времени выполнения одного запроса к `Training DB` (2 секунды);
* ограничение размера пула соединений к `Training DB` (50 соединений) и использование очереди запросов;
* мониторинг занятости пула, времени проверки задач и числа запросов, прерванных по таймауту;
* при росте нагрузки — возможность масштабирования `Training DB` и введения read-only реплик для аналитических сценариев.

---

#### R2. Риск не уложиться в срок MVP (3 месяца) с приемлемым качеством

**Описание**

MVP SQL Trainer реализуется в сжатые сроки (3 месяца) командой из стажёров/джуниоров. Существует риск:

* не успеть реализовать согласованный объём функционала;
* либо уложиться в сроки за счёт ухудшения качества (нестабильность, технический долг, упрощённая безопасность).

**Связанные допущения**

* A3: объём MVP ограничен базовыми сценариями решения задач и простыми отчётами, без сложных интеграций и аналитики;
* A4: команда разработки и наставники доступны в объёме, достаточном для регулярных ревью и поддержки.

**Стратегия смягчения**

* концентрация на ключевых сценариях: решение задач, хранение прогресса, базовые отчёты;
* фиксация в архитектуре явных упрощений для учебного стенда (например, проверка JWT только на входе, отсутствие внешних интеграций);
* отнесение “взрослых” решений (Authorization Code + PKCE/BFF, реплики для BI, расширенная аналитика) в раздел планируемого развития архитектуры;
* регулярные архитектурные и код-ревью критичных частей (Execution, безопасность, работа с БД).

---

#### R3. Зависимость от корпоративного SSO (Keycloak/AD)

**Описание**

SQL Trainer целиком полагается на корпоративный SSO (Keycloak/AD) для аутентификации и получения ролей пользователей. При недоступности SSO или ошибках конфигурации:

* пользователи не могут войти в систему, даже если сам SQL Trainer и базы данных доступны;
* часть сценариев (назначение ролей, доступ к административным функциям) может работать некорректно.

**Связанные допущения**

* A5: работа и доступность Keycloak/AD обеспечиваются отдельной командой в соответствии с корпоративными SLA;
* A6: интеграция SQL Trainer с SSO согласована и поддерживается совместно с этой командой.

**Стратегия смягчения**

* чёткое разделение зон ответственности: SQL Trainer не хранит пароли и не управляет учётными записями, полностью опираясь на SSO;
* использование стандартных протоколов (OIDC/OAuth2) и рекомендуемых настроек для интеграции с Keycloak;
* мониторинг числа ошибок аутентификации/авторизации и технических ошибок обращения к SSO;
* при необходимости — согласование с командой SSO fallback-процедур (например, плановых окон обслуживания, когда тренажёр может быть временно недоступен).

---

#### R4. Отсутствие формального ревью безопасности со стороны ИБ

**Описание**

Архитектура SQL Trainer проектируется с учётом стандартных практик безопасности (зоны, VPN, SSO, изоляция учебных данных), однако:

* безопасность учебного стенда пока **не проходила формального ревью** и официального утверждения службой информационной безопасности;
* есть риск, что при формальном ревью ИБ потребует доработки (например, по токенам, журналированию, доступам администраторов, режимам работы БД).

**Связанные допущения**

* A7: текущая модель (только VPN, SSO, отсутствие боевых данных, отсутствие прямого доступа к БД) соответствует базовым требованиям ИБ для учебных стендов;
* A8: изменения, требуемые ИБ по итогам ревью, могут быть внедрены постепенно, без критического влияния на сроки и эксплуатацию стенда.

**Стратегия смягчения**

* явная фиксация в архитектурной документации текущей модели безопасности (Security View) и упрощений, сделанных для учебного стенда (проверка JWT только на входе и т.п.);
* фиксация целевого “взрослого” варианта (Authorization Code + PKCE/BFF, валидация JWT в сервисах, возможное использование интроспекции) как направления развития;
* подготовка исходных материалов для ревью ИБ (диаграммы зон, описание потоков данных, перечень логируемой информации);
* планирование временного бюджета на доработки безопасности после формального ревью ИБ.

---

### 6.3. Сводный список допущений (Assumptions)

Для удобства анализа и ревью ниже приведён сводный список допущений, на которых базируется архитектура MVP:

* **A1.** Типовые учебные задачи не требуют чрезмерно тяжёлых SQL-запросов по очень большим наборам данных.
* **A2.** Одновременное число активных пользователей и частота запросов находятся в пределах рассчитанных нагрузок (до 500 одновременных пользователей).
* **A3.** Объём MVP ограничен базовыми сценариями: решение задач, хранение прогресса, простые отчёты, без интеграций с внешними HR/LMS и без сложной аналитики.
* **A4.** Команда разработки (стажёры/джуниоры) получает достаточную поддержку и ревью со стороны опытных специалистов.
* **A5.** Работу и доступность Keycloak/AD обеспечивает отдельная команда в рамках корпоративных SLA.
* **A6.** Интеграция SQL Trainer с SSO согласована с ответственной командой и поддерживается совместно.
* **A7.** Модель безопасности учебного стенда (только VPN, SSO, отсутствие боевых данных, отсутствие прямого доступа к БД) укладывается в базовые требования ИБ к внутренним учебным системам.
* **A8.** Возможные доработки по результатам формального ревью ИБ могут быть выполнены без критического изменения архитектурного ядра и нарушений сроков эксплуатации стенда.
