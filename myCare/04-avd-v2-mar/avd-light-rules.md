# Правила оформления краткой версии Architecture Vision Document (Lightweight AVD)

Финальная версия 1.0

---

## Введение

### Назначение правил
Настоящий документ определяет стандарты для создания **Lightweight AVD** — компактного архитектурного документа, предназначенного для быстрой фиксации и коммуникации ключевого архитектурного решения. Основной фокус сделан на контейнерную диаграмму (C4), её структурное описание, детализацию ключевых элементов и поведенческие сценарии.

### Целевая аудитория
- **Команда разработки** (Tech Lead, разработчики, QA) — для понимания структуры сервисов, их границ, внутреннего устройства ключевых компонентов и взаимодействия.
- **Архитекторы** — для быстрой проверки и утверждения ключевых решений.
- **Руководитель продукта/проекта** — для понимания технической сложности и основных компонентов.
- **DevOps-инженеры** — для понимания схемы развертывания и зависимостей.

### Как использовать документ
1. **Как стартовый шаблон** — для быстрого согласования видения архитектуры в начале проекта.
2. **Как "шпаргалку" по системе** — постоянно актуальный справочник для команды.
3. **Как входные данные** — основа для более детальных документов (ADR, User Stories, FDD).

## 1. Общие принципы оформления Lightweight AVD

### 1.1. Философия: "80% ценности за 20% усилий"
- **Главный артефакт — контейнерная диаграмма (C2).** Текст — только пояснение к ней.
- **Фокус на "Что" и "Как работает", а не на "Почему".** Обоснования приводятся только для самых критичных решений.
- **Трехуровневое представление:**
  - **Структура (Каталог элементов)** — что есть в системе.
  - **Детализация (Ключевые элементы)** — как устроены самые важные компоненты.
  - **Поведение (Ключевые потоки)** — как они работают вместе.

### 1.2. Уровень детализации
- **Базовый уровень:** Контейнерный уровень (C2) для всех элементов.
- **Детализация (C3):** Только для элементов, которые:
  - Являются критическими для безопасности (PDP Service, Keycloak)
  - Имеют сложную внутреннюю структуру (Data Sync Service, Integration Service)
  - Содержат ключевые архитектурные решения, которые нужно зафиксировать
- Для остальных элементов достаточно описания в Каталоге.

### 1.3. Язык и стиль

#### 1.3.1. Язык документа
- **Единый язык для всего документа:** Русский или английский (определяется в начале проекта).
- Смешение языков в одном документе **запрещено**.

#### 1.3.2. Стиль изложения — **ПОВЕСТВОВАТЕЛЬНЫЙ ТЕКСТ, НЕ ПУНКТЫ**

**Это критически важное требование.**

Запрещено писать маркированными списками (bullets) в разделах с описанием. Исключение — таблицы и чек-листы по определению.

| ❌ НЕПРАВИЛЬНО (пункты) | ✅ ПРАВИЛЬНО (повествование) |
|:---|:---|
| * Заказ создается в Web UI<br>* Web UI вызывает API Gateway<br>* API Gateway проверяет токен | При создании заказа пользователь через **Web UI** отправляет запрос в **API Gateway**. Получив запрос, **API Gateway** выполняет проверку JWT-токена, обращаясь к **Keycloak**. После успешной валидации запрос маршрутизируется в **Order Service**. |

**Почему это важно:**
- Повествовательный текст читается как история, формируя целостную картину.
- Пункты создают "рваное" восприятие, теряются связи между шагами.
- При генерации текста AI должен быть настроен на связное описание, а не на выдачу списка фактов.

#### 1.3.3. Выделение элементов
Все названия компонентов, сервисов, баз данных и других элементов из **Каталога элементов** выделяются **полужирным шрифтом** при первом упоминании в потоке.

**Пример:**
> При создании заказа пользователь через **Web UI** отправляет запрос в **API Gateway**. **API Gateway** проверяет токен через **Keycloak** и перенаправляет запрос в **Order Service**, который сохраняет данные в **Core DB**.

#### 1.3.4. Тон и грамматика
- Изложение от третьего лица.
- Использование настоящего времени для описания работы системы ("сервис выполняет", "запрос поступает").
- Безоценочные формулировки ("сервис обеспечивает", "компонент отвечает за").

## 2. Требования к визуализации — **ОБЯЗАТЕЛЬНОЕ ИСПОЛЬЗОВАНИЕ PLANTUML**

### 2.1. Почему PlantUML
- **Текст как код (Diagrams as Code).** Все диаграммы хранятся в репозитории рядом с документацией.
- **Версионирование.** Изменения в диаграммах отслеживаются через Git.
- **Единообразие.** Все архитекторы рисуют в одной нотации, исключая "художественное творчество".
- **Автоматизация.** Возможность генерации диаграмм в CI/CD, включение в документацию.

### 2.2. Правила использования PlantUML

#### 2.2.1. Нотация C4 в PlantUML
Используйте официальную библиотеку C4-PlantUML (https://github.com/plantuml-stdlib/C4-PlantUML).

**Обязательный импорт в начале каждого файла:**
```plantuml
!include <C4/C4_Container>
!include <C4/C4_Context>
```

#### 2.2.2. Базовые элементы

| Элемент C4 | PlantUML-функция | Назначение |
|:---|:---|:---|
| Person | `Person(alias, label, description)` | Пользователь, роль |
| System | `System(alias, label, description)` | Внешняя система |
| Container | `Container(alias, label, technology, description)` | Ваш сервис/приложение |
| ContainerDb | `ContainerDb(alias, label, technology, description)` | База данных |
| Boundary | `Boundary(alias, label)` | Группировка (регион, зона) |

#### 2.2.3. Цветовое кодирование (обязательно)

| Тип элемента | Цвет (PlantUML sprite) |
|:---|:---|
| Person | `$personBackColor="LightBlue"` |
| External System | `$systemBackColor="LightGrey"` |
| Container (наш сервис) | `$containerBackColor="LightGreen"` |
| Database | `$containerBackColor="LightCoral"` |
| Boundary (зона/регион) | `$boundaryBackColor="LightYellow"` (прозрачный) |

**Пример:**
```plantuml
Person(customer, "Клиент", "Покупатель туров", $personBackColor="LightBlue")
Container(webui, "Web UI", "React", "Пользовательский интерфейс", $containerBackColor="LightGreen")
ContainerDb(coredb, "Core DB", "MySQL", "Транзакционное хранилище", $containerBackColor="LightCoral")
```

#### 2.2.4. Связи
Используйте `Rel` или `Rel_D` для подписанных связей.

```plantuml
Rel(customer, webui, "Использует", "HTTPS")
Rel(webui, apigateway, "API-вызовы", "JSON/HTTPS")
Rel(orderservice, coredb, "Читает/пишет", "SQL")
```

Подпись должна содержать **протокол** и **краткое описание**.

#### 2.2.5. Группировка (Boundary)
Обязательно группируйте элементы по зонам/регионам.

```plantuml
Boundary(region_a, "Регион A (AWS EU-West)") {
    Container(apigw, "API Gateway", "NGINX")
    Container(orders, "Order Service", "Spring Boot")
    ContainerDb(coredb_a, "Core DB", "MySQL Primary")
}
```

### 2.3. Хранение и интеграция

- **Где хранить:** Исходные файлы `.puml` в папке `/docs/diagrams/` репозитория.
- **Именование:** `[номер]-[название]-диаграммы.puml` (например, `01-container-context.puml`)
- **Генерация изображений:** В CI/CD или локально через `plantuml.jar`
- **Включение в документ:** В документе указывается ссылка на сгенерированное изображение или встраивается base64 (для Markdown).

### 4.5. Детальное описание ключевых элементов (НОВЫЙ РАЗДЕЛ)

#### Назначение раздела
В этом разделе фиксируются **архитектурные решения** по самым важным компонентам системы. Для каждого выбранного элемента дается описание его внутреннего устройства, принципов работы, ключевых взаимодействий и обоснование принятых решений.

#### Критерии выбора элементов для детализации
- Компоненты, реализующие сквозные функции (безопасность, аудит, интеграция)
- Компоненты со сложной внутренней логикой (синхронизация данных, оркестрация)
- Компоненты, которые могут быть непонятны команде без дополнительных пояснений
- Компоненты, по которым были сложные архитектурные дискуссии

#### Формат описания

Для каждого элемента используется следующая структура:

1. **Заголовок с названием элемента**
2. **Назначение** (1-2 предложения)
3. **Ключевые решения и принципы работы** (повествовательный текст)
4. **(Опционально) Компонентная диаграмма C3** (PlantUML)
5. **Взаимодействия** (с какими элементами и как)

**Пример 1: PDP Service (Policy Decision Point)**

> #### PDP Service
>
> **Назначение:** PDP Service обеспечивает централизованную авторизацию запросов на основе атрибутов пользователя, ресурса и контекста (модель ABAC).
>
> **Ключевые решения и принципы работы:**
> Сервис реализует классическую модель PDP (Policy Decision Point), получая от API Gateway (который выступает в роли PEP) контекст запроса: идентификатор пользователя, роли, HTTP-метод, путь запроса и идентификатор ресурса. На основе этих данных сервис оценивает политики доступа, хранящиеся в **Policy DB** (PostgreSQL). Все политики загружаются в кэш **Redis** при старте и обновляются при изменениях, что обеспечивает высокую производительность (решения принимаются за <10 мс). Администраторы управляют политиками через **Admin UI**, который доступен только через VPN. Изменения в политиках применяются без перезапуска сервиса — механизм отслеживает обновления в БД и инвалидирует кэш.
>
> **Взаимодействия:**
> - Получает запросы на авторизацию от **API Gateway** по HTTP
> - Читает политики из **Policy DB** (SQL)
> - Кэширует решения и политики в **Redis**
> - Отправляет события аудита в **Audit Service**

**Пример 2: Data Sync Service (с компонентной диаграммой)**

> #### Data Sync Service
>
> **Назначение:** Обеспечивает двунаправленную синхронизацию данных между Legacy-системой и целевой платформой в период миграции с допустимым лагом не более 5 секунд.
>
> **Ключевые решения и принципы работы:**
> Сервис реализует паттерн Anti-Corruption Layer (ACL), изолируя новую систему от устаревшей модели данных Legacy. Для прямого потока (Legacy → Cloud) используется Change Data Capture (CDC) через Debezium, который отслеживает изменения в **Legacy DB** и публикует события в **Kafka**. **Data Sync Service** потребляет эти события, трансформирует данные из старой схемы в новую доменную модель и идемпотентно записывает их в **Core DB**. Для обратного потока (Cloud → Legacy) используется аналогичный механизм, но запись в Legacy выполняется через его **REST API**, чтобы не нарушать бизнес-логику монолита. Сервис включает механизмы обработки конфликтов (стратегия "последняя запись побеждает") и Dead Letter Queue для необработанных событий.
>
> **Компонентная диаграмма:**
>
> ![Компонентная диаграмма Data Sync Service](images/datasync-components.png)
> *Диаграмма 2. Внутренняя структура Data Sync Service*
> [Исходный код PlantUML](./diagrams/02-datasync-components.puml)
>
> **Взаимодействия:**
> - Читает события изменений из **Legacy DB** через CDC (Debezium)
> - Читает/пишет события в **Kafka**
> - Читает/пишет данные в **Core DB** (SQL)
> - Вызывает **Legacy REST API** для обратной синхронизации
> - Отправляет метрики и логи в систему мониторинга

### 4.6. Описание ключевых потоков (ПОВЕСТВОВАТЕЛЬНЫЙ ТЕКСТ)

#### Поток 1: Оформление нового заказа

Когда клиент нажимает кнопку "Оформить заказ" в интерфейсе, **Web UI** формирует POST-запрос к **API Gateway** на эндпоинт `/api/orders`. Запрос содержит данные заказа в формате JSON и включает JWT-токен в заголовке Authorization.

**API Gateway** при получении запроса в первую очередь выполняет валидацию JWT-токена. Для этого он обращается к **Keycloak**, используя его JWKS-эндпоинт, чтобы проверить подпись токена и убедиться, что он не истек. Если токен невалиден, **API Gateway** немедленно возвращает ошибку 401.

После успешной проверки токена **API Gateway** вызывает **PDP Service** для принятия решения об авторизации. В запросе передаются атрибуты пользователя, метод POST и путь `/api/orders`. **PDP Service** проверяет, имеет ли пользователь право создавать заказы, и возвращает разрешение.

Получив положительное решение от **PDP Service**, **API Gateway** перенаправляет запрос в **Order Service** по внутреннему протоколу gRPC, добавляя атрибуты пользователя в метаданные вызова.

**Order Service**, получив запрос, выполняет бизнес-валидацию: проверяет наличие выбранной программы в каталоге через **Catalog Service**, корректность дат и достаточность прав пользователя для оформления заказа. Если валидация проходит успешно, сервис создает запись о заказе в **Core DB**, фиксируя начальный статус "CREATED".

Далее **Order Service** инициирует платеж, отправляя асинхронный запрос в **Integration Service**. **Integration Service** преобразует внутренний формат в требования внешнего **Payment Gateway**, выполняет вызов и возвращает в **Order Service** идентификатор платежа и статус "PENDING". **Order Service** обновляет запись заказа в **Core DB**, сохраняя полученный идентификатор платежа.

После завершения всех операций **Order Service** возвращает **API Gateway** финальный ответ с данными созданного заказа. **API Gateway** проксирует этот ответ в **Web UI**, и клиент видит подтверждение с номером заказа и статусом "Ожидает оплаты".

### 4.7. Ключевые принципы и ограничения (опционально)

- **Single-writer модель:** Запись в транзакционную базу данных выполняется только в активном регионе (Регион A). Регион B работает в режиме read-only до момента аварийного переключения.
- **Безопасность административного доступа:** Все интерфейсы управления (Admin UI, Audit UI) доступны исключительно через VPN с обязательной MFA-аутентификацией.
- **Лаг синхронизации с Legacy:** В период миграции допустимый лаг синхронизации данных между облачной платформой и legacy-системой не должен превышать 5 секунд.

# Дополнение к правилам Lightweight AVD: Раздел "Описание ключевых элементов"

## Место раздела в структуре документа

Раздел **"Описание ключевых элементов"** следует **после "Каталога элементов"** и **перед "Описанием ключевых потоков"**.

```
4. Каталог элементов (таблица)
5. Описание ключевых элементов  <--- ЭТОТ РАЗДЕЛ
6. Описание ключевых потоков
```

## Назначение раздела

В этом разделе фиксируются **архитектурные решения** по компонентам, которые:
- несут критическую бизнес-логику
- реализуют сквозные функции (безопасность, интеграция, синхронизация)
- имеют нетривиальную логику работы
- были предметом архитектурных дискуссий

**Каталог элементов** отвечает на вопрос **"ЧТО есть в системе?"** (перечень).  
**Описание ключевых элементов** отвечает на вопрос **"КАК ЭТО РАБОТАЕТ и ПОЧЕМУ именно так?"** (принципы и решения).

## ЧТО НЕ НАДО ДЕЛАТЬ

**В ЛЕГКОВЕСНОМ AVD МЫ НЕ РИСУЕМ ВНУТРЕННЮЮ СТРУКТУРУ КОНТЕЙНЕРОВ.**

Компонентные диаграммы (C3) — это для полного AVD или для ADR (Architecture Decision Records), если компонент реально сложный. В легковесной версии **никаких квадратиков внутри квадратиков**.

Почему:
- Lightweight AVD должен влезать в 5-7 страниц
- Если тебе понадобилась компонентная диаграмма — значит, компонент слишком сложный и его надо либо упрощать, либо выносить детализацию в отдельный документ

## Правила отбора элементов для описания

**Не нужно описывать все подряд.** Отбирай только те элементы, которые удовлетворяют хотя бы одному критерию:

| Критерий | Примеры |
|:---|:---|
| **Критично для безопасности** | PDP Service, Keycloak, API Gateway (как PEP) |
| **Важно для понимания системы** | Data Sync Service (как работает синхронизация) |
| **Неочевидное решение** | Query Service (почему читает напрямую из реплики, а не из отдельной витрины) |
| **Предмет споров на ревью** | То, что долго согласовывали — зафиксируй, почему победило это решение |

**Количество:** Обычно 3-5 элементов на проект. Если описываешь больше 7 — ты пишешь простыню, а не легковесный AVD.

## Требования к стилю описания

### Язык — **повествовательный текст, НЕ пункты**

| ❌ НЕПРАВИЛЬНО | ✅ ПРАВИЛЬНО |
|:---|:---|
| * Хранит политики в БД<br>* Кэширует решения в Redis<br>* Вызывается из API Gateway | **PDP Service** хранит все политики ABAC в выделенной **Policy DB**. Для обеспечения производительности сервис кэширует как сами политики, так и результаты принятых решений в **Redis**. При поступлении запроса от **API Gateway** сервис сначала проверяет наличие решения в кэше и только при отсутствии выполняет полноценную оценку политик. |

### Выделение элементов
Все названия компонентов, сервисов, баз данных выделяй **полужирным** при первом упоминании в описании.

### Тон
- Изложение от третьего лица
- Настоящее время ("сервис обеспечивает", "компонент отвечает")
- Безоценочные формулировки ("реализован механизм", "применяется паттерн")

## Что должно быть в тексте

В повествовательном описании должны раскрываться:

1. **Принцип работы** — как элемент обрабатывает запросы, что делает
2. **Принятые паттерны** — какие архитектурные паттерны использованы (если есть)
3. **Обоснование решений** — почему выбран именно такой подход
4. **Атрибуты качества** — как элемент обеспечивает требования к производительности, надежности, безопасности
5. **Взаимодействия** — с кем общается и как

**Чего НЕ должно быть:**
- "Внутри сервиса есть классы Controller, Service, Repository" — это уровень кода, не архитектуры
- Диаграмм с компонентами внутри контейнера
- Описания таблиц в БД
- Деталей реализации ("используется библиотека X версии Y")

## Примеры правильного описания

### Пример 1: PDP Service

> #### PDP Service
>
> **Назначение:** Обеспечивает централизованную авторизацию запросов на основе атрибутов пользователя, ресурса и контекста (модель ABAC).
>
> **Ключевые решения и принципы работы:**
> Сервис реализует классическую модель Policy Decision Point (PDP). При получении от **API Gateway** запроса на авторизацию сервис извлекает из запроса контекст: идентификатор пользователя, его роли, HTTP-метод, путь запроса и идентификатор ресурса. На основе этих данных выполняется оценка политик доступа, которые хранятся в выделенной **Policy DB**. Для обеспечения производительности все политики загружаются в кэш **Redis** при старте сервиса и обновляются при изменениях — это позволяет принимать решения за время менее 10 мс. Изменения политик выполняются через **Admin UI** и применяются без перезапуска сервиса: механизм фоновой проверки отслеживает обновления в БД и инвалидирует устаревшие записи в кэше. Все запросы на авторизацию и их результаты фиксируются в **Audit Service** для последующих расследований.
>
> **Взаимодействия:**
> - Получает запросы на авторизацию от **API Gateway** по HTTP
> - Читает политики из **Policy DB**
> - Кэширует решения и политики в **Redis**
> - Отправляет события аудита в **Audit Service**

### Пример 2: Data Sync Service

> #### Data Sync Service
>
> **Назначение:** Обеспечивает двунаправленную синхронизацию данных между Legacy-системой и целевой платформой в период миграции.
>
> **Ключевые решения и принципы работы:**
> Сервис построен на паттерне Anti-Corruption Layer (ACL), изолируя новую систему от устаревшей модели данных Legacy. Для синхронизации изменений из Legacy в Cloud используется Change Data Capture (CDC): сервис отслеживает изменения в **Legacy DB** через чтение бинарного лога, публикует события в **Kafka**, затем трансформирует данные из старой схемы в новую доменную модель и записывает в **Core DB**. Для обратного потока (Cloud → Legacy) используется другой механизм — запись в Legacy выполняется исключительно через **REST API** монолита. Это принципиальное решение: прямая запись в **Legacy DB** могла бы привести к обходу бизнес-логики и нарушению целостности данных. Сервис также реализует идемпотентность операций и контроль лага синхронизации (целевое значение — не более 5 секунд). События, которые не удалось обработать после нескольких попыток, помещаются в Dead Letter Queue для ручного разбора.
>
> **Взаимодействия:**
> - Читает изменения из **Legacy DB** через CDC
> - Публикует и потребляет события из **Kafka**
> - Записывает данные в **Core DB**
> - Вызывает **REST API** Legacy-системы для обратной синхронизации
> - Отправляет метрики в систему мониторинга
