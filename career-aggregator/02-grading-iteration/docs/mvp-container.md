# Контейнерная диаграмма - MVP поиска вакансий для уходящих сотрудников

## Описание MVP

Упрощенная версия системы для быстрого запуска и тестирования гипотезы. Минимум компонентов, простая реализация для junior-разработчиков.

## Контейнеры системы

### 1. Web Application (Streamlit)
- **Технология**: Streamlit
- **Назначение**: Пользовательский интерфейс для поиска вакансий
- **Функции**:
  - Поисковая строка для ввода запроса
  - Чекбоксы для выбора навыков
  - Отображение списка вакансий с процентным соответствием
- **Преимущества**:
  - Очень простая реализация (Python)
  - Быстрый старт (минимум кода)
  - Встроенные компоненты UI

### 2. API Gateway (FastAPI)
- **Технология**: FastAPI
- **Назначение**: Прием запросов, маршрутизация, rate limiting
- **Функции**:
  - Прием POST запросов от Web Application
  - Rate limiting (2 запроса в день на пользователя)
  - Маршрутизация в Search Service
- **Преимущества**:
  - Простая реализация
  - Автоматическая документация API
  - Высокая производительность

### 3. Search Service (Python/FastAPI)
- **Технология**: Python/FastAPI
- **Назначение**: Основной сервис поиска вакансий
- **Функции**:
  - **LLM-парсинг запроса**: Преобразование текстового запроса в структурированные параметры (JSON) через DeepSeek API
  - **Поиск вакансий**: Запрос к HH.ru API для получения вакансий
  - **Генерация эмбеддингов**: Создание векторных представлений через sentence-transformers
  - **Семантическое ранжирование**: Сравнение векторов запроса и вакансий (косинусное сходство)
  - **Кэширование**: Сохранение результатов в in-memory cache
  - **Хранение данных**: Сохранение профилей пользователей и истории запросов в базу данных
- **Преимущества**:
  - Все в одном сервисе (простота)
  - Минимум межсервисного взаимодействия
  - Легко отлаживать

### 4. In-Memory Cache (Python lru_cache)
- **Технология**: Python lru_cache
- **Назначение**: Кэширование LLM-ответов и результатов поиска
- **Функции**:
  - Кэширование ответов от DeepSeek API
  - Кэширование результатов поиска
  - Кэширование эмбеддингов
- **Преимущества**:
  - Очень простая реализация (декоратор @lru_cache)
  - Не требует отдельного сервиса
  - Быстрый доступ (in-memory)
- **Недостатки**:
  - Ограничение по памяти (в пределах процесса)
  - Потеря кэша при перезапуске

### 5. Embedding Engine (Sentence-Transformers)
- **Технология**: Sentence-Transformers (all-MiniLM-L6-v2)
- **Назначение**: Генерация эмбеддингов для ранжирования
- **Функции**:
  - Векторизация текстовых запросов
  - Векторизация описаний вакансий
  - Косинусное сходство для сравнения
- **Требования к ресурсам**:
  - Память: 200-500 МБ
  - Диск: 80 МБ для модели
- **Преимущества**:
  - Работает офлайн
  - Быстрый инференс
  - Минимальные требования к ресурсам

### 6. Database (PostgreSQL)
- **Технология**: PostgreSQL
- **Назначение**: Хранение данных пользователей, истории запросов, вакансий
- **Функции**:
  - Хранение профилей пользователей (имя, email, специальность, навыки)
  - Хранение истории запросов (запрос, дата, результаты)
  - Хранение вакансий (опционально, для кэширования)
  - Хранение логов (ошибки, активность)
- **Преимущества**:
  - Надежное хранение данных
  - Поддержка множества одновременных подключений
  - Хорошая производительность
  - Расширяемость (можно добавить индексы, партиционирование)
  - Подходит для production
- **Недостатки**:
  - Требует отдельного сервера
  - Нужно настраивать и администрировать
  - Больше требований к ресурсам (чем SQLite)
- **Требования к ресурсам**:
  - Память: 256-512 МБ (для MVP)
  - Диск: зависит от данных (1-10 ГБ)

## Внешние системы

### 1. DeepSeek API
- **Назначение**: LLM для преобразования запроса в структурированные параметры
- **Функции**:
  - Парсинг текстового запроса пользователя
  - Извлечение специальности, навыков, параметров (город, зарплата)
  - Возврат структурированного JSON
- **Преимущества**:
  - Бесплатные модели
  - Простой REST API
  - Высокое качество парсинга

### 2. HH.ru API
- **Назначение**: Источник вакансий (поиск в реальном времени)
- **Функции**:
  - Поиск вакансий по параметрам
  - Получение описаний вакансий
  - Ограничение: 2000 вакансий за запрос
- **Преимущества**:
  - Актуальные вакансии
  - Богатый API
  - Бесплатный доступ (с ограничениями)

## Связи между контейнерами

### Входящие связи
- Уходящий сотрудник → Web Application (HTTPS)

### Внутренние связи
- Web Application → API Gateway (POST /api/search, HTTPS/REST)
- API Gateway → Search Service (REST)
- Search Service → Embedding Engine (in-process)
- Search Service → Cache (in-process)
- Search Service → Database (TCP)

### Внешние связи
- Search Service → DeepSeek API (HTTPS)
- Search Service → HH.ru API (HTTPS)

## Последовательность шагов (MVP)

### Шаг 1: Ввод запроса
1. **Уходящий сотрудник** вводит текстовый запрос в Web Application
2. **Выбирает навыки** через чекбоксы
3. **Нажимает кнопку "Найти вакансии"**

### Шаг 2: Отправка запроса
1. **Web Application** отправляет POST запрос в API Gateway
2. **API Gateway** проверяет rate limiting
3. **API Gateway** перенаправляет запрос в Search Service

### Шаг 3: LLM-парсинг запроса
1. **Search Service** отправляет текстовый запрос в DeepSeek API
2. **DeepSeek API** преобразует запрос в структурированные параметры (JSON)
3. **Возвращает JSON** с специальностью, навыками, городом, зарплатой

### Шаг 4: Поиск вакансий
1. **Search Service** отправляет запрос к HH.ru API с параметрами
2. **HH.ru API** возвращает список вакансий (до 2000)
3. **Search Service** нормализует данные

### Шаг 5: Генерация эмбеддингов
1. **Search Service** генерирует эмбеддинг для запроса через Embedding Engine
2. **Search Service** генерирует эмбеддинги для каждой вакансии через Embedding Engine
3. **Кэширует эмбеддинги** в In-Memory Cache

### Шаг 6: Семантическое ранжирование
1. **Search Service** сравнивает эмбеддинг запроса с эмбеддингами вакансий (косинусное сходство)
2. **Ранжирует вакансии** по степени соответствия (процентное соответствие)
3. **Формирует топ-N результатов** (например, топ-50)

### Шаг 7: Кэширование результатов
1. **Search Service** сохраняет результаты в In-Memory Cache
2. **Устанавливает TTL** (время жизни кэша)

### Шаг 8: Отображение результатов
1. **Search Service** возвращает результаты в API Gateway
2. **API Gateway** передает результаты в Web Application
3. **Web Application** отображает список вакансий с процентным соответствием
4. **Уходящий сотрудник** видит релевантные вакансии

## Преимущества MVP схемы

### Для junior-разработчиков
- ✅ **Простая реализация**: Минимум компонентов
- ✅ **Быстрый старт**: Streamlit + FastAPI + Python
- ✅ **Легко отлаживать**: Все в одном процессе
- ✅ **Минимум зависимостей**: Только Python библиотеки

### Для проекта
- ✅ **Быстрый запуск**: Можно запустить за 1-2 недели
- ✅ **Минимум ресурсов**: 1 ГБ памяти достаточно
- ✅ **Тестирование гипотезы**: Проверка идеи без больших затрат
- ✅ **Масштабируемость**: Легко добавить компоненты позже

## Недостатки MVP схемы

### Ограничения
- ❌ **In-Memory Cache**: Потеря кэша при перезапуске
- ❌ **Один процесс**: Ограничение по масштабированию
- ❌ **Нет аутентификации**: Нет управления пользователями
- ❌ **Нет администрирования**: Нет панели для карьерного консультанта

### Риски
- **Производительность**: При большом количестве пользователей может не хватить ресурсов
- **Отказоустойчивость**: Нет fallback механизмов
- **Масштабируемость**: Сложно масштабировать горизонтально

## Следующие шаги после MVP

1. **Добавить аутентификацию**: JWT, OAuth 2.0
2. **Добавить администрирование**: Панель для карьерного консультанта
3. **Заменить In-Memory Cache на Redis**: Для持久化 кэша
4. **Разделить сервисы**: Выделить Vectorization Service, Caching Service
5. **Добавить fallback**: На случай отказа DeepSeek API
6. **Добавить мониторинг**: Логирование, метрики
