# Контейнерная диаграмма - Career Aggregator System

## Последовательность шагов: от формирования профиля до отображения вакансий

### Шаг 1: Формирование профиля пользователя
1. **Карьерный консультант** заходит в Web Application
2. **Создает профиль уволенного сотрудника** (имя, email, специальность)
3. **Указывает навыки и технологии** (например: Java, Spring, PostgreSQL)
4. **Устанавливает ограничения** (2 запроса в день, 2 месяца доступа)
5. **Сохраняет профиль** → данные записываются в User Database

### Шаг 2: Вход уволенного сотрудника
1. **Уволенный сотрудник** заходит в Web Application
2. **Вводит учетные данные** (email, пароль)
3. **API Gateway** проверяет учетные данные через Провайдер аутентификации
4. **Создается сессия** → данные записываются в Cache (Redis)

### Шаг 3: Формирование поискового запроса
1. **Уволенный сотрудник** выбирает специальность (например: Java-разработчик)
2. **Указывает навыки** (например: Spring Boot, Hibernate, PostgreSQL)
3. **Задает параметры поиска** (город, зарплата, тип занятости)
4. **Нажимает кнопку "Найти вакансии"**

### Шаг 4: Проверка кэша
1. **Web Application** отправляет запрос в API Gateway
2. **API Gateway** проверяет rate limiting (2 запроса в день)
3. **API Gateway** перенаправляет запрос в Search Service
4. **Search Service** проверяет кэш через Caching Service
5. **Если кэш есть** → переходим к Шагу 8
6. **Если кэша нет** → продолжаем

### Шаг 5: Векторизация запроса
1. **Search Service** отправляет запрос в Vectorization Service
2. **Vectorization Service** преобразует текстовый запрос в вектор через AI Engine
3. **AI Engine** использует локальную LLM (Ollama/LLaMA) для векторизации
4. **Возвращается вектор** запроса пользователя

### Шаг 6: Получение вакансий из внешних источников
1. **Search Service** отправляет запрос в Source Adapter Service
2. **Source Adapter Service** обращается к HeadHunter API
3. **Получает список вакансий** (до 2000 вакансий)
4. **Нормализует данные** в единый формат
5. **Сохраняет вакансии** в Vacancy Database

### Шаг 7: Векторизация вакансий и матчинг
1. **Source Adapter Service** отправляет вакансии в Vectorization Service
2. **Vectorization Service** векторизирует каждую вакансию через AI Engine
3. **Search Service** сравнивает вектор запроса с векторами вакансий (косинусное сходство)
4. **Ранжирует вакансии** по степени соответствия (процентное соответствие)
5. **Формирует топ-N результатов** (например, топ-50)

### Шаг 8: Кэширование результатов
1. **Search Service** отправляет результаты в Caching Service
2. **Caching Service** сохраняет результаты в Cache (Redis)
3. **Устанавливает TTL** (время жизни кэша)

### Шаг 9: Отображение результатов
1. **Search Service** возвращает результаты в API Gateway
2. **API Gateway** передает результаты в Web Application
3. **Web Application** отображает список вакансий с процентным соответствием
4. **Уволенный сотрудник** видит релевантные вакансии

### Шаг 10: Повторный запрос (кэширование)
1. **Уволенный сотрудник** делает повторный запрос с теми же параметрами
2. **Search Service** проверяет кэш через Caching Service
3. **Кэш найден** → возвращаем результаты из кэша (без обращения к внешним API)
4. **Кэш не найден** → выполняем Шаги 5-9 заново

## Описание системы

**Career Aggregator System** — платформа для автоматизированного подбора вакансий уволенным сотрудникам компании "Астон". Система обеспечивает семантический матчинг вакансий с профилем пользователя с процентным соответствием.

## Режим работы поиска

Поиск вакансий осуществляется **в режиме онлайн** с возможностью **кэширования результатов** для ускорения последующих запросов:

1. **Онлайн-поиск**: При каждом запросе пользователя система обращается к внешним источникам (HeadHunter, LinkedIn, Indeed, Telegram) для получения актуальных вакансий
2. **Векторизация**: Полученные вакансии векторизируются через Vectorization Service и AI Engine
3. **Матчинг**: Сравнение векторов запроса пользователя и вакансий (косинусное сходство)
4. **Кэширование**: Результаты поиска кэшируются в Redis через Caching Service для ускорения повторных запросов
5. **Инвалидация кэша**: Кэш обновляется при изменении профиля пользователя или появлении новых вакансий

## Контейнеры системы

### 1. Web Application
- **Технология**: React/Vue.js
- **Назначение**: Пользовательский интерфейс для выбора IT-специальностей и навыков, просмотра вакансий
- **Функции**:
  - Форма выбора специальности и навыков
  - Отображение релевантных вакансий с процентным соответствием
  - Административная панель для карьерного консультанта

### 2. API Gateway
- **Технология**: Node.js/Express
- **Назначение**: Обработка запросов, аутентификация, маршрутизация, rate limiting
- **Функции**:
  - Аутентификация пользователей (JWT)
  - Маршрутизация запросов к сервисам
  - Rate limiting (2 запроса в день на пользователя)
  - Валидация токенов через внешний провайдер

### 3. Search Service
- **Технология**: Python/FastAPI
- **Назначение**: Семантический поиск вакансий, ранжирование по релевантности
- **Функции**:
  - Прием поисковых запросов от пользователей
  - Координация работы с Vectorization Service и Caching Service
  - Сравнение векторов (косинусное сходство)
  - Ранжирование вакансий по релевантности
  - Формирование результатов поиска

### 4. Vectorization Service
- **Технология**: Python/FastAPI
- **Назначение**: Векторизация запросов пользователей и вакансий через AI Engine
- **Функции**:
  - Векторизация текстовых запросов пользователей
  - Векторизация вакансий при агрегации
  - Взаимодействие с AI Engine для семантического анализа
  - Кэширование векторов для повторного использования

### 5. Caching Service
- **Технология**: Python/FastAPI
- **Назначение**: Кэширование результатов поиска, инвалидация кэша
- **Функции**:
  - Кэширование результатов поиска в Redis
  - Инвалидация кэша при изменении профиля пользователя
  - Инвалидация кэша при появлении новых вакансий
  - Управление TTL (время жизни) кэша

### 6. Source Adapter Service
- **Технология**: Python
- **Назначение**: Агрегация вакансий из любых внешних источников, нормализация данных
- **Функции**:
  - **Онлайн-парсинг**: Получение вакансий с HeadHunter API в реальном времени при запросе пользователя
  - Адаптеры для разных источников (HeadHunter, LinkedIn, Indeed, Telegram)
  - Нормализация данных в единый формат
  - Векторизация вакансий через Vectorization Service
  - Сохранение в Vacancy Database
  - Расширяемость для добавления новых источников

### 7. Admin Service
- **Технология**: Node.js/Express
- **Назначение**: Управление пользователями, мониторинг активности, администрирование платформы
- **Функции**:
  - Управление доступом уволенных сотрудников
  - Мониторинг активности пользователей
  - Контроль ограничений (2 запроса в день, 2 месяца доступа)
  - Административные операции

### 8. User Database
- **Технология**: PostgreSQL
- **Назначение**: Хранение данных пользователей, выбранных специальностей и навыков, профилей
- **Данные**:
  - Профили уволенных сотрудников
  - Выбранные специальности и навыки
  - История запросов
  - Статус доступа

### 9. Vacancy Database
- **Технология**: PostgreSQL + Elasticsearch
- **Назначение**: Хранение и индексация вакансий, полнотекстовый поиск
- **Данные**:
  - Вакансии из внешних источников
  - Векторные представления вакансий
  - Метаданные (источник, дата публикации и др.)

### 10. Cache
- **Технология**: Redis
- **Назначение**: Кэширование результатов запросов, сессии пользователей
- **Функции**:
  - Кэширование результатов поиска
  - Хранение сессий пользователей
  - Снижение нагрузки на базы данных

### 11. AI Engine
- **Технология**: Python/PyTorch + Ollama
- **Назначение**: Локальная нейросеть (LLaMA) для семантического анализа запросов и векторизации вакансий
- **Функции**:
  - Векторизация текстовых запросов
  - Векторизация вакансий
  - Семантический анализ
  - Fallback на внешние LLM провайдеры при недоступности

## Внешние системы

### 1. HeadHunter API
- **Назначение**: Основной источник вакансий
- **Характеристики**:
  - Ограничение: 2000 вакансий за запрос
  - REST API для получения данных
  - Платный доступ (ограниченный бюджет)

### 2. LinkedIn API (Планируется)
- **Назначение**: Дополнительный источник вакансий
- **Статус**: Будущая интеграция

### 3. Indeed API (Планируется)
- **Назначение**: Дополнительный источник вакансий
- **Статус**: Будущая интеграция

### 4. Telegram Боты/Каналы (Планируется)
- **Назначение**: Парсинг вакансий из Telegram каналов и ботов
- **Статус**: Будущая интеграция

### 5. LLM Провайдер (Fallback)
- **Назначение**: Резервный вариант при недоступности локальной модели
- **Варианты**: OpenRouter, бесплатные модели
- **Функции**: Переключение между моделями при ошибках

### 6. Провайдер Аутентификации
- **Назначение**: Аутентификация пользователей
- **Технология**: OAuth 2.0 / JWT
- **Функции**: Валидация токенов, управление сессиями

## Связи между контейнерами

### Входящие связи (от акторов)
- Карьерный консультант → Web Application (HTTPS)
- Уволенный сотрудник → Web Application (HTTPS)

### Внутренние связи
- Web Application → API Gateway (HTTPS/REST)
- API Gateway → Search Service (HTTPS/REST)
- API Gateway → Admin Service (HTTPS/REST)
- API Gateway → User Database (TCP)
- API Gateway → Cache (TCP)

### Связи сервисов поиска
- Search Service → Vectorization Service (HTTPS/REST)
- Search Service → Caching Service (HTTPS/REST)
- Search Service → Vacancy Database (TCP/REST)
- **Search Service → Source Adapter Service (HTTPS/REST)** — вызывает для получения вакансий из внешних источников
- Vectorization Service → AI Engine (HTTPS/REST)
- Caching Service → Cache (TCP)

### Связи сервиса агрегации
- Source Adapter Service → Vacancy Database (TCP)
- Source Adapter Service → Vectorization Service (HTTPS/REST)

### Связи административного сервиса
- Admin Service → User Database (TCP)

### Внешние связи
- Source Adapter Service → HeadHunter API (HTTPS)
- Source Adapter Service → LinkedIn API (HTTPS)
- Source Adapter Service → Indeed API (HTTPS)
- Source Adapter Service → Telegram Боты/Каналы (HTTPS)
- AI Engine → LLM Провайдер (HTTPS/REST)
- API Gateway → Провайдер аутентификации (HTTPS)

## Архитектурные решения

### 1. Микросервисная архитектура
- **Преимущества**: Разделение ответственности, независимое масштабирование, упрощение разработки
- **Реализация**: 6 сервисов (Search, Vectorization, Caching, Source Adapter, Admin, API Gateway)

### 2. Разделение сервисов поиска
- **Search Service**: Только семантический поиск и ранжирование
- **Vectorization Service**: Только векторизация запросов и вакансий
- **Caching Service**: Только кэширование результатов
- **Преимущества**: Четкое разделение ответственности, возможность независимого масштабирования

### 3. Source Adapter Service для работы с любыми источниками
- **Назначение**: Агрегация вакансий из любых внешних источников
- **Расширяемость**: Легко добавлять новые источники (HeadHunter, LinkedIn, Indeed, Telegram)
- **Нормализация**: Единый формат данных для всех источников

### 4. Локальная LLM вместо облачной
- **Причина**: Снижение затрат, контроль данных
- **Реализация**: Ollama + LLaMA в Docker контейнере
- **Риск**: Требует вычислительных ресурсов

### 5. Векторизация и RAG
- **Подход**: Retrieval Augmented Generation
- **Процесс**:
  1. Вакансии векторизируются и сохраняются
  2. Запрос пользователя векторизируется
  3. Сравнение векторов (косинусное сходство)
  4. Ранжирование и вывод топ-N вакансий

### 6. Кэширование
- **Цель**: Снижение нагрузки на API и LLM
- **Реализация**: Redis для кэширования результатов и сессий
- **Инвалидация**: При изменении профиля пользователя или появлении новых вакансий

### 7. Fallback-механизм
- **Цель**: Обеспечение отказоустойчивости
- **Реализация**: Переключение между моделями при ошибках

## Ограничения

1. **Пользователи**: 30-60 человек по каждой технологии (Java, аналитики и др.)
2. **Запросы**: 2 запроса в день на пользователя
3. **Время доступа**: 2 месяца поддержки
4. **Разработчики**: Junior-специалисты (Python)
5. **Бюджет**: Ограниченный (использование бесплатных моделей)
