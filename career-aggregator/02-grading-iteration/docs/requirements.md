Ниже представлен структурированный перечень требований, выделенных из диалога. Разбивка по категориям поможет при формировании бэклога и архитектурных решений.

---

## 1. Пользователи и роли

| Требование | Детали |
|------------|--------|
| **Карьерный консультант** | Основной пользователь. Управляет профилями позиций, профилями кандидатов, настраивает расписание, просматривает аналитику. Имеет доступ к админ‑панели. |
| **Уволенный сотрудник** | Конечный пользователь с ограниченным доступом (2 месяца). Получает логин/пароль от консультанта. Заполняет свой профиль, просматривает вакансии, отмечает избранное, запускает матчинг. |
| **Разграничение прав** | Консультант – административные функции (создание пользователей, просмотр активности). Сотрудник – только просмотр и матчинг. |
| **Доступ** | Отдельный портал (не корпоративный). Доступ по логину/паролю. Срок жизни учётной записи – 2 месяца (возможно продление). |

---

## 2. Основные сценарии использования

### 2.1 Карьерный консультант
| Сценарий | Описание |
|----------|----------|
| **Управление справочниками** | Запуск ML‑потока (извлечение и нормализация компетенций) через интерфейс («кнопка»). |
| **Создание профиля позиции** | Выбор специальности, добавление компетенций с указанием уровня (junior/middle/senior/lead/expert). |
| **Создание профиля кандидата** | Заполнение компетенций кандидата (из справочника) с уровнями. |
| **Настройка расписания** | Через Admin UI задать частоту выгрузки вакансий (например, раз в день). |
| **Мониторинг** | Просмотр активности сотрудников: прогресс заполнения профиля, дата последнего входа, оставшееся время. |
| **Запуск матчинга** | По запросу (или автоматически) – сравнение кандидата с вакансиями. Результат – match_score и gap (список недостающих навыков). |
| **Просмотр результатов** | Таблица вакансий с match_score, грейдом, зарплатой, ссылкой, а также gap по каждой вакансии. |

### 2.2 Уволенный сотрудник
| Сценарий | Описание |
|----------|----------|
| **Регистрация / вход** | Получает приглашение от консультанта, устанавливает пароль, входит в систему. |
| **Заполнение профиля** | Выбирает компетенции из справочника (выпадающий список), указывает свой уровень. Возможность загрузить CV для автоматического извлечения навыков (опционально). |
| **Просмотр вакансий** | Видит список вакансий (предварительно отфильтрованных по его профилю). Может использовать фильтры (город, грейд, зарплата). |
| **Избранное** | Отмечает вакансии, которые ему интересны. |
| **Запуск матчинга** | Нажимает кнопку «Анализ избранных» (или «Анализ всех»). Система вычисляет match_score и gap для выбранных вакансий. |
| **Результат** | Отображается match_score и список недостающих навыков (gap). |

## 3. Источник данных – HH.ru API

| Требование | Детали |
|------------|--------|
| **Поисковый запрос** | `text=NAME:системный+аналитик` (или по другим специальностям). Нужно уточнить синтаксис, чтобы исключить мусорные вакансии («директор по персоналу»). |
| **Параметры** | `per_page=100`, `page` до 20 (максимум 2000 вакансий). Объём данных ~7 МБ. |
| **Загрузка полных описаний** | После получения списка – для каждой новой вакансии загрузить полный текст по `GET /vacancies/{id}`. |
| **Периодичность** | По расписанию (шедулер) – например, раз в день. |
| **Идемпотентность** | Хэширование содержимого вакансии (`hash`), чтобы не обрабатывать дубли. |
| **Rate limiting** | Соблюдать лимиты HH.ru (не более 1 запроса в 0.5-1 секунду). |

## 4. Обработка вакансий и LLM

### 4.1 ML/ETL поток (строим справочник компетенций)
| Требование | Детали |
|------------|--------|
| **Загрузка сырых вакансий** | Сохранение в таблицу `vacancies` (hh_id, name, description, зарплата, город, ссылка и т.д.). |
| **Извлечение компетенций** | LLM (Perplexity/OpenRouter) получает текст вакансии и возвращает массив названий навыков. Результат – `raw_competencies`. |
| **Нормализация** | Кластеризация похожих навыков (эмбеддинги + косинусное сходство). Группировка синонимов. |
| **Создание справочников** | `competencies` (канонические названия), `competency_variants` (синонимы), `competency_categories` (группы), `competency_category_link`. |
| **Ручной запуск** | Администратор (консультант) запускает ML‑поток через интерфейс («Обновить справочник»). |

### 4.2 Продуктовый поток (грейдирование вакансий)
| Требование | Детали |
|------------|--------|
| **Выгрузка новых вакансий** | По расписанию (шедулер) загружаются вакансии из HH.ru, которых ещё нет в `parsed_vacancies`. |
| **Извлечение требований** | Для каждой вакансии LLM возвращает список: `{competency, level, mandatory, confidence, evidence}`. |
| **Маппинг на справочник** | Через `competency_variants` находим `competency_id`. Если не найдено – логируем в `unknown_competencies`. |
| **Сохранение** | `parsed_vacancies` (общий грейд, зарплата, удалёнка, текст) и `parsed_requirements` (competency_id, required_level, is_mandatory, confidence, evidence). |
| **Расчёт грейда вакансии** | На основе требований (и их категорий) вычисляется `overall_level` (junior/middle/senior/lead/expert). |
| **Логирование неизвестных компетенций** | Отдельная таблица `unknown_competencies` для последующего пополнения справочника. |

### 4.3 Матчинг кандидата и gap-анализ
| Требование | Детали |
|------------|--------|
| **Профиль кандидата** | Хранится в `candidate_profiles` и `candidate_skills` (competency_id + level). |
| **Запуск матчинга** | Консультант или сотрудник нажимает кнопку «Анализ» (для избранных вакансий или для всех). |
| **Вычисление match_score** | Для каждой вакансии из `parsed_requirements` сравниваются уровни кандидата и требуемые уровни. Формула: `(сумма баллов совпавших навыков) / (сумма баллов всех требований) * 100%`. |
| **Gap-анализ** | Список `missing_skills` – какие компетенции из требований вакансии отсутствуют у кандидата (или уровень ниже требуемого). |
| **Сохранение результатов** | Таблица `matches` (candidate_id, vacancy_id, match_score, missing_skills_json, calculated_at). |
| **Отображение** | В интерфейсе – список вакансий с match_score, грейдом, зарплатой, ссылкой, а также список недостающих навыков (gap). |

## 5. Технические и архитектурные требования

| Категория | Требование |
|-----------|-------------|
| **Батчирование** | Разбивать вакансии на пачки динамически, с предварительным подсчётом токенов (tiktoken). Размер пачки управляемый (например, 3-5 вакансий для полного описания). |
| **Rate limiting** | Контроль частоты запросов к LLM (Perplexity/OpenRouter) и к HH.ru. При превышении – экспоненциальная задержка. |
| **Retry logic** | При ошибках подключения, таймаутах – повторные попытки (до 5 раз) с увеличением задержки. |
| **Идемпотентность** | Для вакансий – хэш (SHA256) от `name + requirement + responsibility`. Для профилей кандидатов – проверка дублей. |
| **Кэширование** | In-memory кэш для синонимов и категорий (Python-словарь). Redis не требуется (на MVP). |
| **Векторизация** | Не используется (LLM сама понимает семантику). |
| **База данных** | SQLite (для MVP), в перспективе PostgreSQL. Основные таблицы: `vacancies`, `raw_competencies`, `competencies`, `competency_variants`, `competency_categories`, `competency_category_link`, `parsed_vacancies`, `parsed_requirements`, `candidate_profiles`, `candidate_skills`, `matches`, `unknown_competencies`. |
| **Планировщик (шедулер)** | Встроенный (например, APScheduler) – запуск продуктового потока по расписанию. Настройки расписания через Admin UI. |
| **UI (Streamlit)** | Две роли: консультант (админ-панель) и сотрудник. Интерфейс позволяет управлять профилями, просматривать вакансии, запускать матчинг, настраивать расписание. |
| **Безопасность** | Отдельный контур (не корпоративный). Логин/пароль. Ограничение времени жизни учётной записи (2 месяца). Хранение паролей – хэширование (bcrypt). |
| **Мониторинг и логи** | Логирование ошибок, неизвестных компетенций, времени обработки. Возможность просмотра логов через админ-панель (в упрощённом виде – просмотр таблицы `unknown_competencies`). |
| **Производительность** | Загрузка 2000 вакансий из HH.ru – несколько секунд. Обработка через LLM – несколько минут (зависит от количества токенов, пачек, лимитов). При одновременных сессиях (10-20) – очередь. |
| **Стоимость** | Использование бесплатных моделей через OpenRouter (Gemma, Phi-3, Llama 3). При необходимости – платные модели (DeepSeek, Claude). Контроль расходов через лимиты. |

## 6. Нефункциональные требования (дополнительно)

| Требование | Детали |
|------------|--------|
| **Масштабируемость** | При росте числа пользователей – введение очереди задач (Celery + Redis) и ограничение количества параллельных запросов к LLM. |
| **Надёжность** | Все внешние вызовы (HH.ru, LLM) должны быть обёрнуты в retry с экспоненциальной задержкой. |
| **Прозрачность** | Поле `evidence` в `parsed_requirements` – цитата из вакансии, подтверждающая требование. Поле `confidence` – оценка уверенности LLM. |
| **Расширяемость** | Возможность добавления новых источников вакансий (Telegram, LinkedIn) – через отдельный адаптер. |
| **Документация** | API (если потребуется) должно быть задокументировано. Для внутренних скриптов – комментарии и README. |

## 7. Вопросы, требующие дальнейшего уточнения

- **Количество одновременных сессий** (пиковые нагрузки) – чтобы рассчитать необходимые ресурсы и лимиты LLM.
- **Бюджет на API** – готовы ли платить за более быстрые модели, или ограничимся бесплатными.
- **Интеграция с корпоративной системой** (например, Astra) – нужна ли загрузка навыков сотрудника из HR-системы.
- **Хранение персональных данных** – требования к шифрованию, срокам хранения, соответствию законодательству (152-ФЗ).
- **Деплой** – где будет размещено приложение (внутренний сервер, облако, VPS).
