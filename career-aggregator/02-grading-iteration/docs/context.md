# C4 Context Diagram - Career Aggregator System

## Описание системы

**Career Aggregator System** — платформа для автоматизированного подбора вакансий уволенным сотрудникам компании "Астон". Система обеспечивает семантический матчинг вакансий с профилем пользователя с процентным соответствием.

## Акторы системы

### 1. Карьерный Консультант (Администратор)
- **Роль**: Администратор системы
- **Функции**:
  - Управление доступом уволенных сотрудников к платформе
  - Мониторинг активности пользователей
  - Администрирование платформы
  - Контроль ограничений (2 запроса в день, 2 месяца доступа)

### 2. Уволенный Сотрудник (Конечный пользователь)
- **Роль**: Конечный пользователь системы
- **Функции**:
  - Выбор IT-специальности (Java-разработчик, аналитик и др.)
  - Указание навыков и технологий
  - Получение релевантных вакансий с процентным соответствием
- **Ограничения**:
  - Доступ ограничен 2 месяцами
  - Максимум 2 запроса в день
  - Ручное заполнение профиля (нет интеграции с HR-системой)

## Внешние системы

### 1. HeadHunter API
- **Назначение**: Основной источник вакансий
- **Характеристики**:
  - Ограничение: 2000 вакансий за запрос
  - Текущий процесс: 50 вакансий за раз
  - Платный доступ (ограниченный бюджет)
  - REST API для получения данных

### 2. Другие Источники Вакансий (Планируется)
- LinkedIn
- Indeed
- Telegram каналы и боты
- **Статус**: Будущая интеграция

### 3. Ollama / Локальная LLM
- **Назначение**: Семантический анализ и векторизация
- **Модель**: LLaMA (различные варианты: от 3B до 70B параметров)
- **Развёртывание**: Внутри компании (Docker контейнер)
- **Функции**:
  - Векторизация запросов пользователей
  - Векторизация вакансий
  - Сравнение векторов (косинусное сходство)
  - Ранжирование вакансий по релевантности
- **Преимущества**: Бесплатно, локально, без зависимости от внешних сервисов

### 4. LLM Провайдер (Fallback)
- **Назначение**: Резервный вариант при недоступности локальной модели
- **Варианты**: OpenRouter, бесплатные модели
- **Функции**: Переключение между моделями при ошибках

## Ключевые требования

### Функциональные требования
1. **Матчинг вакансий**: Семантическое сравнение профиля пользователя с вакансиями
2. **Процентное соответствие**: Отображение степени релевантности вакансии
3. **Управление доступом**: Ограничение по времени и количеству запросов
4. **Администрирование**: Мониторинг активности пользователей

### Нефункциональные требования
1. **Производительность**: До 1000 пользователей в день
2. **Масштабируемость**: Возможность добавления новых источников вакансий
3. **Стоимость**: Минимизация затрат (использование локальной LLM)
4. **Простота**: Учитывая junior-уровень разработчиков

### Ограничения
1. **Пользователи**: 30-60 человек по каждой технологии (Java, аналитики и др.)
2. **Запросы**: 2 запроса в день на пользователя
3. **Время доступа**: 2 месяца поддержки
4. **Разработчики**: Junior-специалисты (Python)
5. **Бюджет**: Ограниченный (использование бесплатных моделей)

## Архитектурные решения

### 1. Локальная LLM вместо облачной
- **Причина**: Снижение затрат, контроль данных
- **Реализация**: Ollama + LLaMA в Docker контейнере
- **Риск**: Требует вычислительных ресурсов

### 2. Векторизация и RAG
- **Подход**: Retrieval Augmented Generation
- **Процесс**:
  1. Вакансии векторизируются и сохраняются
  2. Запрос пользователя векторизируется
  3. Сравнение векторов (косинусное сходство)
  4. Ранжирование и вывод топ-N вакансий

### 3. Fallback-механизм
- **Цель**: Обеспечение отказоустойчивости
- **Реализация**: Переключение между моделями при ошибках
- **Список моделей**: Массив с перебором при ошибках

### 4. Кэширование
- **Цель**: Снижение нагрузки на API и LLM
- **Реализация**: Логирование, аналитика, кэширование результатов
