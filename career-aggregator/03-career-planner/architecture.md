# architecture.md — Career Planner (MVP)

> Модульный монолит FastAPI + PostgreSQL/pgvector; источник вакансий за портом-адаптером (C.E.R.B.E.R. либо HH.ru — открытое решение ADR-001).

Обновлено: 08.09.2026, по дорожной карте (Confluence CA, стр. 290768227) и итогам встречи с PO.
Предыдущая версия диаграммы: architecture_v1.1.0.puml. Текущая: architecture_v1.2.0.puml.

## §1 Стек и версии

- Язык: Python 3.10+ (существующая кодовая база aggregator-2).
- Веб-фреймворк: FastAPI + Uvicorn — REST API, оркестрация.
- БД: PostgreSQL 16 + расширение pgvector — хранение и векторный поиск (зафиксировано дорожной картой, Pre-MVP п.6).
- Эмбеддинги: Sentence-Transformers; конкретная модель — ADR-002.
- LLM: внешний API через адаптер; провайдер — ADR-003.
- Фронтенд: — ADR-004.
- Деплой: Docker Compose (один сервер, закрытый контур).

## §2 Слои и зоны ответственности

```
app/
  api/                     — REST-точки; роутеры сгруппированы по доменам
  domains/
    access/                — учётные записи, RBAC, сроки доступа, блокировка, обезличивание
    profile/               — профиль: ФИО, контакты, страна, категория, специализация, навыки, опыт
    taxonomy/              — справочник навыков (название + описание) и специализаций; алиасы
    vacancies/             — пайплайн: расписание (jobs), адаптер источника (Port), обогащение,
                             LLM-адаптер, векторизация, каталог вакансий
    matching/              — предфильтр по технологии + векторный поиск, расчёт % соответствия
    analytics/             — события пользователей, агрегаты, таблицы метрик
  storage/                 — репозитории; по подмодулю на домен
  core/                    — конфигурация, логирование
```

Границы (инварианты):
- Домены общаются только через публичный интерфейс (service-слой) другого домена, не через его внутренности.
- Taxonomy — единственный домен, который остальные читают; никто, кроме него, не пишет в справочник.
- storage не импортирует api/domains; доступ к БД — только через storage.
- Адаптеры (источник вакансий, LLM) живут внутри домена vacancies и не содержат бизнес-логики: только трансляция внешнего формата во внутренний.
- Пайплайн vacancies не вызывается из пользовательского запроса (кроме ручного запуска консультантом в Pre-MVP); матчинг не пишет в Raw DB.
- api не обращается к адаптерам напрямую, только через домены.

## §3 Поток данных

### 3.1 Пайплайн вакансий (ежедневно, MVP; ручной запуск в Pre-MVP)

| Шаг | Слой | Действие |
|---|---|---|
| 1 | jobs | Запуск по расписанию |
| 2 | adapters/vacancy_source | Чтение v_vacancies инкрементом: скользящее окно по published_at (окно > интервала запуска, т.к. published_at — дата публикации HH, а не сбора), дедуп по id + hash полей |
| 3 | storage | Вакансии кладутся в Raw DB «как есть» |
| 4 | pipeline/enrichment | На входе key_skills_enriched источника (уже извлечены из описания, нижний регистр; у HH-части key_skills часто пуст). Задача LLM: чистка мусора и soft skills («с», «по», «опыт», «внимательность»), отсечение лишнего; извлечение из description — только если enriched пуст |
| 5 | services/taxonomy | Маппинг названий на справочник каскадом: точное совпадение → алиасы → pgvector similarity по порогу (порог задаётся после выбора модели ADR-002, у каждой модели своя шкала косинуса) → несмапленное в очередь «Unmapped Skills» на ручную разметку владельцу справочника |
| 6 | pipeline/embeddings | Векторизация конкатенации «Название + Описание» из справочника |
| 7 | storage | Вакансии + векторы навыков в Application PostgreSQL |

### 3.2 Запрос матчинга (пользователь)

| Шаг | Слой | Действие |
|---|---|---|
| 1 | api | Аутентификация, RBAC (роль USER) |
| 2 | services/matching | Предфильтр: User Technology = Vacancy Technology |
| 3 | services/matching | pgvector similarity: каждое требование вакансии × лучший навык пользователя (MAX), среднее = % |
| 4 | api | Сортировка по %, карточка: название, %, компания, ссылка на HH |
| 5 | services/analytics | Событие генерации списка |

### 3.3 Онбординг (после первого входа)

Выбор специализации → выбор User Key Skills из справочника → заполнение опыта работы (аналитика, не матчинг). Векторы пользовательских навыков не считаются на лету — берутся готовыми из справочника.

## §4 Паттерны

- Port / Adapter для источника вакансий: контракт «источник отдаёт вакансии» + реализации CERBER и HH. Изоляция открытого решения ADR-001.
- LLM-адаптер: timeout, ограниченный retry, структурированный ответ; при недоступности — фиксация сбоя задания, без автоматического фоллбэка на другого провайдера (подтверждено PO ранее).
- Матчинг: детерминированный расчёт одним SQL-запросом поверх pgvector (CTE: векторы пользователя → MAX сходства по каждому требованию вакансии → AVG = %; без N+1, векторы не покидают БД — проверено прототипом prototype-vector); версия алгоритма сохраняется с результатом.
- Фоновые задания: отдельный worker-процесс из того же образа (docker compose, APScheduler); причина — RAM: модель эмбеддингов (1–3 ГБ) не живёт в веб-процессе. Брокер очередей (Celery/Redis) не вводится — дневной батч его не оправдывает.
- Маппинг на справочник: каскад точное совпадение → алиасы → векторная близость по порогу → очередь ручной разметки (см. §3.1 шаг 5).

## §5 Секреты и конфигурация

- Локально: .env; на сервере: переменные окружения контейнеров.
- .env.example в репозитории — имена без значений.
- Секреты: токены CERBER/HH, ключ LLM, пароли БД. Текущий пароль CERBER передан через чат — при переходе к прод ротировать и передавать защищённым каналом.
- Подключение к CERBER: без TLS (сервер SSL не поддерживает — проверено 10.09); psycopg2 с sslmode по умолчанию; требование к источнику — включить SSL либо письменное одобрение ИБ plaintext-канала во внутренней сети.
- Инвариант: секреты не в коде, логах, README и чатах.

## §6 Non-functional

- Логирование: структурные логи (запрос, слой, ошибка) без персональных данных и текстов вакансий целиком.
- Аудит: события пользователей с первого дня (входы, просмотры, клики, отклики, генерации) — таблицы метрик в админке.
- Воспроизводимость: pin версий, Docker Compose, модель эмбеддингов зафиксирована версией в конфиге.
- Данные: автоблокировка доступа через 2 мес; обезличивание (ФИО, контакты, логин → анонимный ID) через 6 мес; история действий сохраняется.
- Бэкапы: Application PostgreSQL (справочник с описаниями критичен — наполняется вручную); Raw DB и векторы пересчитываемы.
- Raw DB retention: сырые вакансии хранятся 60 дней (нужны для пересборки при смене модели эмбеддингов ADR-002 или LLM ADR-003), партиционирование по месяцам, старые партиции удаляются; Application DB хранит обработанную историю независимо.
- Память: модель эмбеддингов загружается синглтоном при старте worker-процесса; веб-процесс её не грузит. ONNX/Optimum — после замеров производительности.

## §9 Контракт источника C.E.R.B.E.R. (ADR-001 — решён)

- Подключение: PostgreSQL-протокол, Greenplum за PXF (внешняя таблица поверх файлов), база headhunter, схема schema_career_advisor, только SELECT. Credentials — в секретах (.env), не в коде.
- Объект: view v_vacancies. Поля: id (text), name, alternate_url, archived (bool), area_name, employer_name, employer_accredited_it_employer, experience_name, salary_from/to/currency, description (HTML с entities), key_skills (JSON-массив, из HH, часто пуст), key_skills_enriched (JSON-массив, извлечено источником, нижний регистр), work_format (JSON-массив, содержит \xa0), professional_roles, technologies (JSON-массив специализаций; заполнен с вечера 02.09.2026, раньше пуст), published_at.
- Объём на 10.09: ~68к строк за июль–сентябрь; 8988 с тегами технологий за 02–08.09 (~17 специализаций, бывают мультитеги); ~4% дублей по id в свежих данных; зарплата указана у ~55%.
- Предфильтр матчинга: technologies = наша Vacancy Technology; для данных до 02.09 тегов нет — либо не использовать, либо выводить из professional_roles.
- Особенности чтения (PXF): внешняя таблица периодически отдаёт transfer error — адаптер ОБЯЗАН: ретраи, чанкование по published_at, отказ от LIKE-фильтров по technologies (гасит чтение), логирование пропущенных чанков.
- Опыт: experience_name = 4 диапазона HH («Нет опыта», «От 1 года до 3 лет», «От 3 до 6 лет», «Более 6 лет») — ровно диапазоны фильтра MVP.
- Гео: РФ + РБ + Казахстан/Узбекистан (Алматы, Ташкент) — фильтр локации на нашей стороне.
- Запросы к источнику (зона доставки, не логика): 1) версионирование — изменения схемы только новыми колонками/версиями вьюхи, не ломая текущую; 2) плоские вьюхи `v_vacancy_technologies(vacancy_id, technology)` и `v_vacancy_skills(vacancy_id, skill)` вместо JSON-строк — фильтр JOIN-ом, LIKE не использовать (валит PXF); 3) поле `loaded_at` (время сбора) для честного инкремента — published_at это дата публикации HH, позднособранные вакансии выпадают из окна; 4) фиксация retention сырых данных.
- Требования безопасности (письмо Генриху 10.09): обязательное — сервисный логин с `CONNECTION LIMIT 2` + `statement_timeout 60s`, ротация текущего пароля (гулял в чате), передача нового защищённым каналом; опциональное (по запросу их ИБ) — IP allowlist в pg_hba, hostssl/TLS, клиентские сертификаты вместо пароля. Обоснование деления: реальные риски — утекший пароль и наша же нагрузка на их кластер; allowlist/TLS закрывают гипотетические внутренние угрозы при публичных не-персональных данных.
- Граница ответственности: Цербер доставляет сырьё стабильной схемой; чистка, маппинг на справочник, дедуп и матчинг — на нашей стороне. Чтение — pull по расписанию в Raw DB; FDW и прямое чтение в рантайме отвергнуты (прод не зависит от доступности источника).
