# CRPR_job_aggregating_service

## Описание архитектуры и требования к данным

> Документ для согласования с командой. Описывает как устроен сервис, что переиспользуется из существующего кода, и в каком виде ожидаем данные из HeadHunter в Google Sheets.

---

## 1. Что делает сервис

Сотрудник Астона открывает приложение, выбирает свои навыки из дерева (с уровнями владения), нажимает «Подобрать» — и получает список вакансий, отсортированных по проценту релевантности. Карточки вакансий берутся из Google Sheets, куда лабораторный проект Астона ежедневно выгружает данные из HeadHunter.

---

## 2. Архитектура

### 2.1. Компоненты

| Компонент | Технология | Что делает |
|---|---|---|
| **Фронтенд** | Streamlit (:8501) | Дерево навыков + карточки вакансий |
| **Бэкенд** | FastAPI (:8000) | Чтение Google Sheets, матчинг через LLM, отдача ранжированного списка |
| **Источник данных** | Google Sheets (read-only) | Таблица вакансий, обновляется раз в день лабпроектом |
| **LLM** | OpenAI gpt-4o через LangChain | Сопоставление навыков кандидата с требованиями вакансий |
| **Инфраструктура** | Docker Compose, GitLab CI | 2 контейнера: api + ui |

**Базы данных нет.** Единственное хранилище — Google Sheets. Бэкенд читает его через `gspread`, кэширует результат в памяти на 1 час (данные обновляются раз в день, торопиться некуда).

### 2.2. Поток данных

Подробная диаграмма — в файле [`architecture.drawio`](./architecture.drawio) (формат draw.io).

**Офлайн — сбор вакансий (раз в день):**

| Шаг | Откуда | Куда | Что передаётся |
|---|---|---|---|
| 1 | hh.ru | Лабораторный проект Астона | Вакансии по выбранным технологиям |
| 2 | Лабораторный проект Астона | Google Sheets, лист `vacancies` | Выгрузка вакансий (~1500-2000 строк) |

**Онлайн — подбор позиций (по клику пользователя):**

| Шаг | Откуда | Куда | Что передаётся |
|---|---|---|---|
| 1 | Пользователь | Streamlit UI | Выбор навыков с уровнями |
| 2 | Streamlit UI | FastAPI | POST /rank/positions (список навыков) |
| 3 | FastAPI | In-memory кэш | Запрос кэшированных данных (TTL 1 час) |
| 3a | Кэш (промах) | Google Sheets | gspread read всей таблицы вакансий |
| 4 | FastAPI | OpenAI gpt-4o | Промпт + Markdown-таблица вакансий и навыков |
| 5 | OpenAI gpt-4o | FastAPI | Structured output: рейтинг релевантности 1-100 по каждой вакансии |
| 6 | FastAPI | Streamlit UI | Ранжированный список вакансий |
| 7 | Streamlit UI | Пользователь | Карточки вакансий, отсортированные по проценту |

### 2.3. Кэширование

Google Sheets читается через `gspread` — один вызов забирает весь лист (~2 секунды для 2000 строк). Результат кэшируется в памяти процесса на 1 час:

- Первый запрос после старта или протухания кэша: ~2 секунды
- Все последующие запросы в течение часа: мгновенно
- Лимиты Google Sheets API: 300 чтений/мин — при 1-10 пользователях в день проблем нет

### 2.4. Что переиспользуется из candidate_matching_service

| Файл | Переиспользование |
|---|---|
| `app/core/ranker.py` | LangChain + gpt-4o + structured output. Промпты переписываются под инверсию направления. |
| `app/core/services.py` | gspread + pandas. Источник данных меняется: карты компетенций на таблицу вакансий. |
| `app/api/v1/router.py` | FastAPI маршруты. Добавляется `POST /rank/positions`. |
| `app/schemas/ranking.py` | Pydantic-модели. Адаптируются под новый формат запроса/ответа. |
| `ui.py` | Streamlit. Существенная переработка: два режима — выбор навыков и результаты. |
| `docker-compose.yml` | Без изменений (2 сервиса: api + ui). |

### 2.5. Этап 2 (план)

Этап 1 — LLM-сопоставление (MVP, текущая архитектура).
Этап 2 — векторизация навыков кандидатов и вакансий + векторная БД для мгновенного ранжирования без LLM-вызова.

## 3. Требования к данным в Google Sheets

### 3.1. Общая схема

В одном Google Sheets-документе — два листа:

| Лист | Кто заполняет | Как часто | Назначение |
|---|---|---|---|
| **vacancies** | Лабпроект Астона (автоматически) | Раз в день | Вакансии из HeadHunter |
| **skill_taxonomy** | Команда проекта (вручную, один раз) | По мере необходимости | Справочник навыков с группами и синонимами |

### 3.2. Лист `vacancies` — что мы ожидаем от лабпроекта

Лабпроект выгружает данные из HH API в таблицу. Нам нужно понимать, какие поля попадают в таблицу.

**Минимально обязательные колонки:**

| Колонка | Тип | Обязательна | Пример | Зачем |
|---|---|---|---|---|
| `key_skills` | текст, навыки через `;` | **да** | `Python; PostgreSQL; Docker; Redis` | Матчинг — основа всего. HH отдаёт `key_skills` как структурированный массив, лабпроект должен класть его в одну колонку через разделитель. |
| `title` | текст | да | `Backend Python-разработчик` | Заголовок карточки |
| `url` | текст (URL) | да | `https://hh.ru/vacancy/49123871` | Ссылка из карточки на HH |
| `id` | число | желательно | `49123871` | Дедупликация вакансий |

**Желательные колонки (для карточек):**

| Колонка | Тип | Пример | Зачем |
|---|---|---|---|
| `company` | текст | `Т-Банк` | Название компании |
| `salary_from` | число | `350000` | Зарплата «от» |
| `salary_to` | число | `450000` | Зарплата «до» |
| `area` | текст | `Москва` | Город / удалёнка |
| `experience` | текст | `3-6 лет` | Требуемый опыт |
| `employment` | текст | `Удалёнка` | Формат работы |

**Пример строк таблицы `vacancies`:**

| id | title | company | salary_from | salary_to | key_skills | experience | area | employment | url |
|---|---|---|---|---|---|---|---|---|---|
| 49123871 | Backend Python-разработчик | Т-Банк | 350000 | 450000 | Python; PostgreSQL; FastAPI; Docker; Redis | 3-6 лет | Москва | Удалёнка | hh.ru/vacancy/49123871 |
| 49123872 | Senior Data Engineer | Авито | 300000 | 400000 | Python; SQL; Airflow; Spark; ClickHouse | 3-6 лет | Москва | Гибрид | hh.ru/vacancy/49123872 |
| 49123873 | Python Developer | Яндекс | 250000 | 350000 | Python; SQL; PostgreSQL; Docker; Java | 1-3 года | Москва | Офис | hh.ru/vacancy/49123873 |

### 3.3. Критичный вопрос про `key_skills`

HH API возвращает два поля с описанием вакансии:

| Поле HH API | Что это | Нам подходит? |
|---|---|---|
| `key_skills` | Структурированный массив навыков: `[{name: "Python"}, {name: "PostgreSQL"}]` | **Да, идеально.** Готовый список для матчинга. |
| `description` | HTML-текст полного описания вакансии | Только если `key_skills` нет. Потребуется LLM-извлечение навыков из текста — дополнительный шаг и стоимость. |

**Вопрос к лабпроекту:** попадает ли поле `key_skills` в выгрузку отдельной колонкой? Если да — карточки и матчинг работают без проблем. Если лабпроект выгружает только `description` — нужен дополнительный слой извлечения навыков.

### 3.4. Лист `skill_taxonomy` — справочник навыков

Этот лист заполняется командой вручную, один раз. Описывает структуру навыков: группы, canonical-названия, синонимы.

| group | skill | aliases |
|---|---|---|
| Базы данных | PostgreSQL | postgres; pg; постгрес; postgresql |
| Базы данных | MS SQL | mssql; t-sql; microsoft sql server |
| Базы данных | ClickHouse | click house; ch; кликхаус |
| Базы данных | MySQL | my sql; mariadb; мария |
| Языки | Python | python3; питон; py |
| Языки | Java | jvm; ява |
| Языки | Go | golang; го |
| Фреймворки | FastAPI | fast api; fast-api |
| Фреймворки | Django | джанго; django rest |
| DevOps | Docker | контейнеры; docker compose |
| DevOps | Kubernetes | k8s; кубернетес |
| ... | ... | ... |

**Зачем нужен:**

1. **Синонимы.** HH может написать «postgres», а кандидат выбрал «PostgreSQL». По алиасам это один навык.
2. **Группы.** PostgreSQL и MS SQL — обе «Базы данных». Если кандидат знает PostgreSQL, а вакансия требует ClickHouse — это косвенное совпадение (та же группа, другой инструмент), процент ниже, но не ноль.

**Как работает в рантайме:**

1. Берём `key_skills` из вакансии, режем по `;`.
2. Каждый навык ищем в `skill_taxonomy` по колонке `skill` и `aliases`.
3. Находим группу.
4. Сравниваем с группами навыков кандидата — точное совпадение (тот же навык) или косвенное (та же группа, другой навык).

### 3.5. Что если колонки в таблице вакансий поменяются?

В коде имена колонок не захардкожены. Маппинг «колонка Google Sheets → поле в коде» хранится в конфигурации (`settings.py`). Если лабпроект поменяет название колонки — меняем одну строку в конфиге, код не трогаем.

## 4. Вопросы для согласования

1. **Поля выгрузки.** Какие поля HH попадают в Google Sheets? Особенно критично — есть ли `key_skills` отдельной колонкой, или только `description`.

2. **Количество технологий.** Сейчас ~9. Какой полный список нужен? Достаточно ли расширить список, или есть ограничения со стороны лабпроекта?

3. **Формат `key_skills`.** Лабпроект кладёт навыки через разделитель (`;`) или в каком-то другом формате?

4. **Доступ к таблице.** Предоставить service account JSON для чтения Google Sheets, либо использовать существующий из candidate_matching_service.

5. **Объём данных.** Сколько примерно строк в день? ~1500-2000? Влияет на размер кэша и контекст LLM.

6. **Структура `key_skills` в HH.** В некоторых вакансиях навыки не указаны — как обрабатывать такие вакансии? Исключать из выдачи или показывать с низким рейтингом?
