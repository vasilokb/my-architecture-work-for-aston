## 1. Цель встречи

Существующий сервис (candidate_matching_service) передан команде для адаптации. Нужно помочь кандидату найти позиции с ранжированием по совпадению компетенций кандидата и позиции (1 кандидат, много позиций). Существующий сервис делает обратное — сопоставляет 1 вакансию с кандидатами.

**Что нужно было оценить:**
- Что в существующем сервисе можно переиспользовать, что придётся менять.
- Откуда брать данные по вакансиям (источник, формат).
- Как фронтенд будет отображать данные — команда хочет разместить таблицу вакансий в Google Sheets и выводить карточки из неё.
- Как сопоставлять навыки кандидата с требованиями вакансий.

### 2.3. Что сервис делает сейчас

Инструмент для HR/рекрутеров: сопоставляет **требования вакансии** с внутренними **картами компетенций** сотрудников. Направление — **1 вакансия, много кандидатов/интервьюеров**.

**Поток данных (как реализовано):**

1. Рекрутер вставляет текст требований вакансии в Streamlit-форму, выбирает департамент и лист компетенций.
2. API `POST /rank/candidates` (или `/rank/interviewers`) загружает матрицу компетенций из Google Sheets через `gspread`.
3. DataFrame преобразуется в Markdown-таблицу (`df.to_markdown()`).
4. Markdown-таблица + текст требований отправляются в LangChain-цепочку: `prompt | ChatOpenAI.with_structured_output(WorkerRating)`.
5. LLM (`gpt-4o`, `temperature=0`, `seed=42`) возвращает список `Worker` с `rating` (1–100), `goods` (релевантные навыки), `bads` (навыки к подтягиванию), отсортированный по убыванию.
6. Результат отображается в Streamlit-таблице.

### 2.4. Источник данных — Google Sheets

Захардкоженные таблицы (`DEPARTMENTS_MAP`):

| Департамент | Таблица |
|---|---|
| `1C` | «Карта компетенций 1с» |
| `Data Platform` | «Карта компетенций DP» |
| Интервьюеры | «Карта интервьюеров» |

- Матрицы компетенций: строки = навыки (первый столбец «Навык»), столбцы = сотрудники, ячейки = уровень владения.
- Служебные столбцы фильтруются: `cnslt` (консалтинг) — всегда удаляются; `staff` (стаффинг) и `laba` (лаборатория) — опционально.
- Заголовок таблицы ожидается в строке с индексом 5, данные — с индекса 6.
- Для интервьюеров: перекрёстное чтение двух таблиц, аннотация колонок уровнем (например, `«Ivanov (S2)»`). Департамент `1C` для интервьюеров не поддерживается.

## 3. Ход обсуждения

### 3.1. Контекст и архитектурный подход (00:01–02:05)

- Существующий сервис — инженерный форк сервиса матчинга (не пресейл). Передан команде для адаптации.
- Ранее предложено монолитное решение — система узкая, микросервисы избыточны. Это согласуется с фактической реализацией: компактный монолит FastAPI + Streamlit.
- В архитектуре сервиса: карта компетенций, автокомпетенции (Google Sheets), ранжирование по кандидату — всё это присутствует в коде.

### 3.2. Анализ существующего сервиса (06:49–08:09)

- В реальном времени прошлись по коду сервиса (`architecture.puml`, промпты, таблицы Google Sheets).
- Сервис работает с **Google Sheets** (карта компетенций интервьюеров) и сопоставляет требования позиции с компетенциями сотрудников.
- **Ключевое отличие:** существующий сервис — **1 вакансия, пачка кандидатов**. Нужно наоборот — **1 кандидат, пачка вакансий**.
- Сервис **не работает с вакансиями из HeadHunter** — в коде нет HH-интеграции. Только read-only из Google Sheets.

### 3.3. Два подхода к поиску вакансий (05:22–17:45)

| Параметр | Подход A: По запросу (on-demand) | Подход B: Батч-сбор (кэширование) |
|---|---|---|
| **Когда берутся данные** | При каждом нажатии «Найти вакансии» — реалтайм-запрос к HH | Раз в день собирается массив вакансий и сохраняется локально |
| **Сопоставление** | Запрос к HH, сравнение с резюме в реальном времени | Список предобработан, сравнение по локальным данным |
| **Скорость** | ~20 минут на запрос | Мгновенно |
| **Стоимость токенов** | Выше | Ниже (обработка один раз) |
| **Охват** | Без ограничений по технологиям | Ограничен списком технологий |

### 3.4. Оценка токенов и стоимости (21:35–25:05)

- ~950 токенов на описание одной позиции (hh.ru), ~50 позиций, итого ~47 500 токенов.
- Стоимость: порядка **20 центов** на весь запрос.
- **Вывод:** суммы настолько малы, что можно экспериментировать даже с подходом A.

### 3.5. Оценка количества пользователей (25:41–27:26)

- Сценарий: увольняющиеся сотрудники Астона получают доступ к сервису.
- Оценка: **1–10 человек в день**, максимум до 20.
- Решение: уточнить реальное количество человек в неделю.

### 3.6. Источник данных по вакансиям (43:30–44:49)

- В Астоне есть **лабораторный проект**, который раз в день собирает вакансии из HH **по конкретному списку технологий** (~20 технологий, ~1500–2000 вакансий).
- Этот проект может делиться данными. Список технологий можно расширить.
- **Открытый вопрос:** в каком формате данные и можно ли получить структурированные поля (зарплата, ключевые навыки), а не только текстовое описание.

### 3.7. Можно ли брать данные из Google Sheets? (01:20:11–01:26:16)

> Прямой вопрос с встречи: может ли сервис работать с вакансиями, выгруженными в таблицу Google Sheets (как сейчас делает существующий сервис с картами компетенций)?

**Технически — да.** Существующий сервис уже читает данные из Google Sheets через `gspread` в `app/core/services.py`. Если лабораторный проект Астона выгружает вакансии в Google Sheets-таблицу, то:

- `services.py` может работать почти без изменений — `gspread`-клиент и логика чтения переиспользуются.
- Структура таблицы должна содержать нужные поля: описание вакансии, технология, **ключевые навыки** и **зарплата**.
- **Критичный вопрос:** может ли такая таблица заполняться в реальности? Есть ли у HH ключевые навыки в структурированном виде (а не только в тексте описания)?

Обсуждение свелось к двум вариантам:

| Сценарий | Что меняется в коде |
|---|---|
| HH отдаёт структурированные ключевые навыки | `services.py` работает почти без изменений (gspread), данные готовы для сопоставления |
| HH отдаёт только текстовое описание | Нужен дополнительный слой извлечения навыков из текста (через LLM-промпт) перед сопоставлением |

Если таблицу можно полностью адаптировать под нужды команды — «тогда вообще супер отличный».

### 3.8. Доступ к HeadHunter (33:25–43:25)

- Для программного доступа к hh.ru нужен **корпоративный доступ** — на момент встречи он ещё не получен.
- Для этого требуется **регистрация приложения** от организации (Астон) в качестве разработчика.
- hh.ru при регистрации запрашивает информацию о компании, URL для перенаправления пользователя; заявка рассматривается вручную.
- **Решение:** уточнить процесс получения корпоративного доступа и регистрации приложения.

### 3.9. Механика матчинга навыков (45:16–53:15)

- Вариант 1: **строгое совпадение тегов** — детерминированно, но не учитывает схожесть (SQL vs MS SQL).
- Вариант 2: **LLM-сопоставление** — модель оценивает схожесть стеков (T-SQL ~ SQL, оценка 90%), но недетерминирован.
- **Согласованная позиция:** небольшая вариативность результата (+/-несколько процентов) допустима.
- Существующий сервис уже использует одностадийное LLM-ранжирование (`gpt-4o`, `temperature=0`, `seed=42`) — промпт + Markdown-таблица компетенций, на выходе structured output `Worker[]`.
- Подсвечен граничный кейс: кандидат знает SQL, вакансия требует MS SQL — считать ли полным совпадением. Конкретных правил не зафиксировано.

### 3.10. Двухэтапный подход развития (53:35–55:05)

| Этап | Что делается | Результат |
|---|---|---|
| **Этап 1 (MVP)** | LLM-сопоставление через существующий `ranker.py` (адаптация промптов) | Рабочий MVP, возможно медленный |
| **Этап 2 (развитие)** | Векторизация кандидатов и позиций, векторная БД, мгновенное ранжирование | Высокая скорость |

## 4. Прототипы Figma и фронтенд (01:19:09–01:29:42)

### 4.1. Что показали в Figma

- Страница со списком позиций/вакансий.
- По каждой позиции должны быть **определены навыки** (например, React, Redux и т. д.).
- Карточки вакансий для отображения.

### 4.2. Текущий UI существующего сервиса (`ui.py`)

Streamlit-приложение с двумя вкладками:
1. **«Подбор кандидата»** — рекрутер вводит требования вакансии, получает ранжированный список сотрудников.
2. **«Подбор интервьюера»** — аналогично для интервьюеров (недоступно для департамента 1C).

Предложено добавить **третий режим — «Подбор позиций»** (инверсия): пользователь вводит компетенции кандидата, получает ранжированный список вакансий.

### 4.3. Чего не хватает в Figma (ключевая проблема)

> «У нас есть ключевой бизнес-сценарий, когда пользователь выбирает свои компетенции, а потом отправляет запрос на поиск вакансий. Вот такой бизнес-сценарий. Сейчас на рисунке — это самый основной процесс, а у нас его нет.»

**В Figma не отражён ключевой поток:** пользователь выбирает свои навыки, нажимает «Поиск», получает ранжированный список вакансий с процентом релевантности.

### 4.4. Как должен выглядеть фронтенд (обсуждённый вариант)

**Страница 1 — Резюме:**
- Список технологий.
- Пользователь отмечает свои навыки **чекбоксами**.
- Внизу — кнопка «Найти вакансии».

**Страница 2 — Результаты:**
- Карточки вакансий.
- Для каждой вакансии: **процент релевантности** (rating), навыки по позиции.
- Сортировка по убыванию релевантности.

**Важная особенность:** список вакансий обновляется **раз в день** (offline, лабораторным проектом). Поэтому кнопка «Поиск» не делает запрос к HH, а сопоставляет навыки кандидата с уже предобработанным списком. Результат стабилен в течение дня.

### 4.5. Вопрос соответствия карточек данным

> «У вас есть карточки на Figma — и насколько эти карточки соответствуют тому, что у вас будет в базе данных?»

- Навыки на карточках: либо **предзаполнены** (из CV/профиля кандидата), либо **формируются моделью в моменте** (модель определяет навыки — React, Redux и т. д.).
- Это влияет на архитектуру: если навыки определяются моделью в реальном времени, нужен соответствующий слой обработки.
- Команда хочет разместить таблицу вакансий в Google Sheets и выводить карточки вакансий из неё. Существующая архитектура это поддерживает (Streamlit, FastAPI, `gspread`, Google Sheets). Вопрос: как карточки в Figma должны соответствовать данным из таблицы — навыки берутся напрямую из Google Sheets или определяются моделью.
- Если таблицу вакансий можно полностью адаптировать (структурированные поля), карточки в Figma могут напрямую соответствовать данным.

### 4.6. Совет: сначала сценарии, потом Figma

## 5. Предлагаемая схема работы сервиса

Диаграмма — в файле **[`proposed-flow.puml`](./proposed-flow.puml)** (формат PlantUML, как и существующий `architecture.puml`).

**Краткое описание потоков:**

**Offline-поток (раз в день):** лабораторный проект Астона собирает вакансии из HH.ru и выгружает их в таблицу Google Sheets.

**Online-поток (по запросу пользователя):**
1. Сотрудник Астона заходит на страницу резюме, отмечает навыки чекбоксами.
2. Нажимает «Найти вакансии» — отправляется `POST /rank/positions`.
3. `services.py` загружает таблицу вакансий из Google Sheets через `gspread`.
4. `ranker.py` (LangChain + gpt-4o) сопоставляет навыки кандидата с вакансиями, возвращает `Worker[]` с rating.
5. Страница результатов отображает карточки вакансий с процентом релевантности.

## 6. Принятые решения

1. **Переиспользовать бэкенд** (`ranker.py`, LangChain + structured output) с адаптацией промптов под инверсию (1 кандидат, много вакансий).
2. **Сохранить источник данных Google Sheets** (`gspread` в `services.py`) — таблица вакансий выгружается лабораторным проектом Астона в Google Sheets-совместимом формате.
3. **Существенная переработка фронтенда** (`ui.py`): добавить режим «Подбор позиций» — выбор навыков чекбоксами, затем ранжированные вакансии.
