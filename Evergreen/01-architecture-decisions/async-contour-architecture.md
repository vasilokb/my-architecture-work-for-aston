- **Компаньон:** `docs/c4-component-diagram.mmd` — верхнеуровневая схема (sync + async режимы)

## 1. Назначение

Схема детализирует асинхронный контур АБС и отвечает на два вопроса, которые не решает верхнеуровневая схема:

1. **Как переживаются сбои** — падения сервисов, ределиверы Kafka, таймауты вебхуков, ретраи банка.
2. **Где живёт идемпотентность** — как повтор любой операции на любом шаге не приводит к двойной бизнес-операции (второму кредиту, двойной проводке).

Ключевой принцип: **идемпотентность — свойство бизнес-процесса, а не транспорта.** Kafka и HTTP не дают гарантий exactly-once; дубли нормальны и ожидаемы, дедупликация выполняется на границах владения данными.

## 2. Граница владения и роли

| Компонент | Владелец | Ответственность | НЕ делает |
|---|---|---|---|
| **API Gateway** | Платформа | Аутентификация банка, rate-limit, резолв `tenant_id` | Бизнес-логику, хранение состояний |
| **Sync-сервисы** (4 шт.) | Бизнес-команды | `credit-decision` / `loan-issuance` / `loan-signing` / `accounting` — выполнение бизнес-операций | Не публикуют в Kafka напрямую, отвечают синхронно по REST |
| **Async Facade** | Платформа | Полный жизненный цикл асинхронной операции: приём, хранение, публикация задач, приём результатов, доставка вебхука | Бизнес-логику |
| **Consumer задач** | Платформа | Мост Kafka → REST: вычитывает задачи, вызывает сервисы, публикует результат | Не хранит состояние, не дедуплицирует |
| **Kafka** | Платформа | Транспорт at-least-once | Не источник истины о статусе операции |

Разделение строгое: **таблица `async_operations` — единственный источник истины о статусе операции.** Kafka — транспорт, вебхук — уведомление поверх статуса, sync-ответ — результат вызова. Никакая компонента не хранит статус операции вне этой таблицы.

## 3. Поток операции (happy path)

```
Банк — POST /api/v1/async/operations (Idempotency-Key: request_id)
  → GW: аутентификация, tenant_id
  → Фасад TX: INSERT async_operations (ACCEPTED) — коммит → 202 банку
Task Relay (фон): poll ACCEPTED → publish async-tasks → TASK_PUBLISHED
Consumer задач: consume async-tasks
  → REST / sync-сервис (X-Message-Id) → сервис обрабатывает с Inbox → ответ
  → publish async-results (result | бизнес-ошибка)
Result Consumer (фон, фасад): consume async-results
  → UPDATE async_operations: COMPLETED|FAILED (WHERE TASK_PUBLISHED)
Webhook Sender (фон, фасад): poll COMPLETED/FAILED
  → HTTPS-вебхук в банк (HMAC, event_id) → NOTIFIED
```

Альтернативный канал: банк в любой момент вызывает `GET /async/operations/{request_id}` — long-polling fallback на случай, если вебхук не доходит. Оба канала читают одну строку таблицы, противоречие статусов невозможно.

## 4. Машина состояний операции

```
ACCEPTED → TASK_PUBLISHED → COMPLETED | FAILED → NOTIFIED
```

| Переход | Кто | Триггер | Идемпотентность перехода |
|---|---|---|---|
| `→ ACCEPTED` | Operations API | POST с новым `request_id` | PK `(tenant_id, request_id)` — дубль вставки невозможен |
| `→ TASK_PUBLISHED` | Task Relay | успешный publish в Kafka | повторный publish безопасен (см. §5) |
| `→ COMPLETED/FAILED` | Result Consumer | сообщение из `async-results` | `WHERE status = TASK_PUBLISHED` — повторный UPDATE затрагивает 0 строк |
| `→ NOTIFIED` | Webhook Sender | успешный вебхук (2xx от банка) | переход из NOTIFIED невозможен; повтор вебхука по тому же event_id дедуплицируется банком |

`FAILED` — это **бизнес-неуспех** (отказ стоп-листов, отказ скоринга), а не транспортная ошибка. Транспортные ошибки (сервис лежит, таймаут) не меняют статус — их отрабатывают ретраи Consumer'а, в пределе DLQ.

## 5. Гарантии при сбоях (построчный разбор)

Семантика всех связей — **at-least-once**: дубликаты возможны на любом шаге, потери исключены.

| Сбой | Поведение | Кто защищает |
|---|---|---|
| Банк ретраит POST (таймаут на своей стороне) | Второй INSERT падает о PK → банк получает тот же 202, второй задачи не создаётся | PK `(tenant_id, request_id)` |
| Фасад упал между коммитом и ответом 202 | Строка есть (ACCEPTED); банк ретраит → PK conflict → тот же 202 | PK + ретрай банка |
| Task Relay упал после publish, до пометки | Строка осталась ACCEPTED → пере-публикация → дубль в Kafka | Inbox сервисов (см. ниже) |
| Ределивер Kafka в Consumer задач | Повторный REST-вызов сервиса с тем же X-Message-Id | Inbox сервиса: дубль → кэш ответа |
| Consumer упал после ответа сервиса, до publish в async-results | Ределивер задачи → сервис отвечает из кэша Inbox → publish доезжает | Inbox + at-least-once |
| Ределивер async-results | Повторный UPDATE → 0 строк → no-op | `WHERE TASK_PUBLISHED` |
| Webhook Sender упал после отправки, до пометки NOTIFIED | Повторный вебхук с тем же event_id | Дедуп банком по event_id |
| Вебхук не доставлен (эндпоинт банка мёртв) | Ретраи с backoff → исчерпание → DLQ + алерт; статус остаётся COMPLETED/FAILED — банк может прочитать его через GET | DLQ + статусный API |

Инвариант контура: **дубли возможны — потери нет.** Каждая точка возможного дубля имеет явно указанного дедупликатора. Единственный сценарий ручного вмешательства — DLQ (задач или вебхука).

## 6. Inbox в бизнес-сервисах (где реально живёт идемпотентность)

Каждый sync-сервис содержит inbox-таблицу в **своей схеме БД** (не в общей):

```
TX сервиса (одна транзакция):
  SELECT из inbox по message_id
    → найдено: вернуть сохранённый ответ (кэш), бизнес-код не выполняется
    → не найдено: бизнес-операция + INSERT inbox (message_id, ответ) — атомарно
```

Дополнительный рубеж: UNIQUE бизнес-ключ в бизнес-таблицах (`application_id` / `loan_id` + тип операции) — даже при баге в inbox-логике двойная проводка невозможна на уровне constraint.

Inbox не может быть «одной общей таблицей» с `async_operations`: они принадлежат разным сервисам и обязаны коммититься в одной транзакции с бизнес-записью (иначе теряется сама guarantee).

## 7. Контракты и сквозные идентификаторы

| Идентификатор | Генерирует | Живёт в | Назначение |
|---|---|---|---|
| `request_id` | Банк | HTTP-заголовок `Idempotency-Key`, таблица (PK), все сообщения | Дедуп на входе, ключ статуса для GET и вебхука |
| `message_id` | Фасад (ULID) | `async-tasks`, X-Message-Id, inbox сервисов | Дедуп бизнес-обработки |
| `event_id` | Фасад (ULID) | `webhook-events`, payload вебхука | Дедуп доставки на стороне банка |

Ключ партиционирования Kafka (`async-tasks`): `tenant_id + entity_id` — сохраняет порядок операций в разрезе одного кредита/клиента и даёт параллелизм между тенантами и сущностями.

### 7.1. Контракт конверта `async-tasks`

Решение встречи 28.08.2026: централизованный Consumer — «перекладчик»; сообщение несёт полный рецепт REST-вызова, поэтому Kafka-контракт один и не дублирует REST-контракты сервисов.

```json
{
  "message_id": "01JD...",
  "request_id": "32F03003EBF81AFA894A0004AC1D4FDA",
  "tenant_id": "evergreen",
  "created_at": "2026-08-28T14:30:00+03:00",
  "request": {
    "httpMethod": "POST",
    "url": "/api/v1/applications",
    "queryParams": { "clientCode": "BVD8LW" },
    "body": { }
  }
}
```

| Поле | Кто заполняет | Назначение |
|---|---|---|
| `message_id` | Фасад (ULID) | Дедуп в inbox бизнес-сервиса (заголовок `X-Message-Id` при вызове) |
| `request_id` | Банк (GUID, = Idempotency-Key) | Дедуп на входе, корреляция статуса и вебхука |
| `tenant_id` | Фасад (из GW) | Мультитенантность, RLS |
| `request.httpMethod` / `url` / `queryParams` / `body` | Продуцирующая сторона | Рецепт вызова; Consumer не знает бизнес-логики |

**Разворачивание консьюмером:**

```
POST {url}?{queryParams}
Headers: X-Message-Id: {message_id}, X-Tenant-Id: {tenant_id}
Body: {request.body}
```

Ответ сервиса (или ошибка) публикуется в `async-results` как есть — конверт результата симметричен (`message_id`, `request_id`, `tenant_id`, `result`).

**Ограничение безопасности:** `url` не может быть произвольным — консьюмер вызывает только эндпоинты из реестра разрешённых операций тенанта (валидация на фасаде при формировании конверта). Иначе внешний тенант получает возможность дёргать любой внутренний адрес через async-канал.

## 8. Принятые решения и альтернативы

| Решение | Альтернатива | Почему так |
|---|---|---|
| Одна таблица `async_operations` (state machine) в фасаде | Отдельные inbox-/outbox-таблицы | Один запрос на операцию (1:1), GET-статус без join'ов; нагрузка (пик 800 rps) не требует разделения. Разделение станет обязательным при 1:N событий или при продюсерах в разных сервисах |
| Два фоновых процесса в фасаде (Relay, Webhook Sender) + Result Consumer | CDC/Debezium, отдельный сервис доставки | Poll + `FOR UPDATE SKIP LOCKED` проще в эксплуатации; релеи и Result Consumer скейлятся инстансами фасада (ShedLock/leader-election при необходимости) |
| Результат идёт через ответный топик `async-results` | Consumer пишет в таблицу напрямую | Фасад и Consumer не разделяют БД-транзакцию; Kafka — стандартный мост, таблица обновляется владельцем (фасадом) |
| Consumer задач стейтless | Consumer сам дедуплицирует | Идемпотентность — на бизнес-границе (решение от 24.08); Consumer проще масштабировать, его рестарт безопасен |
| Webhook Sender читает таблицу, а не Kafka | Sender как Kafka-consumer | Доставка с ретраями — это перечитывание неотправленного; полл таблицы делает retry-цикл тривиальным и не требует Kafka-группы |
| Бизнес-ошибки (FAILED) идут тем же контуром | Отдельный канал ошибок | Единая машина состояний и единый вебхук-контракт; банк различает исход по полю, а не по каналу |

## 9. Ограничения и риски

1. **`GET /async/operations/{request_id}` ещё не заявлен в API фасада** — требует включения в OpenAPI-контракт (без него long-polling fallback из mvp-architecture §5 нереализуем).
2. **Retention таблицы** — строки в NOTIFIED растут неограниченно; нужен job архивации (например, 30/90 дней) с сохранением ответа на дедуп-ретрай «просроченный request_id → 409/422».
3. **Порядок операций для одной сущности** — гарантируется ключом партиции `tenant_id + entity_id`; при смене ключа миграция консьюмер-групп потребует паузы (stop-the-world) — зафиксировать в runbook.
4. **DLQ-инструментарий** — нужен UI/CLI для реплея задач из DLQ и повторной отправки вебхуков; без него DLQ — чёрная дыра.
5. **Backpressure** — если сервисы деградируют, Consumer упирается в ретраи; per-tenant rate limit на Consumer'е (не только на GW) — кандидат на Этап 2.
6. **Мониторинг** — обязательные алерты: глубина `ACCEPTED` (Task Relay отстаёт), глубина `COMPLETED/FAILED` (вебхуки не уходят), размер DLQ, возраст старейшей незавершённой операции.

## 10. DLQ — точки отказа доставки и политика

DLQ нужен везде, где потребитель делает ретраи. В контуре три такие точки; одна из них — не Kafka, а таблица.

### 10.1 Где нужен и где не нужен

| Точка | Нужен ли | Форма | Причина попадания |
|---|---|---|---|
| **Consumer задач** (`async-tasks`) | ✅ | Kafka-топик `async-tasks.dlq` | 5xx/таймауты сервисов после исчерпания ретраев; poison-сообщение (не парсится, неизвестный тип операции) |
| **Result Consumer** (`async-results`) | ✅ | Kafka-топик `async-results.dlq` | Десериализация; `request_id` не найден в таблице (архив/баг) — обновлять нечего |
| **Webhook Sender** | ✅ | **Таблица** `webhook_dead_letters`, не Kafka | Отправитель читает таблицу, а не топик; его «очередь» — сама БД. После исчерпания ретраев строка операции + контекст попыток переносится в dead-letters |
| Task Relay | ❌ | — | Kafka недоступна → строки копятся в `ACCEPTED` (backlog, алерт на глубину), это не DLQ |
| Sync-путь (GW → сервисы) | ❌ | — | Ошибку получает банк синхронно; ретраи и дедуп — на его стороне через `Idempotency-Key` |

### 10.2 Политика ретраев и попадания в DLQ

- Ретраи: экспоненциальный backoff, лимит попыток (например, 5) — затем DLQ.
- **Неретраебельные ошибки — сразу в DLQ, без ретраев:** ошибки десериализации, бизнес-4xx (повтор бессмыслен), неизвестный тип операции.
- Сообщение в DLQ несёт: исходный payload, `message_id`/`request_id`/`tenant_id`, класс ошибки, счётчик попыток, время первой попытки — достаточный контекст для реплея.

### 10.3 Ключевое правило: DLQ задачи ≠ зависшая операция

Попадание задачи в `async-tasks.dlq` **не оставляет операцию висеть** в `TASK_PUBLISHED`: Consumer одновременно публикует `FAILED` (причина — technical_failure) в `async-results` → операция завершается для банка (вебхук + статус в GET). DLQ — внутренняя механика для разбора, банк получает финальный статус в срок.

Исключение — Result Consumer: если в `async-results.dlq` попало сообщение с результатом, операция останется в `TASK_PUBLISHED` — это ловится алертом на возраст операции (§9 п.6) и чинится реплеем.

### 10.4 Реплей

- Replay CLI / Admin UI: перенос из DLQ обратно в исходный топик (или перезапуск отправки вебхука) — **с сохранением исходных `message_id` / `event_id`**: inbox сервисов и дедуп банка корректно гасят повтор, двойной операции не возникнет.
- Реплей — ручное действие (human-in-the-loop) после анализа причины; автоперепубликация из DLQ не допускается.
- Метрика здоровья: размер DLQ = 0 в норме; ненулевой — алерт P2, зависший `TASK_PUBLISHED` старше N минут — P1.

## 11. Открытые вопросы

1. TTL для «подвисших» операций (статус не меняется N часов) — автоперевод в FAILED + вебхук, или только алерт?
2. Семантика ретрая банка для **синхронных** эндпоинтов (sync-путь тоже должен принимать `Idempotency-Key` — тот же inbox в сервисах, но входной ключ от банка) — зафиксировать в контракте GW.
3. Подпись вебхука: состав HMAC-каноникализации (method + path + timestamp + body) и окно анти-replay — вынести в контракт безопасности.
4. Владение проводками: `accounting` — единственный владелец ledger (внутри `loan-signing` проводок нет) — подтвердить и отразить в `c4-component-diagram.md` v2.
