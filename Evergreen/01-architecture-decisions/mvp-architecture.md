### **Архитектурное решение для интеграции банков с АБС-платформой**  
*Версия 1.0 (по итогам обсуждения от 24.08.2026)*

---

#### 1. Введение
Настоящий документ фиксирует архитектурные решения для взаимодействия между мультитенантной АБС-платформой (ядро) и банками-клиентами (в частности, пилотным банком «Эвергрин»). Основная цель – обеспечить масштабируемость, безопасность и соответствие бизнес-процессам при подключении новых банков.

---

#### 2. Бизнес-процессы верхнего уровня
Выделены **три независимых бизнес-процесса**, разделённых действиями клиента (разрывы во времени):

| № | Процесс | Инициатор | Описание |
|---|---------|-----------|----------|
| 1 | **Кредитный конвейер** (заявка → решение) | Клиент подаёт заявку через банк | Проверка стоп-листов, скоринг, формирование кредитного предложения. Возврат результата банку синхронно. |
| 2 | **Оформление кредита** (открытие счёта, подготовка документов) | Клиент соглашается на предложение | Открытие кредитного и операционного счетов, генерация черновика договора. |
| 3 | **Подписание и выдача** (подписание → начисление) | Клиент ставит подпись | Фиксация подписи, привязка документов, перечисление средств с операционного счёта на кредитный. |

Процессы **не зависят друг от друга** и могут выполняться с временными интервалами (от минут до дней).

---

#### 3. Архитектурные принципы
- **Микросервисная декомпозиция по бизнес-процессам** – каждый процесс реализован отдельным микросервисом.
- **Независимость сервисов** – каждый сервис имеет собственную схему БД (или таблицы) и не вызывает другие сервисы синхронно.
- **Синхронное взаимодействие с банками** – банк вызывает REST API соответствующего сервиса **по факту действия клиента** (подача заявки, согласие, подпись). Время ответа – до 300 мс.
- **Асинхронность внутри АБС** – для внутренней декомпозиции (если потребуется) используется Kafka, но это не влияет на внешний контракт.
- **Мультитенантность** – изоляция данных банков на уровне БД (схема на банк или RLS). Единые внутренние топики Kafka с полем `tenant_id`.

---

#### 4. Описание сервисов АБС

| Сервис | Зона ответственности | API (пример) | БД |
|--------|----------------------|--------------|----|
| **credit-decision** | Приём заявки, стоп-листы, скоринг, генерация предложения | `POST /api/v1/applications` | Схема `decision` |
| **loan-issuance** | Открытие счетов, формирование документов (черновик) | `POST /api/v1/loans/issue` | Схема `issuance` |
| **loan-signing** | Подписание, привязка документов, перечисление средств | `POST /api/v1/loans/sign` | Схема `signing` |

Каждый сервис **не вызывает другие синхронно**. При необходимости получения данных (например, `loan-signing` должен знать ID заявки) – используется общая БД (чтение данных из таблиц других сервисов) или асинхронные события (Kafka).

---

#### 5. Взаимодействие
- **Банк → АБС**: только синхронные REST-запросы к трём эндпоинтам (аутентификация через API-ключ или mTLS).  
- **АБС → Банк**: синхронный ответ на каждый запрос (результат операции).  
- **Дополнительно**: для асинхронных уведомлений (например, статус заявки, готовность документа) в будущем могут быть реализованы:
  - **Вебхуки** (приоритетный способ – банк предоставляет HTTPS-колбэк, АБС отправляет уведомления).
  - **Long polling** (как альтернатива для банков, не имеющих публичных эндпоинтов).

**Важно**: между микросервисами АБС **нет** синхронных вызовов. Обмен данными – через общую БД или через внутренние топики Kafka (если потребуется событийная цепочка).

---

#### 6. Безопасность и мультитенантность
- **Аутентификация** банков: API-ключ или клиентские сертификаты (mTLS) на уровне API Gateway.
- **Изоляция данных**: схема БД на каждого банка (или единая схема с RLS-политикой). Поле `tenant_id` присутствует во всех таблицах и сообщениях Kafka.
- **Единые топики Kafka** – для внутренних событий используется один топик с партиционированием по `tenant_id`. Отдельные топики на банк не создаются (избыточно).
- **Шифрование** – передача данных только по HTTPS, при необходимости – шифрование полей с персональными данными.

---

#### 7. Онбординг нового банка (Provisioning)
- Заведение записи о банке в таблице `tenants` (или создание новой схемы БД).
- Выдача API-ключей/сертификатов.
- Настройка лимитов (rate limiting) и прав доступа (RBAC) для банка.
- Автоматизация процесса через административный интерфейс (Self-Service или автоматический скрипт).

---

#### 8. Использование Kafka
- **Внешне** банки не видят Kafka – она используется только внутри АБС.
- **Внутренняя шина** – для обмена событиями между сервисами (например, `credit-decision` публикует событие «заявка одобрена», на которое могут подписаться другие сервисы для превентивных действий). Это опционально и может быть реализовано на следующих этапах.
- **Единый топик** – с полем `tenant_id` для маршрутизации сообщений внутри АБС. Отдельные топики для каждого банка **не требуются**.

---

#### 9. План развития (Roadmap)
- **MVP (текущий этап)** – реализация трёх сервисов с синхронным REST-интерфейсом. Простая общая БД (или схемы). Без внутренней Kafka.
- **Этап 2** – внедрение вебхуков для асинхронных нотификаций (при необходимости).
- **Этап 3** – переход на событийную архитектуру внутри АБС (Kafka) для повышения отказоустойчивости и снижения связности, если нагрузка возрастёт.
- **Этап 4** – горизонтальное масштабирование отдельных сервисов по профилю нагрузки (например, `credit-decision` может быть развёрнут в нескольких экземплярах).

---

#### 10. Заключение
Предложенная архитектура:
- **Соответствует бизнес-процессам** (разрывы по времени между процессами).
- **Обеспечивает производительность** (синхронные REST с лимитом 300 мс).
- **Готова к масштабированию** (микросервисы, изоляция тенантов).
- **Минимизирует сложность** (нет синхронных вызовов между сервисами АБС, единые топики Kafka).

Данное решение является базовым для разработки и может быть дополнено по мере уточнения нефункциональных требований.
