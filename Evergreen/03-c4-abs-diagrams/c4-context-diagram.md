# Архитектурное описание контекстной диаграммы Облачной АБС

## 1. Введение и назначение документа

Настоящий документ описывает контекстную архитектуру **Облачной автоматизированной банковской системы (АБС)**. Диаграмма контекста является верхним уровнем архитектурного описания и определяет границы системы, ее пользователей и внешние системы, с которыми осуществляется взаимодействие.

### 1.1 Целевая аудитория
- Системные архитекторы
- Руководители ИТ-подразделений
- Бизнес-аналитики
- Технические специалисты банков-клиентов
- Разработчики интеграционных решений

### 1.2 Ключевые архитектурные принципы
- **Многотенантность**: Единая платформа обеспечивает работу множества банков-клиентов с полной изоляцией данных
- **Расширяемость**: Возможность построения надстроек и кастомизации в соответствии с бизнес-задачами каждого банка
- **API-first подход**: Взаимодействие с фронтальными системами и надстройками осуществляется через публичное API
- **Разделение ядра и надстроек**: Базовая функциональность АБС отделена от специфических требований конкретных банков
- **Облачная модель**: Развертывание в облачной инфраструктуре с моделью оплаты по факту использования

**Тип:** Система (ядро платформы)

**Назначение:**
Облачная АБС представляет собой центральное ядро банковской автоматизации, предоставляемое как платформа для банков-клиентов. Система обеспечивает базовую функциональность для ведения банковского бизнеса, позволяя банкам строить поверх этого ядра собственные надстройки и кастомизации.

**Ключевые функции ядра:**
- Бухгалтерский учет банковских операций (базовые проводки, план счетов)
- Расчетно-кассовое обслуживание (РКО) физических и юридических лиц
- Кредитный конвейер (андеррайтинг, выдача, обслуживание кредитов)
- Формирование пруденциальной и управленческой отчетности
- Управление лимитами и стоп-листами
- Интеграция с внешними платежными и регуляторными системами
- Управление пользователями и ролевая модель

**Техническая модель:**
- **Модель предоставления:** Платформа как сервис (PaaS) с элементами SaaS
- **Интерфейсы:** REST API, события, вебхуки для кастомизаций
- **Архитектура:** Многотенантная с изоляцией данных на уровне схем или отдельных баз данных
- **Расширяемость:** API-first, возможность подключения внешних модулей и надстроек

## 3. Пользователи системы

### 3.1 Клиент (Физическое лицо)

**Роль:** Конечный пользователь банковских услуг

**Взаимодействие:**
Клиент-физическое лицо не взаимодействует с АБС напрямую. Доступ к банковским услугам осуществляется через **ДБО Физических лиц** — фронтальную систему, которая может быть как стандартной (предоставляемой платформой), так и кастомной (разработанной банком).

**Бизнес-сценарии:**
- Управление счетами и картами
- Инициирование переводов (внутрибанковских, через СБП, карточных)
- Просмотр выписок и истории операций
- Оплата услуг

### 3.2 Клиент (Юридическое лицо)

**Роль:** Юридическое лицо или индивидуальный предприниматель

**Взаимодействие:**
Доступ осуществляется через **ДБО Юридических лиц** — специализированную систему с расширенным функционалом для бизнеса, которая может быть адаптирована под требования конкретного банка.

**Бизнес-сценарии:**
- Формирование и отправка платежных поручений
- Зарплатные проекты
- Валютный контроль
- Получение банковских выписок
- Управление расчетными счетами

### 3.3 Сотрудник банка

**Роль:** Внутренний пользователь банка (операционист, бухгалтер, кредитный инспектор, администратор)

**Взаимодействие:**
Работает через **АРМ Сотрудника** — автоматизированное рабочее место, которое может быть стандартным или расширенным в соответствии с бизнес-процессами конкретного банка.

**Бизнес-сценарии:**
- Обслуживание клиентов в отделении
- Проведение операционного дня
- Андеррайтинг и оформление кредитов
- Формирование отчетности для регулятора
- Администрирование системы и пользователей
- Настройка бизнес-правил и кастомизация процессов

### 3.4 Администратор платформы 

**Роль:** Администратор облачной платформы

**Взаимодействие:**
Работает с АБС напрямую (или через административный портал), не используя фронтальные системы банков-клиентов.

**Бизнес-сценарии:**
- Создание и конфигурация новых тенантов (банков-клиентов)
- Управление лимитами и квотами для каждого тенанта
- Мониторинг состояния платформы и отдельных тенантов
- Управление биллингом и тарификацией
- Обновление версий платформы
- Просмотр общих логов и метрик
- Управление правами доступа администраторов

**Отличие от сотрудника банка:**
- Сотрудник банка работает **внутри** своего тенанта (конкретного банка)
- Администратор платформы работает **на уровне платформы**, управляя всеми тенантами


## 4. Фронтальные системы и надстройки

### 4.1 ДБО Физических лиц

**Тип:** Внешняя система (фронт-офис)

**Назначение:**
Обеспечивает дистанционное обслуживание физических лиц. Может быть реализована как:
- Стандартное решение, предоставляемое платформой
- Кастомная разработка банка, использующая API АБС
- Интеграция с существующей системой банка

**Интеграция с АБС:**
- **Протокол:** REST API
- **Направление:** ДБО → АБС
- **Данные:** Запросы остатков, инициирование переводов, управление картами, получение выписок

**Возможности расширения:**
Банк может добавлять собственные интерфейсы, сценарии обслуживания и дополнительные сервисы поверх базового API.

### 4.2 ДБО Юридических лиц

**Тип:** Внешняя система (фронт-офис)

**Назначение:**
Обеспечивает дистанционное обслуживание юридических лиц и ИП. Поддерживает кастомизацию под специфические требования бизнес-сегментов.

**Интеграция с АБС:**
- **Протокол:** REST API
- **Направление:** ДБО → АБС
- **Данные:** Платежные поручения, зарплатные ведомости, запросы выписок, валютный контроль

**Особенности:**
Поддерживает расширенные форматы документов, интеграцию с корпоративными системами клиентов, ЭЦП и сложные сценарии согласования.

### 4.3 АРМ Сотрудника

**Тип:** Внешняя система (рабочее место)

**Назначение:**
Автоматизированное рабочее место сотрудника банка. Предоставляет базовый функционал, который может быть расширен под специфику банка.

**Интеграция с АБС:**
- **Протокол:** REST API
- **Направление:** АРМ → АБС
- **Данные:** Операционный день, андеррайтинг, комплаенс, отчетность, администрирование

**Возможности расширения:**
- Добавление специфических бизнес-процессов
- Интеграция с внутренними системами банка (CRM, документооборот)
- Настройка ролевой модели и прав доступа
- Кастомизация отчетных форм

### 4.4 Надстройки и кастомизации 

**Тип:** Внешняя система (опциональная)

**Назначение:**
Представляет собой собирательный образ всех клиентских расширений, разрабатываемых банками или сторонними вендорами для кастомизации платформы под специфические бизнес-задачи.

**Типы надстроек:**
- **Специфические модули:** Кредитные продукты с уникальной логикой, нестандартные тарифные сетки
- **Интеграции:** Подключение к CRM, документообороту, бухгалтерским системам банка
- **Расширения интерфейсов:** Кастомизированные формы, отчеты, дашборды
- **Автоматизации:** Скрипты и обработчики для специфических бизнес-процессов

**Интеграция с АБС:**
- **Протокол:** REST API, Webhooks
- **Направление:** Двунаправленное
- **Данные:**
  - *Запросы:* Получение данных, инициирование операций
  - *События:* Подписка на события для реализации собственной логики

**Архитектурные особенности:**
- Надстройки не влияют на работу ядра платформы
- Каждый тенант может иметь свой набор надстроек
- Надстройки разрабатываются и поддерживаются банком или вендором

## 5. Внешние системы (прямые интеграции)

### 5.1 Платежная инфраструктура

**Тип:** Внешняя система

**Назначение:**
Обеспечивает карточный процессинг, эквайринг и управление банкоматной сетью. Интеграция с этой системой может быть как на уровне платформы, так и на уровне отдельных банков.

**Интеграция с АБС:**
- **Протокол:** API / файловый обмен
- **Направление:** Двунаправленное
- **Данные:**
  - *Исходящие:* Выгрузка лимитов, стоп-листов, справочников
  - *Входящие:* Транзакции для бухгалтерского учета

**Архитектурные особенности:**
- Высокие требования к отказоустойчивости
- Низкая латентность
- Возможность подключения различных процессинговых центров

### 5.2 СБП (Система быстрых платежей)

**Тип:** Внешняя система ЦБ РФ

**Назначение:**
Обеспечивает мгновенные переводы между счетами в разных банках по номеру телефона. Является обязательной интеграцией для всех банков.

**Интеграция с АБС:**
- **Протокол:** API
- **Направление:** Двунаправленное
- **Данные:**
  - *Исходящие:* Инициирование переводов, запросы информации о получателе
  - *Входящие:* Входящие переводы, статусы операций

**Бизнес-сценарии:**
- Переводы C2C (клиент-клиент)
- Переводы C2B (оплата товаров и услуг)
- Запросы на перевод

### 5.3 Межбанковские расчеты 

**Тип:** Внешняя система (агрегированная)

**Назначение:**
Обеспечивает межбанковские переводы различных типов. На контекстном уровне представлена как единая система, объединяющая:

| Компонент | Назначение | Протокол |
|-----------|------------|----------|
| **ЦБ РФ (БЭСП)** | Система банковских электронных срочных платежей для крупных переводов в рублях | API / файлы |
| **ЦБ РФ (МЭР)** | Межрегиональные электронные расчеты для небольших платежей | Файловый обмен |
| **Банки-корреспонденты** | Расчеты через ностро/лоро счета для валютных операций и расчетов с банками, не имеющими прямых счетов в ЦБ | SWIFT / Telex |
| **SWIFT** | Международные переводы и обмен финансовыми сообщениями | SWIFT FIN / FileAct |
| **СПФС** | Система передачи финансовых сообщений (российский аналог SWIFT) | API / файлы |

**Интеграция с АБС:**
- **Протокол:** API / файловый обмен / SWIFT
- **Направление:** Двунаправленное
- **Данные:** Платежные поручения, выписки по корреспондентским счетам, SWIFT-сообщения


### 5.4 ЦБ РФ (Регулятор)

**Тип:** Внешняя система

**Назначение:**
Обеспечивает нормативное регулирование и сбор отчетности. Интеграция является обязательной и критически важной для деятельности банка.

**Интеграция с АБС:**
- **Протокол:** API / файловый обмен / АРМ ЦБФ
- **Направление:** Преимущественно исходящее
- **Данные:**
  - Пруденциальная отчетность
  - Обязательные нормативы
  - Отчетность по открытым валютным позициям

### 5.5 Кредитные бюро

**Тип:** Внешняя система

**Назначение:**
Обеспечивает обмен кредитными историями с бюро кредитных историй. Платформа поддерживает интеграцию со всеми основными бюро.

**Интеграция с АБС:**
- **Протокол:** API
- **Направление:** Двунаправленное
- **Данные:**
  - *Исходящие:* Передача кредитных историй
  - *Входящие:* Запрос кредитных историй при андеррайтинге

**Особенности:**
- Поддержка форматов различных бюро
- Соблюдение требований к защите персональных данных
- Возможность настройки скоринговых моделей

## 6. Архитектурные паттерны и принципы

### 6.1 Многотенантность

| Характеристика | Реализация |
|----------------|------------|
| **Изоляция данных** | Логическая изоляция на уровне схемы БД или отдельной базы данных |
| **Кастомизация** | Возможность настройки бизнес-правил, отчетов и процессов для каждого тенанта |
| **Масштабирование** | Независимое масштабирование ресурсов для крупных тенантов |
| **Обновления** | Единое обновление ядра для всех тенантов с сохранением обратной совместимости |

### 6.2 Расширяемость и кастомизация

**Принципы:**
- **API-first:** Все функции ядра доступны через API
- **Событийная модель:** Возможность подписки на события для реализации собственной логики
- **Плагинная архитектура:** Подключение внешних модулей и надстроек
- **Конфигурация, а не код:** Максимальное количество бизнес-правил вынесено в настройки

**Уровни кастомизации:**
1. **Конфигурация:** Настройка справочников, лимитов, тарифов
2. **Расширение:** Добавление собственных полей, форм, отчетов
3. **Интеграция:** Подключение внешних систем через API
4. **Разработка надстроек:** Создание собственных модулей с использованием API платформы

### 6.3 API-first подход

**Принципы:**
- Все функциональные возможности доступны через REST API
- API является контрактом между ядром и надстройками
- Версионирование API для обратной совместимости
- Документация OpenAPI (Swagger)
- Наличие sandbox-окружения для разработки надстроек

**Слои API:**
- **Публичный API:** Для ДБО, АРМ сотрудника и надстроек
- **Партнерский API:** Для интеграции с внешними системами
- **Административный API:** Для управления тенантами и мониторинга

## 7. Потоки данных (ключевые сценарии)

### 7.1 Перевод между счетами в разных банках (через СБП)

```
Клиент (Физ.лицо) → ДБО → АБС → СБП → АБС другого банка
```

**Характеристики:**
- Синхронный режим
- Мгновенное зачисление
- Единый API для всех банков-клиентов

### 7.2 Операция по карте в торговой точке

```
ТСП → Платежная инфраструктура → АБС (учет)
```

**Характеристики:**
- Асинхронное получение клиринговых файлов
- Массовая обработка транзакций
- Возможность настройки комиссий для конкретного банка

### 7.3 Оформление кредита с кастомной скоринговой модельей

```
АРМ Сотрудника → АБС → Кредитное бюро → АБС (скоринг) → АРМ
```

**Характеристики:**
- Поддержка собственных скоринговых моделей банка
- Возможность интеграции с внешними системами принятия решений
- Настройка кредитных продуктов

### 7.4 Формирование отчетности для ЦБ РФ

```
АБС (формирование) → ЦБ РФ (Регулятор)
```

**Характеристики:**
- Пакетный режим
- Возможность кастомизации отчетных форм
- Поддержка различных форматов сдачи

## 8. Возможности для надстроек и кастомизации

### 8.1 Типовые сценарии кастомизации

| Сценарий | Способ реализации |
|----------|-------------------|
| **Специфические кредитные продукты** | Конфигурация продуктов через API, добавление собственных полей |
| **Интеграция с CRM банка** | Использование событийной модели и webhook'ов |
| **Собственные отчеты и дашборды** | Доступ к данным через API, построение витрин |
| **Расширенный комплаенс** | Добавление собственных проверок через точки расширения |
| **Уникальные тарифные сетки** | Конфигурация тарифов на уровне тенанта |
| **Брендирование интерфейсов** | Кастомизация frontend-систем на стороне банка |

### 8.2 Точки расширения платформы

- **API:** Полный доступ к функциям ядра
- **События:** Подписка на события (создание клиента, проведение платежа и др.)
- **Webhook'и:** Вызов внешних систем при наступлении событий
- **Пользовательские поля:** Расширение справочников и сущностей
- **Скрипты:** Выполнение скриптов в точках расширения (перед проведением, после создания)

## 9. Требования к безопасности

### 9.1 Аутентификация и авторизация
- **API-доступ:** OAuth 2.0 / JWT с поддержкой tenant'ов
- **Межсистемное взаимодействие:** mTLS
- **Фронтальные системы:** Интеграция с корпоративными SSO банков-клиентов
- **Изоляция тенантов:** Каждый банк-клиент работает только со своими данными

### 9.2 Защита данных
- **Шифрование:** TLS 1.3 для всех сетевых взаимодействий
- **Хранение:** Шифрование чувствительных данных в покое
- **Изоляция:** Логическая изоляция данных тенантов на уровне БД

### 9.3 Соответствие требованиям
- 152-ФЗ (персональные данные)
- 161-ФЗ (национальная платежная система)
- Положения Банка России
- Требования к защите информации для банковских систем

## 10. Нефункциональные требования

| Требование | Целевой показатель | Обоснование |
|------------|-------------------|-------------|
| **Доступность** | 99.0% (SLA для платформы) | Допустимые простои до 7,2 часов в месяц |
| **Время ответа API** | < 500 мс (p95) | Достаточно для демонстрации и отладки интеграций |
| **Пропускная способность** | 50+ запросов/сек на тенант | Покрывает потребности пилотных банков |
| **Изоляция** | Полная изоляция данных между тенантами | Базовое требование для банковской системы |
| **Масштабируемость** | Горизонтальное масштабирование до 5+ узлов | Возможность расширения при росте числа клиентов |
| **Время создания тенанта** | Не более 2 часов (автоматизированное) | Упрощение подключения новых банков |
| **Время обновления** | Без даунтайма для существующих тенантов | Непрерывная поставка обновлений |
| **RPO** | 15 минут | Допустимая потеря данных при аварии |
| **RTO** | 4 часа | Время восстановления после отказа |



## 11. Ограничения и допущения

### 11.1 Технологические ограничения
- На начальном этапе поддерживается не более 10 одновременных тенантов
- Объем хранилища на тенант ограничен 100 ГБ
- Количество одновременных сессий на тенант не более 500

### 11.2 Функциональные допущения
- Базовая отчетность покрывает основные формы, сложные отчеты могут требовать надстроек
- Кредитный конвейер реализован для стандартных продуктов, сложные схемы кредитования требуют кастомизации
- Интеграции с внешними системами реализованы для типовых сценариев

## 12. Заключение

Представленная контекстная диаграмма и архитектурное описание определяют границы **Облачной АБС** как платформы для банковской автоматизации.

**Ключевые архитектурные решения:**
1. **Многотенантная архитектура** обеспечивает экономическую эффективность и масштабируемость
2. **Разделение ядра и надстроек** позволяет банкам адаптировать платформу под свои бизнес-задачи без модификации базовой функциональности
3. **API-first подход** создает четкий контракт для разработки надстроек и интеграций
4. **Агрегирование внешних систем** на контекстном уровне упрощает понимание архитектуры
5. **Расширяемость через конфигурацию и точки расширения** минимизирует необходимость в кастомной разработке
