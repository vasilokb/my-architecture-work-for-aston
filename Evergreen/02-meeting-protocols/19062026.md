| 7 | При появлении нового эндпоинта / новой функциональности — как соответствующая информация (роль, разрешение) попадает в Keycloak: через миграции PostgreSQL, SQL-скрипты или админский UI? Участники встречи обсудили: безопасный деплой SQL-запросов vs. конфиг-репозиторий vs. админский UI; упомянут удачный опыт соседнего проекта с альтернативным фреймворком авторизации; решение — **посмотреть на нём** и вернуться с конкретным подходом. | **Финальное решение (per `saas-onboarding-flow.md`, шаг 2):** логика авторизации (`.rego`) живёт в Git и меняется редко (только при появлении новой парадигмы, например доступ по расписанию). **Данные маппингов** `роль → метод` живут в **выделенной БД `admin_db`** Admin Service (таблица `role_permissions`) — **логически/физически отделена от бизнес-данных АБС**. При изменении Admin Service **синхронно** триггерит **OPA Bundle Server** (`POST /internal/v1/bundle/trigger`), OPA Bundle Server запускает **асинхронный воркер**, который читает `role_permissions`, формирует `data.json` и пушит bundle в OPA (`PUT /v1/policies/bundle`). Fallback: cron-джоб внутри OPA Bundle Server раз в 5 минут пересобирает bundle. Git не используется для динамических маппингов — чтобы не плодить мусорные авто-коммиты. Для Keycloak (состав пользователей/ролей) — синхронный Keycloak Admin API в момент операции. PostgreSQL к деплою политик отношения не имеет. | ✅ Уточнено |
| 8 | Как настраивать роли для первого банка — скриптами / экспериментами? | «Как мы в итоге не настраивались… для 1-го банка обычно прописывать… через эксперименты?» | **Частично:** можно и скриптами, но **нужен лёгкий UI** для управления ролями. Финальный способ определить после анализа соседнего проекта. | **Финальное решение (per `saas-onboarding-flow.md`, шаг 2):** владелец банка в UI галочками отмечает, какие методы АБС разрешены для роли. Admin Service сохраняет маппинг в таблицу `role_permissions` в выделенной БД **`admin_db`** и **синхронно** триггерит OPA Bundle Server. Никаких скриптов, никакого Git, никакого ручного ввода разработчиками. | ✅ Уточнено |
| 9 | Где должен размещаться механизм проверки ролей — Keycloak или отдельный сервис? | «Сервис, который будет возвращать, разрешено… В нём должно быть реализовано и само хранение. Попробуйте подумать, как это реализовать на 1-м сервисе и при этом разграничить между банками». | Не дан. **Задача архитектора** — продумать, как реализовать проверку ролей на 1-м сервисе с изоляцией по банкам. | **Решение — OPA** (per `D:\Астон\evergreen\git\abs\docs\c4-infrastructure-container-diagram.md`, п. 2.1). Логика авторизации (`policies/authz.rego`) написана **обобщённо** — Rego-политика итерирует по `input.roles` и проверяет `data.tenants[input.tenant_id].roles[user_role].allowed_methods` с поддержкой wildcard-ов через `match_endpoint`. Данные поставляются в OPA динамически через **OPA Bundle Server** (синхронно по триггеру от Admin Service + cron-джоб fallback раз в 5 минут). Конкретные структуры `data.json`, `input.json` и `authz.rego` — в `saas-onboarding-flow.md`, шаг 4. Kong вызывает OPA синхронно (timeout 50 мс) на каждом внешнем запросе; `tenant_id` — вход Rego-политики. Для внутренних межсервисных вызовов в доверенной сети кластера прокидывается заголовок **X-User-Roles** без обращения к OPA. **PostgreSQL к PDP не относится** — это БД бизнес-данных АБС. | ✅ Уточнено |
| 10 | Как разграничить роли между банками, чтобы банк B не видел роли банка A? | «Как тогда разграничить, чтобы условно второй банк не мог видеть роли первого банка?» | **Ответ:** кастомные роли, которые банк создаёт, **не хранятся в открытом виде** на стороне банка — только у платформы; RLS / изоляция по `tenant_id` снимает этот риск. | **Решение — Defense in Depth (3 уровня):** (1) **Keycloak** — client-роли банка изолированы по client_id, банк видит только свои; (2) **OPA** — `tenant_id` в JWT проверяется Rego-политикой против `data.tenants.active`; (3) **PostgreSQL** — RLS по `tenant_id` через `SET LOCAL app.current_tenant`, даже если OPA ошибся, банк не увидит чужие данные. | ✅ Уточнено |

## 4. Блок 3. Жизненный цикл сотрудника и токена

| 11 | Что делать при увольнении сотрудника с активным JWT-токеном? | «У него есть токен, дживити… 3 часа ещё сотрудника есть, чтобы ещё что-то посмотреть». | **Ответ:** токен нельзя отозвать мгновенно (TTL ~5 ч.). **Решение — blacklist-сервис** на входе через Kong: банк сигнализирует об увольнении, на gateway делается дополнительная проверка по blacklist. | **Финальное решение (per `saas-onboarding-flow.md`, шаг 5):** (1) Admin Service **синхронно** добавляет `user_id` в Redis blacklist с TTL=1 час (максимальное время жизни JWT) — ключ автоматически удалится, не раздувая память. (2) **Асинхронно** выставляет в Keycloak `enabled=false` через `PUT /admin/realms/abs/users/{user-id}`. Keycloak прекращает выдачу новых токенов, но уже выданные валидны до истечения (переписка с Софией, 14.05). Следующий запрос Kong проверяет Redis (`EXISTS blacklist:user:{user_id}`) и при наличии отбивает запрос с 401. | ✅ Отвечено |
| 12 | Каждому сотруднику — отдельный токен с ролью, или роль «общая»? | «Мы будем каждый отдельные роли выдавать отдельный токен, правильно или как мы будем проверять?» | **Ответ:** токен выдаётся **пользователю**, не роли. У каждого сотрудника — индивидуальный токен, в котором содержится роль. | **PDF (Keycloak, п.2):** TTL токена — **1 час**. Подпись проверяется математически на API Gateway (JWKS в кэше, TTL 5 мин, lazy refresh). | ✅ Отвечено |
| 13 | Как регистрировать сотрудников банка в Keycloak — вручную каждого или bulk-загрузкой? | «В банках 100 сотрудников, каждого вручную… как-то забивать с Keycloak?» | **Решение:** банк передаёт **список сотрудников файлом** (например, 10 000), платформа автоматически регистрирует их в Keycloak с ролями и отдаёт банку обратно. Сотрудник при первом входе меняет первичный пароль. | **Финальное решение (per `saas-onboarding-flow.md`, шаг 3):** два режима. **Ручной** — UI → Admin Service → Keycloak Admin API: `POST /admin/realms/abs/users`, `POST .../role-mappings/realm` или `/clients/{uuid}`, `PUT .../execute-actions-email` с телом `["UPDATE_PASSWORD"]` (Keycloak сам шлёт сотруднику email со ссылкой). **Bulk** — UI загружает CSV в Admin Service (`POST /api/v1/employees/import`), Admin Service мгновенно отвечает `202 Accepted` с `task_id`, фоновый воркер по одной создаёт учётки в Keycloak. **Идемпотентность:** ошибки (дубликаты email, несуществующая роль) фиксируются, обработка продолжается. Владелец видит отчёт по `task_id` (`GET /api/v1/employees/import/tasks/{task_id}`): «создано 998, ошибок 2». **Платформа не генерирует и не хранит пароли** — Keycloak шлёт сотруднику ссылку на установку пароля сам (TTL ссылки 1 час). | ✅ Уточнено |

## 8. Ключевые принципы (ADR Summary)
