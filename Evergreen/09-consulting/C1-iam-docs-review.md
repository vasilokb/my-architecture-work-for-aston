**Консультация 1. Ловушка в примере API PDP (избыточный tenant_id)**

> **Василий (16:06):** пример запроса к PDP содержал `tenant_id`:
> ```json
> { "method": "POST", "path": "/v1/credit/score", "roles": ["bank_client"], "tenant_id": "SBER001" }
> ```
> «Раз ты предлагаешь строгую модель RBAC и решил, что PDP не проверяет tenant_id
> (а только роли и пути), то передача tenant_id в этот конкретный JSON-запрос
> становится избыточной. **Если разработчики увидят этот пример в документации,
> они решат: "Ага, значит PDP всё-таки проверяет tenant_id", и потратят время
> на написание логики изоляции в Rego-политиках**»

**Результат:** Михаил исправил документ в тот же день (16:10 «сейчас поправлю»,
16:43 «убрал все о tenant id в pdp»).

**Ценность:** предотвращена потеря времени разработчиков на реализацию
неверной логики изоляции — ошибка поймана на уровне проектной документации,
до написания кода.

**Консультация 2. Эволюция модели авторизации RBAC → ABAC**

> **Василий (16:19):** «Я еще гляну, для MVP RBAC пойдет, но в реальности,
> если пользователей много, нужно использовать ABAC. При RBAC очень много
> усилий будет чтобы заводить роли»

**Ценность:** задано направление развития модели доступа с оговоркой о
достаточности для MVP — типичная работа архитектора: не переусложнить сейчас,
но не заблокировать рост потом.

### 07.05 — Ревью нулевого эпика и ingress-архитектуры

**Консультация 3. Уточнение граничного решения ingress vs Gateway API**

> **Михаил (14:43):** «то как мы видим нулевой эпик»
>
> **Василий (14:47, ответ через 4 минуты):** «Все таки ингресс? не gateway api?»
> + уточняющая схема потока: Банк → Istio Ingress Gateway (TLS termination,
> маршрутизация) → API Gateway Kong (JWT, rate limit, OPA, X-Tenant-Id) →
> бизнес-микросервисы

**Консультация 4. Ревью финальной схемы трафика**

Михаил прислал детализированную схему на утверждение (15:15):

```
[Банк] (HTTPS)
  ▼
[Istio Ingress Gateway]  — TLS termination, DDoS, балансировка, маршрутизация по Hostname
  ▼ (HTTP внутри кластера)
[API Gateway (Kong)]     — Rate limiting (100 RPS на банк), JWT (JWKS-кэш),
                           запрос в OPA (50 мс), проброс X-Tenant-ID
  ▼ (REST / JSON + mTLS)
[Бизнес-микросервисы]
```

> **Василий (16:11):** «Одобрямс. mtls для продакшна. Балансировка нагрузки
> (Level 4/7) — добавь уровень. gRPC — мы же вроде выкидывали? что-то изменилось?»

Два замечания по схеме:
1. Уточнить уровень балансировки (L4/L7) — принятая практика фиксировать явно.
2. Возврат gRPC в схему без решения — контроль соблюдения ранее принятых
   архитектурных решений.

**Результат:** Михаил убрал gRPC («а, сорян»), схема утверждена к
реализации с mTLS для production.
