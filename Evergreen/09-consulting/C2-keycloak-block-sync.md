# C2. Синхронизация статуса безопасности: блокировка банка в Keycloak (CDC vs sync API)

**Направление:** консультационная поддержка по интеграции Keycloak и управлению состоянием безопасности АБС
**Период:** 13 — 15 мая 2026
**Участники:** Василий Буркин (архитектор), София Минаева (аналитик/разработчик команды)
**Канал:** личные сообщения

## Контекст

София проектирует механизм распространения изменения статуса банка (блокировка /
разблокировка / удаление) из сервиса клиентов в остальные системы, включая
Keycloak. Техлид команды направил её на согласование решения к архитектору.

### 14.05, 10:44 — Развёрнутый архитектурный ответ (через 9 минут)

> **Василий:** «София, CDC для обновления статусов в Keycloak не подходит.
> **Это асинхронный процесс, который создает окно уязвимости** — заблокированный
> банк сможет получать токены до тех пор, пока сообщение не дойдет и не
> обработается. Во-вторых, **прямая запись в БД Keycloak сломает его внутренние
> кэши**. Для блокировки нужно использовать синхронный вызов Keycloak Admin API
> в момент изменения статуса в нашей БД. Либо (можно и совместно) проверять
> локальный стоп-лист на уровне API Gateway (Kong). **CDC только для аналитики**
> (переливка данных в Read-реплики), но не для управления состоянием безопасности.
> CDC — это отлов изменений из лога БД (Debezium и т.п.), и потому он асинхронный
> и не транзакционный относительно исходной операции».

**Отклонены два варианта команды с обоснованиями:**
1. CDC для блокировки — окно уязвимости (security)
2. Прямая запись в БД Keycloak — ломает внутренние кэши (technical debt)

**Предложено:** синхронный Keycloak Admin API + опционально стоп-лист на Kong.

### 14.05, 15:32 — Проверка понимания

София воспроизводит полный алгоритм из 6 шагов:

1. Client Service получает запрос на изменение статуса банка (администратор или джоба, например банк не прошёл стоп-листы)
2. Сервис обновляет статус в своей БД
3. Маппинг статуса: `keycloak_enabled = (status == "active")`
4. Синхронный вызов `PATCH /admin/realms/abs/clients/{uuid} {"enabled": ...}`
5. Keycloak меняет статус в своей БД
6. Возврат 204

### 14.05, 18:45 — Подтверждение + важный нюанс о токенах

> **Василий:** «София, да, ты поняла алгоритм верно! Это гарантирует, что в
> момент блокировки доступ банка будет закрыт гарантированно и синхронно.
> **Нюансик на будущее** — на самом деле киклоака не отзывает токены, они
> остаются валидными до истечения срока. В случае вызова к киклоаке, он мгновенно
> запрещает банку запрашивать новые токены. Но если банк уже получил JWT-токен
> 5 минут назад (со сроком жизни, например, 1 час), этот токен технически
> останется валидным до конца часа — так как API Gateway проверяет подпись
> математически. **Для MVP это норм** — закрыли доступ, через 60 минут старые
> токены умрут сами. Но если бизнес в будущем потребует мгновенную блокировку
> уже выданных токенов, нам нужно добавить на уровне API Gateway (Kong) проверку
> по стоп-листу (blacklist), о котором мы говорили в документации.
> **Но для текущей реализации твой алгоритм — 10 из 10**»

## Что доказывает этот артефакт

1. **Скорость:** развёрнутый архитектурный ответ по безопасности — **9 минут**
   после уточнения задачи (10:35 → 10:44); подтверждение алгоритма — в тот же день.
2. **Глубина экспертизы:** внутреннее устройство Keycloak (кэши, Admin API,
   жизненный цикл JWT), природа CDC, PEP/PDP-паттерн — консультация уровня
   senior-архитектора без подготовки, «с ходу».
3. **Предотвращённый security-дефект:** команда собиралась управлять блокировкой
   банков через асинхронный CDC — окно уязвимости, при котором заблокированный
   банк продолжает получать токены. Поймано на этапе проектирования, до кода.
4. **Баланс «сейчас vs потом»:** не потребовал мгновенной блокировки токенов в MVP,
   но зафиксировал готовое решение (blacklist на Kong) на случай требования бизнеса.
5. **Наставничество:** полный цикл обучения — ответ → проверка понимания →
