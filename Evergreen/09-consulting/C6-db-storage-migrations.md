## Вопрос 1. Топология хранения данных

### Запрос (Денис Бет)

> «Как можно организовать хранение данных:
> 1. в каждом поде микросервиса своя бд (считаю самым плохим вариантом)
> 2. отдельная выделенная бд для каждого микросервиса
> 3. одна единая бд для всех микросервисов
> нужен компромисс, так как нужно продумать: бэкапы, администрировать,
> отказоустойчивость, высокую доступность»

> **Василий:** «Привет, попозже гляну»

### Ответ — готовое архитектурное решение в одном сообщении

**Шаг 1. Отбор по рискам домена — почему не отдельные БД:**

> «Если разносить по разным базам — значит внедрять сагу и компенсирующие
> операции, **для банка риск рассинхрона**. Поэтому используем общую базу,
> потому что **банковская проводка затрагивает несколько схем одновременно**»

**Шаг 2. Общая база ≠ общая схема — изоляция по схемам:**

> «Бизнес-данные (счета, клиенты, проводки, кредиты) — общая PostgreSQL.
> **Но не общая схема. Каждый микросервис должен иметь свою схему:**
> account, client, transaction — и с правами только на свою схему.
> **Никто не должен лезть в чужую напрямую**»

**Шаг 3. Мультитенантность поверх схем:**

> «Поверх схем — **Row-Level Security по tenant_id**. Каждый банк видит
> только свои строки, в какой бы схеме они ни лежали»

**Шаг 4. Разделение ответственности по данным:**

> «IAM-конфигурация (role_permissions, tenant mappings) — **отдельная
> admin_db**. Другие паттерны доступа, другой график бэкапов»

**Шаг 5. Бэкапы и высокая доступность:**

> «По бэкапам и доступности — **через Patroni, Master плюс Replica,
> автоматический фейловер**. Один бэкап покрывает все схемы всех тенантов.
> admin_db — отдельный бэкап»
>
> «Мастер падает — Patroni автоматически делает Replica новым Master,
> система переключается, **сотрудники банков не замечают**»

### Реакция

> **Денис:** «Спасибо за подробное пояснение! В процессе настройки задам
> вопросы, если будут. **Пока в теории всё понятно!**»

## Вопрос 2. Миграции схемы: Flyway vs Liquibase

### Запрос (Денис Бет)

> «Определили два способа:
> 1. Flyway — в pipeline отдельная стадия миграции, flyway сам применяет нужные миграции
> 2. Liquibase — декларативно описать изменения и применить **при старте приложения**
>
> Какой способ считаете более GitOps-подходящим и ориентированным на продакшен?»

### Ответ

> **Василий:** «**Берём Flyway за прозрачность SQL.** Миграции через отдельную
> стадию в пайплайне, **не при старте приложения**. Для безопасного изменения
> схемы — **expand/contract**. У меня на других проектах был опыт обоих
> подходов: Flyway-style, где ты пишешь SQL сам, и Liquibase-подобный (Prisma),
> где инструмент генерирует миграции из декларативной схемы. **Для банковского
> продакшена однозначно первый — нужен контроль над каждой строкой SQL,
> которая пойдёт в базу**»

Три решения в одном ответе:
1. Инструмент: Flyway — прозрачность SQL против генерации из декларатива
2. Механика: отдельная стадия пайплайна, а не старт приложения
   (предсказуемость и контроль момента применения)
3. Методология: expand/contract — совместимые вперёд миграции без даунтайма

## Сводка результатов

| # | Решение Василия | Обоснование |
|---|---|---|
| 1 | Общая PostgreSQL, отдельные БД отклонены | Сага/компенсации = риск рассинхрона для банка; проводка затрагивает несколько схем |
| 2 | Схема-на-микросервис, права только на свою | Изоляция без распределённых транзакций |
| 3 | RLS по tenant_id поверх схем | Мультитенантность на уровне строк |
| 4 | admin_db отдельно от бизнес-данных | Разные паттерны доступа и графики бэкапов |
| 5 | Patroni: Master + Replica, автофейловер | HA: «сотрудники банков не замечают»; один бэкап на все схемы/тенантов |
| 6 | Flyway + стадия пайплайна + expand/contract | Контроль каждой строки SQL для банковского продакшена |

Все четыре требования Дениса из запроса (бэкапы, администрирование,
отказоустойчивость, высокая доступность) закрыты явно.

## Что доказывает этот артефакт

1. **Плотность ответа:** на вопрос «какую топологию выбрать» — пятишаговое
   архитектурное решение (отбор по рискам → схема-на-сервис → RLS →
   разделение admin_db → Patroni). Это эквивалент ADR, выданный в чате
   без подготовки, одним сообщением.
2. **Решения от предметной области, не от моды:** «банковская проводка
   затрагивает несколько схем», «риск рассинхрона для банка», «контроль
   над каждой строкой SQL для банковского продакшена» — выбор общий БД
   против модного database-per-service — зрелость, а не консерватизм.
3. **Кросс-проектный опыт как аргумент:** «у меня на других проектах был
   опыт обоих подходов» (включая Prisma) — выбор Flyway сделан из опыта
   обеих альтернатив, а не по привычке.
4. **Полнота охвата:** каждый пункт запроса получил явный ответ; реакция
   Дениса — «пока в теории всё понятно» — вопрос закрыт с первого прохода,
   без итераций.
5. **Связность с собственными артефактами:** RLS-решение детально
   проработано Василием ранее (`04-rls-multitenancy/` — имплементация
   52 КБ + SQL ролей), admin_db реализована в `06-sandbox-stand`,
   решение «общая БД в MVP» зафиксировано в архитектурном решении
   от 24.08 (`01-architecture-decisions/mvp-architecture.md`).
   Консультация = перенос собственной проработанной практики, а не экспромт.
