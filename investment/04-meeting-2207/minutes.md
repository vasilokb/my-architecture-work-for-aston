# Протокол встречи — 22.07.2026

## Что обсуждали

1. **Авторизация.** Архитектор подготовил материалы для самостоятельного изучения: демо-стенд на Keycloak и диаграмму подходов к авторизации по мере развития платформ. Команда ознакомится; текущая реализация авторизации не подлежит обязательному рефакторингу — если объём переделки слишком большой, предпочтение отдаётся ядру операций и регистрации.

2. **financialtransactions-service — граница клиент/админ.** Сервис физически в админке, но управляет финансовыми операциями клиента — смешение основной бизнес-логики в админской части. Функции: подтверждение транзакций, настройка комиссий, способы пополнения/вывода, отчёты, история операций.
   - Договорились о характере функций: подтверждение транзакций — часть **основного процесса** (брокер подтверждает от лица клиента, без подтверждения транзакция не проходит); комиссии/способы вывода — **вспомогательные** (админ); отчёты/история — **чтение** (админ).
   - Архитектор изначально предложил вынести основные операции в клиентскую часть, но обозначил как мнение («это всё на обсуждение»).
   - **Контраргумент команды — data-driven design:** команда отталкивается от данных — клиентские данные → клиентская часть, данные админов → админская часть. Подтверждение выполняет админ/менеджер → админские данные → сервис остаётся в админке. Аналитика: задача реализуется там, где в data-модели хранятся данные.
   - Архитектор задал уточняющие вопросы («кому подтверждают? клиенту», «почему это не клиентские данные?»), команда объяснила (брокер подтверждает от лица клиента → админские данные).
   - **Архитектор согласился с доводами команды** («ну, хорошо»). Решение: сервис остаётся в админской части.

3. **Аудит действий.** Новая задача — аудит действий клиентов и администраторов (безопасность). Решение: выделить в **отдельный сервис**; простой вариант — публикация событий через Kafka с фиксацией «кто и что делал». Аудит и история операций — разные сущности.

4. **support-service / chat-service.** Разделение подтверждено: `support-service` — обращения (тикеты), `chat-service` — отдельный сервис для чата клиента с менеджером. Ранее это была одна сущность, теперь разграничены.

5. **Keycloak.** Сейчас Keycloak — внутренний компонент `customer-service` (клиентские токены); для админки — отдельный `auth-service` со своим Keycloak. Авторизация централизована в API Gateway: проверка токена + роли (для админки). Клиентские сервисы роль не проверяют, админские — проверяют. Решение ~1 года назад: админка — на Keycloak, клиент — на кастомном решении. Архитектор подготовит рекомендации: единый или раздельный Keycloak.

6. **customercare-service.** Клиентский сервис для работы с личным менеджером (приобретение/смена/отключение услуги). Прослойка между клиентом и админкой; приобретение — внешняя оплата через банки. Решение: **переносится в клиентскую часть**.

7. **tax-service.** Автономный клиентский сервис: расчёт налогов, списание при выводе с брокерского счёта, заполнение декларации, возврат/переплата, отчётность по годам. Интеграции с админкой нет. Решение: **подтверждён как клиентский сервис**.

8. **userinfo-service — оркестратор / CQRS.** Единая точка входа для клиентской части: получает и передаёт данные другим сервисам, может изменять данные клиента (прокладка). Не имеет собственной модели данных — бизнес-оркестратор. Архитектор пояснил паттерн CQRS (разделение команд и запросов): запись — в основных сервисах, чтение — через отдельный сервис или реплику для разгрузки БД. Проблемы перегрузки БД сейчас нет. Решение: **оставить как бизнес-оркестратор**; вынос чтения в отдельный сервис — не сейчас, CQRS как целевой подход на будущее.

9. **Чат-сервис — ревью ERD.** Разбор модели данных:
   - **message** — сообщения с историей (пагинация, lazy-load при прокрутке).
   - **topic** — 4 темы + «другое», со статусом active/inactive (управляются менеджерами высокого ранга по сезонности/популярности); без темы писать нельзя.
   - **system messages** — приветственное сообщение, «остались ли вопросы?» (с кнопками закрыть/продолжить), «спасибо за запрос» при закрытии.
   - **employee/client** — данные сотрудника и клиента (имя, фамилия, аватар) для отображения.
   - У одного пользователя — один чат, один закреплённый личный менеджер.
   - **Файловое хранилище:** на первом этапе — Postgres `bytea` (до 1 ГБ); сообщение не может быть пустым (текст или файл); просмотр менеджером, пока живёт обращение.
   - **БД:** одна физическая БД, логически разделена по схемам; `chat-service` — отдельный микросервис с изолированной схемой, единый источник правды для чата.
    - **Синхронизация данных сотрудника/клиента:** по событиям (Kafka, event-driven); шедулер отвергнут. Механизм не утверждён окончательно.
    - **Блокировка клиента (живой JWT):** страница ещё видна, но при прокрутке вверх (после ~10 сообщений) — запрос и выкидывание; при выборе темы — блокировка; проверка при отправке — **не реализована**.
    - **Блокировка/увольнение сотрудника:** обновляет статус в чате; есть ручка (endpoint), тестируется; в админской части блокировка **ещё не реализована**; сессия **не инвалидируется сразу** (пользователя не сразу выкидывает).
    - **Blacklist-сервер (рекомендация архитектора):** в финтехе при блокировке/увольнении вносят в список отозванных токенов; каждый запрос через API Gateway проверяет список. Команда: «нет активных сессий — зачем?». Архитектор: «не всегда, есть обходные пути». На бэке есть недокументированная реализация — источник неясен.

10. **Межсервисное взаимодействие.** Клиент и админка коммуницируют через API Gateway; идёт разделение на два отдельных гейтвея. Токен сотрудника — `auth-service` (свой Keycloak), токен клиента — `customer-service` (кастомное).

## Ответы на архитектурные вопросы

**В1. customercare, tax, financialtransactions — клиентские? Какие признаки говорят об обратном? Куда отнести и как решить смешение?**

- Признаки против (financialtransactions): физически в `backend/` (админка), но методы относятся к операциям клиента — подтверждение транзакций, история, отчёты; в админке намешана основная бизнес-логика транзакций клиента.
- Куда отнести: `financialtransactions` → **админская** (data-driven: подтверждение выполняет админ → админские данные; архитектор согласился с доводами команды после уточняющих вопросов). `customercare` → клиентская. `tax` → клиентская (автономный, без админ-интеграции).
- Как решить: **data-driven design** — клиентские данные → клиент, данные админов → админ; задача реализуется там, где в data-модели хранятся данные. Подтверждение выполняет админ/менеджер → админские данные → сервис в админке. Архитектор задал контрвопросы («кому подтверждают? клиенту»), команда объяснила (брокер подтверждает от лица клиента), архитектор согласился. Аудит — в отдельный сервис; характер функций зафиксирован.

**В2. Роль support-service? Связан ли с chat-service?**

- `support-service` — обращения (тикеты); `chat-service` — отдельный сервис чата клиента с менеджером. Ранее одна сущность, теперь разграничены. Не связаны — независимые сервисы.

**В3. userinfo-service содержит чужую доменную логику. Роль и что хранить в БД?**

- Роль: бизнес-оркестратор (единая точка входа/выхода для клиентской части). Своей модели данных нет.
- Идеально: вынести чтение в отдельный сервис (CQRS — разделение команд и запросов; чтение из реплики/проекций). Сейчас проблемы перегрузки БД нет → оставить как есть. CQRS — целевой подход на будущее.
- Что хранить в своей БД: явного решения нет; при CQRS — проекции/read-модели для сторонних систем.

**В4. UserInfo как оркестратор? Единственный в админке, кто взаимодействует с клиентской частью?**

- Да, может быть оркестратором и единственной точкой входа/выхода для клиентской части. Создание аналогичного сервиса на стороне админки избыточно (запросы идут преимущественно от клиента). Обратный сценарий (клиенту нужны данные об админах) — через общий `chat-service`. Условие: пока помогает — оставить.

**В5. Выделять ли централизованный audit-service?**

- Да. Безопасность — в отдельный контур. Аудит и история операций — разные сущности. Простой вариант: действия публикуются через Kafka в `audit-service` (фиксация «кто и что делал»). Даст единое хранилище, единый формат, централизованный доступ.

**В6. JWT достаточно для защиты данных customer-service, или нужна дополнительная защита?**

- **JWT недостаточен.** Токен stateless — остаётся валидным до истечения срока действия. Заблокированный или уволенный пользователь может продолжать обращаться к сервисам с активным токеном.
- **Рекомендация архитектора — blacklist-сервер.** В финтехе при блокировке или увольнении пользователя вносят в список отозванных токенов. Каждый запрос, проходящий через API Gateway, проверяет этот список. Команда возразила: «у заблокированного нет активных сессий, он не сможет начать». Архитектор ответил: «не всегда, есть обходные пути». На бэке уже есть похожая недокументированная реализация — нужно задокументировать и выяснить, на чём остановились.
- **Поведение при блокировке клиента.** Страница ещё видна, но: при прокрутке истории вверх (после первых ~10 сообщений) отправляется запрос, и заблокированного выкидывает; при выборе новой темы — блокировка; проверка при отправке сообщения пока **не реализована**.
- **Поведение при блокировке или увольнении сотрудника.** Статус обновляется в чате (есть ручка, тестируется). В админской части блокировка **ещё не была реализована**. Сессия **не инвалидируется сразу** — пользователя не выкидывает мгновенно.
- Архитектор (№1) также готовит рекомендации по централизации Keycloak (единый IdP для клиента и админа).

## Что решили

1. Авторизация — материалы для самостоятельного изучения; обязательного рефакторинга нет.
2. financialtransactions-service — остаётся в **админской части** (data-driven: подтверждение выполняет админ/менеджер → админские данные). Архитектор согласился с доводами команды. Характер функций: подтверждение — часть основного процесса (не вспомогательная); комиссии/способы вывода — админ (вспомогательные); отчёты/история — чтение (админ). Аудит — в отдельный сервис.
3. Аудит действий — отдельный сервис (безопасность), события через Kafka.
4. support-service (тикеты) и chat-service (чат) — подтверждены как независимые.
5. customercare-service — переносится в клиентскую часть.
6. tax-service — подтверждён как клиентский сервис.
7. userinfo-service — остаётся бизнес-оркестратором; CQRS на будущее при проблемах с производительностью.
8. chat-service — отдельный общий микросервис с изолированной БД; файлы — Postgres `bytea`; синхронизация — через Kafka.
9. Keycloak — архитектор готовит рекомендации (единый vs раздельный).
