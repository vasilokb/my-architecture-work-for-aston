## 2. Ход обсуждения

### 2.1. Постановка проблемы (00:01–02:15)

- Команда клиентская и команда админская ведут разработку параллельно; известно, что **требования размазаны по клиенту и админке**.
- Для клиентской части архитектура существует, дорисована и расписана.
- Для админской части — **архитектуры нет вообще**.
- Озвучены ключевые боли:
  - слишком большое количество проблем с интеграцией между частями;
  - некоторые сервисы не относятся однозначно ни к одной из частей;
  - часть сервисов присутствует только в рамках нарисованной архитектуры и фактически не используется;
  - требования не пересматриваются и не обновляются с течением времени.

### 2.2. Уточнение понятия «админская часть» (02:22–03:37)

- **Архитектор (№1):** ожидал, что «админская часть» — это управление доступами, справочниками, где администратор корректирует данные. Удивлён, что к админке относят часть с реализованной бизнес-логикой.
- **Участник (№3):** по сути это два разных приложения с общим бэкендом — UI для сотрудников (тех, кто работает с клиентами) и UI для обычных пользователей-инвесторов.
- Достигнуто общее понимание: «админская часть» = **интерфейс и сервисы для сотрудников-менеджеров**, а не техническая админка с ролями/справочниками.

### 2.3. Разделение ответственности клиент ↔ админ (04:30–30:55)

Принятый критерий разделения (формулировка представителя команды):

> **Клиентская часть** — всё, что делает **сам клиент**: регистрация, торговля ценными бумагами, управление портфелем, подача заявок, заполнение своих данных, получение услуг.
> **Админская часть** — всё, что делает **менеджер компании**: ведение клиентов, заведение сотрудников компании, общение с клиентом (саппорт), заполнение новостных статей, метрики по клиентам и сотрудникам.

**Ключевое уточнение по торговле (~05:01–06:30, ~08:35):**
- Главная функция приложения — торговля ценными бумагами — **по требованиям относится к клиентской части**.
- Обоснование: счета и финансовая информация формируются и хранятся в клиентской части, поэтому торговля к ней привязана.
- В будущем требования могут измениться — но тогда потребуется перестройка текущей логики.

**Уточнение по сделкам от лица менеджера (~29:47–30:08):**
- Прямого совершения сделок от имени клиента менеджером сейчас **не предполагается**.
- Однако отдельные сервисы неизбежно будут пересекаться между частями.

### 2.4. Аналогия с АБС — концептуальная рамка (16:00–17:34)

Архитектор (№1) предложил полезную аналогию:

- **Ядро = автоматизированная банковская система (АБС):** учёт клиентов, счетов, справочников параметров счетов, учёт транзакций. В проекте этому ядру соответствует **клиентская часть**.
- **Всё остальное строится поверх ядра:** CRM, уведомления, мобильные приложения, метрики, образование и т. п. — это **админская часть**.
- В реальной финтех-компании за эти области отвечают **разные команды и разные бизнес-направления** (продажи, безопасность, поддержка и т. д.).
- **Вывод:** админская часть — это не единый домен, а набор разных доменных областей, сгруппированных по принципу «обслуживание бизнеса и клиента со стороны сотрудника».

### 2.5. Функциональный состав админской части (07:10–22:00)

Выявленные направления (по требованиям):

| Направление | Что входит |
|---|---|
| **CRM / работа с клиентами** | Управление клиентами, просмотр и редактирование, история, счета, метрики |
| **Коммуникации** | Чат клиента с личным менеджером — планируется вынести в **общий** сервис (пересекает границу клиент/админ) |
| **Поддержка** | Саппорт клиентов, тикеты |
| **HR** | Учёт сотрудников компании, рабочие места, метрики по сотрудникам |
| **Безопасность** | Аутентификация сотрудников, профили |
| **Образование (админ-контент)** | Наполнение образовательного контента, новостных статей |
| **Тарифы/услуги** | Подключение платных услуг — статус обсуждается |
| **Финансовая аналитика** | Отчёты по операциям, история транзакций |

### 2.6. Объём предстоящих работ (~21:12)

- ~141–142 истории (user stories) для клиентской части.
- Примерно столько же — для админской части.
- Проект должен считаться завершённым после реализации этих объёмов.

### 2.7. Анализ текущих сервисов (10:35–38:30)

Принято решение ориентироваться на **прод-стенд**: сервисы, задействованные в реальных фичах на проде, считать актуальными; остальные — кандидаты на удаление.

По конкретным сервисам:

| `account-service-pb` | Пустой, фактически не существует |
| `trading-service` | По требованиям — **клиентский**; физически лежит в `backend/` — это историческое несоответствие |

### 2.8. Контекст развёртывания (~41:19–43:00)

- Используются **три стенда:** feature → test → prod.
- Рабочий процесс: фича реализуется на feature-стенде → тестируется → вливается → выкатывается на test → затем на prod.
- Клиентская и админская части работают по одному и тому же процессу.

### 2.9. Управление задачами (44:55–конец)

- Демонстрация доработанной системы задач (Jira).
- Предложено разбить тяжёлую сводную таблицу по **эпикам** (например, «Обслуживание», «Выдача наличных» и т. д.) с динамически генерируемыми подтаблицами по подзадачам.
- Каждая подзадача должна содержать: аналитика, разработчик, номер подзадачи, срок, причина переноса и т. п.

## 3. Структура проекта и статус сервисов

Проект разделён на две части по принципу «кто действие выполняет»:

```
investment/
├── client/                          ← КЛИЕНТСКАЯ ЧАСТЬ (то, что делает клиент)
│   ├── backend/
│   │   ├── account-service          ← брокерские счета, депо, операции
│   │   ├── catalog-service          ← каталог инструментов, котировки
│   │   ├── customer-service         ← профиль клиента, регистрация, 2FA
│   │   ├── document-service         ← PDF-документы для клиентов
│   │   ├── emulator-service         ← эмуляция биржи MOEX (ордера, сделки)
│   │   ├── notification-service     ← push, SSE, email-уведомления
│   │   └── otp-service              ← генерация и валидация OTP-кодов
│   └── react/
│       └── react-service            ← фронтенд SPA (React)
│
└── backend/                         ← АДМИНСКАЯ ЧАСТЬ (то, что делает менеджер)
    ├── api-gateway                  ← единая точка входа, маршрутизация, auth
    ├── auth-service                 ← аутентификация сотрудников (JWT)
    ├── trading-service              ← ⚠️ по требованиям клиентский, физически здесь
    ├── management-service-pb        ← управление портфелями + образование (админ)
    ├── userinfo-service             ← back-office по клиентам (CRM, KYC, чат)
    ├── employee-service             ← сотрудники, рабочие места, задачи
    ├── account-service-test         ← ❌ не используется
    ├── document-service-pb          ← 📦 в архиве
    ├── education-service            ← каталог курсов (клиентский read-side)
    ├── test-service                 ← квалификационные тесты
    ├── tax-service                  ← расчёт НДФЛ, 2-НДФЛ
    ├── financialtransactions-service← история транзакций, отчёты
    ├── customercare-service         ← подключение платных услуг (статус спорный)
    ├── support-service              ← тикеты поддержки (полумёртвый)
    ├── newsfeed-service             ← новостная лента (к админке — заполнение контента)
    └── criticalfeedbackchannel      ← выведен, заменён сервисом поддержки
```

### Известные несоответствия (факт vs требования)

- `trading-service` — по требованиям клиентский, физически в `backend/`.
- `customercare-service`, `financialtransactions-service`, `tax-service` — граница клиент/админ не определена однозначно.
- Чат клиента с менеджером — планируется вынести в **общий** сервис (пересекает границу).

## 4. Принятые решения

1. **Принять критерий разделения клиент/админ:** «что делает клиент» vs «что делает менеджер компании».
2. **Приписать торговое ядро к клиентской части** (по требованиям, несмотря на физическое расположение `trading-service` в `backend/`).
3. **Описывать админскую часть как набор модулей** по бизнес-направлениям, а не как единое целое — в соответствии с аналогией АБС.
4. **Формат результата:** верхнеуровневое описание архитектуры админской части с явно зафиксированной границей между клиентской и админской частями.
5. **Место результата:** черновик выкладывается в **Confluence** с правом последующего обсуждения и доработки.
6. **Признать несоответствия** между физическим расположением сервисов и их бизнес-принадлежностью — зафиксировать их как известные долги, не пытаться решить в рамках текущей задачи.
7. **Использовать прод-стенд как источник истины** по фактическому составу актуальных сервисов.
