# Протокол встречи — 14.07.2026

## Что обсуждали

1. **Запрос на архитектуру админки.** Для клиентской части архитектура есть, для админской — нет. Нужно описать так, чтобы не противоречить тому, что уже реализовано.

2. **Что считать «админской частью».** Это не техническая админка со справочниками и ролями, а интерфейс и сервисы для сотрудников-менеджеров: ведение клиентов, общение с ними, заведение сотрудников, заполнение контента, метрики.

3. **Граница клиент/админ.**
   - Клиентская часть — всё, что делает сам клиент: регистрация, торговля ЦБ, портфель, заявки, свои данные.
   - Админская часть — всё, что делает менеджер: работа с клиентами, саппорт, HR, образование, метрики.

4. **Где живёт торговое ядро.** По требованиям торговля ценными бумагами — клиентская часть (счета и финансы хранятся там). Физически `trading-service` лежит в `backend/`, но это историческое несоответствие, не архитектурное решение.

5. **Аналогия с АБС.** Клиентская часть — ядро учёта (клиенты, счета, транзакции), админская — всё вспомогательное поверх ядра (CRM, уведомления, образование и т.д.). В реальном финтехе за эти зоны отвечают разные команды.

6. **Состав админской части** (по направлениям): CRM/клиенты, коммуникации (чат), поддержка, HR, безопасность, образование (админ-контент), тарифы/услуги, финансовая аналитика.

7. **Объём работ.** ~141–142 истории для клиента и примерно столько же для админки.

8. **Развёртывание.** Три стенда: feature → test → prod. Обе части работают по одному процессу.

## Структура проекта и статус сервисов

Проект разделён на две части по принципу «кто действие выполняет»:

```
investment/
├── client/                          ← КЛИЕНТСКАЯ ЧАСТЬ (то, что делает клиент)
│   ├── backend/
│   │   ├── account-service          ← брокерские счета, депо, операции
│   │   ├── catalog-service          ← каталог инструментов, котировки
│   │   ├── customer-service         ← профиль клиента, регистрация, 2FA
│   │   ├── document-service         ← PDF-документы для клиентов
│   │   ├── emulator-service         ← эмуляция биржи MOEX (ордера, сделки)
│   │   ├── notification-service     ← push, SSE, email-уведомления
│   │   └── otp-service              ← генерация и валидация OTP-кодов
│   └── react/
│       └── react-service            ← фронтенд SPA (React)
│
└── backend/                         ← АДМИНСКАЯ ЧАСТЬ (то, что делает менеджер)
    ├── api-gateway                  ← единая точка входа, маршрутизация, auth
    ├── auth-service                 ← аутентификация сотрудников (JWT)
    ├── trading-service              ← ⚠️ по требованиям клиентский, физически здесь
    ├── management-service-pb        ← управление портфелями + образование (админ)
    ├── userinfo-service             ← back-office по клиентам (CRM, KYC, чат)
    ├── employee-service             ← сотрудники, рабочие места, задачи
    ├── account-service-test         ← ❌ не используется
    ├── document-service-pb          ← 📦 в архиве
    ├── education-service            ← каталог курсов (клиентский read-side)
    ├── test-service                 ← квалификационные тесты
    ├── tax-service                  ← расчёт НДФЛ, 2-НДФЛ
    ├── financialtransactions-service← история транзакций, отчёты
    ├── customercare-service         ← подключение платных услуг (статус спорный)
    ├── support-service              ← тикеты поддержки (полумёртвый)
    ├── newsfeed-service             ← новостная лента (к админке — заполнение контента)
    └── criticalfeedbackchannel      ← выведен, заменён сервисом поддержки
```

### Известные несоответствия (факт vs требования)

- `trading-service` — по требованиям клиентский, физически в `backend/`.
- `customercare-service`, `financialtransactions-service`, `tax-service` — граница клиент/админ не определена однозначно.
- Чат клиента с менеджером — планируется вынести в **общий** сервис (пересекает границу).

## Что решили

1. Разделять клиент/админ по принципу «кто действие выполняет» — клиент или менеджер.
2. Торговое ядро относить к клиентской части.
3. Описывать админскую часть как набор модулей по бизнес-направлениям, а не как единый монолит.
4. Формат результата — верхнеуровневое описание архитектуры с зафиксированной границей.
5. Черновик выложить в Confluence для обсуждения.
6. Несоответствия между физическим расположением сервисов и их бизнес-принадлежностью — зафиксировать как долг, не ломать сейчас.
7. Актуальность сервисов определять по прод-стенду.
